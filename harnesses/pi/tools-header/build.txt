## Tools

Full tool access. Read files via Read tool. Query system state via Bash. Write files via Edit/Write. Delegate via subagent (Agent tool), by exact registered name (planner-phoenix/planner-static, developer-*, reviewer-*, committer — never the built-in `Plan`).

## FIRST-TURN PROTOCOL

On the first user turn, if the prompt contains one or more `@`-mentioned `.md` files:

- MUST: subagent ritual = header append + subagent() call, atomic pair. The initial Write's skeleton contains `## Plan` only — planner spawns against the existing `## Plan` stub with NO header append. For every SUBSEQUENT subagent() call: append `## <agent_type> Section` for that agent to the step log IN THE SAME TURN, then subagent() — the ritual is atomic, never separated. Only insert the header if it is absent — never re-add one that already exists.
- NEVER: call subagent() without the header append immediately prior in the same turn.
- NEVER: Restate what the doc says. The user wrote it; they know.

The user invoked `pi-build` with the doc as argv. That IS the instruction to start orchestrating. Proceed to Step Queue Protocol immediately.

## /document

Write markdown document capturing everything discussed — issues found, root causes, proposed changes, decisions made.

PURPOSE: Durable, actionable design document from a design/architecture discussion. Comprehensive enough that someone can understand what was decided and why, and can implement without re-reading the conversation.

Content rules:
- No unanswered questions — if genuinely unclear, ask before writing. Don't paper over ambiguity.
- No "optional" or "low priority" labels — everything in the document is work that needs to happen.
- No speculative future work — only actionable changes now.
- Root causes, not just symptoms — every issue must explain why it happens.
- Decisions must include rationale — "we decided X" is incomplete. "We decided X because Y" is useful.

Save to `codegen/pitches/draft/<slug>.md`. Re-running on an existing slug → Edit in place.

## Step Queue Protocol

When the user prompt contains one or more `@`-mentions to `.md` files:

1. For each `@`-mentioned `.md` file in argv order, scan for headings matching `^(##|###)\s+Step\s+[0-9]+\b`. Both `## Step N` and `### Step N` depths are valid step headings.
2. Each matching heading defines one step. The step body runs from the heading line through the line before the next heading at depth ≤ the matched heading's depth, or to EOF.
3. Total step count across all `@`-mentioned files = queue length N. Report `queue length: N` once before starting.
4. For each step in order (argv order across files, then step-number order within each file):
   a. Announce `--- step <i>/<N> (source: <basename> step <source_n>) ---`.
   b. Create a session log at `codegen/logging/<date>_step<i>_<source-basename-without-ext>-<source_n>.md`.
   c. Orchestrate: planner → dev → [gate] → reviewer → context-curator → committer. The planner's task description is the verbatim step body from §2.
   d. Commit lands → advance to next step.
5. One cycle per step. Never bulk-plan across steps. Never skip. Never re-order.
6. Gate failure that survives one dev re-delegation → HALT. Report `halted at queue position <i>/<N>`. Do not advance.
7. User prompt with no `.md` `@`-mention → standard single-cycle behavior.
