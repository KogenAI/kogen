# Refuse acceptance that runs unwritten tests

Slug: k-shape-unwritten-tests
Model: not applicable — one more refusal in the existing Shape submission path and a reworded Build notice; no new state or transition
Acceptance:
- .kogen/intents/k-shape-unwritten-tests/acceptance.feature
- features/steps/k_shape_unwritten_tests_steps.js

Fix K-SHAPE-UNWRITTEN-TESTS (change_type: fix; Studio kogen issue 35634814-99a3-4d1e-a42d-b84d42f860e8, the same shape-acceptance family as issue 42502600). K-APPROVAL-REBASE's shaped acceptance ran named Go tests that did not exist before the Build, for example `cd cli && go test -count=1 -json -run ^TestApprovalRebaseInstalledMove$ .`, which exits 0 and reports the test as absent (ran zero times). All four scenarios stayed red through 11 verification passes in Build 043fc6db and again in Build 619ca93e; each ended `no_progress` ("the builder was told which required acceptance items are missing and answered again without a tool call"). Acceptance that depends on names the Build has to invent cannot be passed by a correct implementation whose tests are named differently.

After this change Shape does not publish acceptance whose pass depends on a named test that does not exist yet, and tells the shaper why; acceptance that observes behaviour (and acceptance that runs tests that already exist) is published as before. The Build's missing-items notice tells the builder to act with its tools or report a blocker; a builder that still answers without a tool call stops at once, as today. No new command, flag, option or setting; no timeout, retry or limit change.

## Shape: refuse acceptance that runs tests nobody has written
- Where: every Shape, native and external (`executor: claude-code`), in the readiness check of a complete candidate (`certify`, reached from `checkSubmission` in `cli/shape/shape.go`), after the dry run produced accounted scenario results (no not-ready problems) and before the candidate is returned as readiness observations or accepted as ready.
- What counts as an unwritten test: a scenario with status `failed` whose failing step's named-test analysis reports a required test as not run. The analysis is the existing one in `cli/verify/namedtests.go` (`missingNamedTests`, from the step's arguments, `-run` selectors and `go test -json` rows in the failure), which today only feeds the Build's `required tests that did not run` block. Each of its lines of the form `<id>: did not run (<why>)` is an unwritten test. A line `<id>: skipped` (the test exists) is not, and tests that ran (passed or failed) are not. The analysis result has to reach Shape with the scenario result (for example a field that is not serialized); the readiness record format is unchanged.
- Refusal: when at least one scenario has an unwritten test, nothing is published for this submission, and its tool result (external Shape: the next round's feedback) is exactly the headline
  `Acceptance depends on tests the Build would have to invent: <N> scenario(s) run named tests that do not exist before the Build; nothing was published. Acceptance must observe behaviour that any correct implementation produces (run the program, call the code or inspect its output), not test names or files the Build has to write. Rewrite these steps; resubmitting them unchanged is refused again.`
  followed by one line per unwritten test, scenarios in feature order and tests in the analysis's order, exactly `- <scenario name> (line <line>): <the analysis line>`, for example `- The doubling test passes (line 2): TestWidgetDoubles: did not run (no tests to run)`, joined by single newlines with nothing after the last line. N is the number of scenarios with at least one unwritten test.
- It is an invalid submission under the existing rules (SHP-4): one `submission_refused` event with gate `unwritten_tests` whose problems are the item lines; it counts on the shared invalid-submission counter; accumulated proposals stay; the written files stay as after other not-ready feedback. A refused candidate supplies no readiness evidence and is never acknowledgeable: an unchanged resubmission is refused again with the same text, never `accepted: unchanged checked observations acknowledged`. At the third invalid submission Shape ends as today with `intent/not_ready: the Intent is not ready to build` and the item lines (exit 1); the files of that last attempt stay.
- A candidate without unwritten tests continues unchanged: accounted red goes back as readiness observations to acknowledge, green is ready.
- Shaping instructions: after the existing `Named-test helpers:` guidance in `cli/shape/context.go` (kept unchanged), Shape's instructions add exactly this paragraph, ending with a newline: `Unwritten tests: acceptance must not depend on test names or files the Build has to invent. A step may run a named test only when that test already exists before the Build; Shape refuses a candidate whose acceptance runs a named test that did not run on the unchanged tree. Observe behaviour that any correct implementation produces instead.` Refine's instructions do not carry it, like the named-test guidance.

## Build: the missing-items notice names both ways forward
The native missing-items notice (`missingItemsNotice` in `cli/build/noprogress.go`) replaces its sentence `Work on them now with your tools (write the missing tests and the implementation they need), then call finish.` with `Act on them now with your tools (change the code and the tests it needs), then call finish. If a correct implementation cannot make them pass because a protected acceptance file is wrong, call report_blocker with its paths, the contradiction and your observed evidence instead.` Everything else is unchanged; for one missing scenario the complete notice is:

```
Required acceptance items are still missing: verification pass 2 is the same red as the pass before it, and your last round ended without a tool call. The Build is not complete until each of these acceptance scenarios passes:
- failed: The candidate app (line 2)
Act on them now with your tools (change the code and the tests it needs), then call finish. If a correct implementation cannot make them pass because a protected acceptance file is wrong, call report_blocker with its paths, the contradiction and your observed evidence instead. Another round without a tool call into the same red stops the Build as no_progress.
```

followed, as today, by a blank line and the pass's ordinary feedback. When and how often the notice is given, the `missing_items_notice` event, the `candidate/no_progress` stop of the next tool-free round into the same red (with its `missing:` lines) and the `report_blocker` stop as `candidate/build_blocked` are unchanged.

## Unchanged and out of scope
- `kogen intent approve`, Refine, the readiness record (version 3), acknowledgment of ordinary missing-feature red, the step self-check, Feasibility checks and the Build's named-test feedback block are unchanged.
- External executors (claude-code Build) get no notice and keep their `executor_no_progress` stop after three identical passes.
- Files the Build must invent are covered by the shaping guidance only; Kogen has no reliable signal for them and the refusal detects only named tests reported as not run. Detection is not exhaustive.
- Documentation: `spec/prose/02-shaping.md` SHP-8 describes the refusal (headline, item lines, gate `unwritten_tests`, not acknowledgeable, third time `intent/not_ready`); `spec/prose/04-building.md` LOOP-7 says the notice asks the builder to act with tools or call `report_blocker`. `sh check.sh` in `spec/` must still pass. Update the expected notice in `cli/build/noprogress_test.go` and in the earlier suite `features/steps/k_build_early_stop_steps.js` to the new wording.

## Decisions
- Shaping does not declare acceptance whose pass depends on test names or files the Build must invent; such a candidate goes back to the shaper with that reason, and a behavioural alternative is accepted (source: request)
- A builder told that acceptance items are missing is asked to act (write code or tests) or report a blocker, and one that answers without tool calls ends promptly with a clear stop reason instead of repeating to the round limit (source: request)
- No new command, flag or option, and no timeout, retry or limit change (source: request)
