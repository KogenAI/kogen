# Manage Kogen's own pinned Claude Code runtime

Slug: k-managed-claude
Model: .kogen/intents/k-managed-claude/model.qnt invariants=NeverRunsUntested,InstallsOnlyTested,ActiveVersionsStayInstalled seed=31 samples=200 steps=14

Kogen stops running whatever `claude` is first on PATH. Every Claude Code role (Shape, Refine, Build, Review and resumed Builds) runs one pinned, tested Claude Code, `2.1.312`, that Kogen installs itself under `~/.kogen/claude-code/` and runs with its own configuration directory and updates disabled, so the user's own Claude Code install, settings, plugins, skills, hooks, memory and credentials neither affect Kogen's executor nor are changed by it, and an auto-update can never swap the executable mid-run. Kogen's own hooks (`--settings`) and the intended project context (the checkout, the Kogen task framing) still apply. One lifecycle covers acquisition, login, status, diagnostics, deliberate update, interruption recovery and uninstall, with no new command or flag.

Replaced or removed: `exec.LookPath("claude")` resolution in the adapter (`cli/executor/claudecode`) and in `kogen init` readiness (`cli/readiness`), the minimum-version rule (`claudecode.MinVersion` `2.1.295`, `VersionAtLeast`, `versionAtLeast`) with its `npm install -g @anthropic-ai/claude-code` hints, and the advice to sign Kogen's executor in with `claude auth login`. Other executors and providers, all timeouts, retries and limits are unchanged. Supported platforms stay macOS on Apple Silicon and Linux x86-64 (glibc).

## Requirements
1. **Pin.** Kogen's binary carries the only version source: version `2.1.312`; `darwin/arm64` maps to platform `darwin-arm64` with SHA-256 `6b5ec691195e551b02c41df9f7d723f4ea61eaa03c2df90acefe3736f1aeb620` and 275988512 bytes; `linux/amd64` maps to `linux-x64` with SHA-256 `4f4178ce41d83e23341ebfbaecdbcf8ea6bf7baea0690025abe49eeec3a5d01d` and 293592432 bytes; the download URL is `https://downloads.claude.ai/claude-code-releases/2.1.312/<platform>/claude` (Anthropic's native-installer distribution; values from its `2.1.312/manifest.json`). In production Kogen reads no manifest and never asks for `latest` or `stable`, never runs `claude install` or `claude update`, and has no setting, flag or environment variable that selects another version. Any other GOOS/GOARCH stops the role with `executor/unavailable` and `Kogen's Claude Code runtime supports macOS on Apple Silicon and Linux x86-64 only, not <goos>/<goarch>`.
2. **Storage.** `<home>` is `$HOME`. `<home>/.kogen/claude-code/` (directories 0700, created when needed) holds `<version>/claude` (the executable, 0755; `<version>` directory 0700), `config/` (Kogen's Claude Code configuration directory), `install.lock`, and `.partial-<random>/` while an installation is unfinished.
3. **When it is acquired.** Before the first Claude Code child process of a role start (Shape, Refine, Build, Review, `kogen intent resume`), when `<home>/.kogen/claude-code/2.1.312/claude` does not exist. Nothing else downloads: `kogen init`, `kogen intent approve`, `kogen provider login claude-code` and `kogen provider list` never do.
4. **How it is acquired.** Take an exclusive blocking lock on `install.lock` (waiting for another Kogen's installation); remove every `.partial-*` entry (leftovers of interrupted installations); if the runtime exists now, use it. Otherwise create `.partial-<random>/`, print to stderr `kogen: installing Claude Code 2.1.312 into <home>/.kogen/claude-code/2.1.312`, fetch the URL with one HTTP GET and stream it into `.partial-<random>/claude` while computing its SHA-256 and size. A transport error or a status other than 200 is `cannot download Claude Code 2.1.312 from <url>: <detail>`. A size or digest different from the pin is `the downloaded Claude Code 2.1.312 does not match its pinned SHA-256; nothing was installed`, and those bytes are never executed. Then set mode 0755 and run `<partial>/claude --version` with the child environment of requirement 6: unless the first whitespace-separated field of the trimmed answer is `2.1.312` the result is `the downloaded Claude Code reports <answer>, not 2.1.312; nothing was installed` (`<answer>` is the whole trimmed answer). On success rename `.partial-<random>` to `2.1.312` (one atomic rename) and print `kogen: installed Claude Code 2.1.312 (sha256 <lowercase hex digest>)`. Every failure removes its partial directory and stops the role with `executor/unavailable` (a Build exits 1, before any Claude Code round, edit or commit). The installation has no timeout or retry of its own: it ends in success, a refusal, the Build's existing deadline or an interrupt (whose exit code is kept; its partial directory is removed by the next installation). A later fresh `kogen intent build` of the same approved Intent starts the installation again.
5. **Test seam.** `KOGEN_CLAUDE_CODE_URL` is for tests only. When set it must be `http://127.0.0.1:<port>` or `http://localhost:<port>` (the `KOGEN_PROVIDER_URL` pattern), otherwise the installation is refused with `KOGEN_CLAUDE_CODE_URL must be http://127.0.0.1:<port> or http://localhost:<port>` before any request. With it, the expected digest and size are `platforms.<platform>.checksum` and `.size` of `<seam>/2.1.312/manifest.json` (the official manifest shape) and the bytes come from `<seam>/2.1.312/<platform>/claude`; everything else is identical.
6. **Running it.** The adapter's executable is exactly `<home>/.kogen/claude-code/2.1.312/claude`; `claude` is never resolved on PATH and no other version directory is ever run. At every role start its `--version` answer must have `2.1.312` as first field, else the role stops with `executor/unavailable` and `Kogen's Claude Code at <home>/.kogen/claude-code/2.1.312/claude reports <answer>, not the pinned 2.1.312; remove <home>/.kogen/claude-code/2.1.312 to reinstall it`, with no download, replacement or round. A role keeps the executable path it started with for all of its rounds. Every child (the installation's `--version`, `--version`, `auth status --json` and every round) keeps the existing environment rules plus exactly one `CLAUDE_CONFIG_DIR=<home>/.kogen/claude-code/config` and exactly one `DISABLE_UPDATES=1` (inherited values of both are removed); `HOME` stays the user's home and the argv is unchanged (`--settings` with Kogen's hooks, `--setting-sources ""`, `--strict-mcp-config` with no MCP servers, `--no-chrome`, Kogen's framing). `executor_started` keeps recording the exact version. The messages of this Intent are printed whole, never shortened.
7. **Login.** `kogen provider login claude-code` and the fd-3 token are unchanged; that token is how Kogen's runtime signs in (`claude setup-token` prints one without storing it). The user's own `claude auth login` is not visible to Kogen's runtime (separate configuration directory and macOS Keychain entry). With no stored token and an `auth status` of `loggedIn: false`, the role stops with `executor/auth_refused` and ``Kogen's Claude Code is not signed in; make a token with `claude setup-token` and save it with `kogen provider login claude-code` ``. Every other auth rule and message is unchanged.
8. **Status.** `kogen provider list` (text form) prints one more line right after the provider status lines (which end with `claude-code: token saved (not verified)` when a token is saved) and before `Official compatibility ...`, when a Claude Code token is saved or `<home>/.kogen/claude-code` exists: `claude-code runtime: Claude Code 2.1.312 installed (<home>/.kogen/claude-code/2.1.312/claude)` when that path is a regular file, otherwise `claude-code runtime: Claude Code 2.1.312 not installed`. It runs nothing and makes no request. With neither, the output is byte-identical to today; `--json` is unchanged.
9. **`kogen init` readiness** (`models`, for `executor: claude-code` roles): no PATH lookup. An unsupported platform is a problem with requirement 1's message. A present runtime whose `--version` is not pinned is the problem `claude-code: Kogen's Claude Code at <path> reports <answer>, not the pinned 2.1.312` with the fix `rm -rf <home>/.kogen/claude-code/2.1.312`. A stored token is a sign-in; otherwise a present runtime's `auth status --json` (environment of requirement 6) must report `loggedIn` with `authMethod` `claude.ai`; anything else, including no runtime yet, is `claude-code: no stored token and no claude.ai subscription sign-in` with the fix `kogen provider login claude-code`. A runtime that is not installed yet is not a problem by itself; readiness never downloads.
10. **Update.** Only a newer Kogen release changes the pin (version, both digests and sizes) to a newly tested version; its first Claude Code role installs that version into its own directory. Older version directories are never modified, run or removed except by uninstall, so an older Kogen's runs that are still active keep their executable. Claude Code has no session resume, so `kogen intent resume` starts its fresh Claude Code sessions on the version the running Kogen pins; run records keep each session's exact version.
11. **Uninstall.** `kogen uninstall` (an install.sh installation) also removes `<home>/.kogen/claude-code` with everything in it when it exists, printing `Removed Kogen's Claude Code runtime from <home>/.kogen/claude-code` between the unchanged `Uninstalled kogen from <prefix>` and `Kept your ...` lines; a removal failure is `environment/uninstall_failed` (exit 3). It never touches `~/.kogen/credentials/` (the saved token stays), `~/.claude`, `~/.claude.json` or the user's own Claude Code install. Without that directory the output is unchanged.
12. **No fallback.** Never the Claude Code on PATH, an API key or other paid route, another version, or the native executor instead.
13. **Existing tests and documents.** Tests that fake Claude Code (Go tests, `test/acceptance` support and fixtures, earlier `features/steps` drivers) provide the fake as `$HOME/.kogen/claude-code/2.1.312/claude` reporting `2.1.312` (or through the seam), never on PATH and never from the network; minimum-version tests become pinned-version tests. Spec LOOP-15 and INS-5 prose and the `spec/features/04-building.feature` scenario "A Claude Code older than the qualified version is unavailable before any edit" describe the pinned runtime ("not the pinned version"). README, `docs/configuration.md`, `docs/executor-contract.md` and `docs/getting-started.md` describe the managed runtime, the seam as test-only, and making a token without an own Claude Code: `CLAUDE_CONFIG_DIR="$HOME/.kogen/claude-code/config" "$HOME/.kogen/claude-code/2.1.312/claude" setup-token`.

Deterministic acceptance uses the shipped packaged Kogen, a different Claude Code on PATH, a customized user setup and the loopback seam serving a scripted runtime. A live run on the real downloaded 2.1.312 with a real token remains the separate release real-use gate.

## Decisions
- Kogen's runtime is Claude Code 2.1.312, the version delivery pinned by hand on every build host after 2.1.314 broke the executor hooks; nothing selects another version. (source: request)
- Kogen keeps its runtime in `~/.kogen/claude-code/`, apart from the user's Claude Code, with its own configuration directory there. (source: request)
- The pinned runtime is installed by the first Claude Code role that needs it, with two progress lines, so the agreed CLI gains no command or flag. (source: request)
- Login stays `kogen provider login claude-code`; status is a `claude-code runtime:` line in `kogen provider list`; diagnostics name the exact path and the fix. (source: request)
- Updates arrive only with a Kogen release that pins a newly tested version; older version directories stay until uninstall so active runs keep working. (source: request)
- `kogen uninstall` removes `~/.kogen/claude-code` and keeps `~/.kogen/credentials` and the user's own Claude Code. (source: request)
