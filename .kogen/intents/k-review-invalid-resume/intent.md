# Resume green Builds after an invalid review

Fix K-REVIEW-INVALID-RESUME (change_type: fix). Today a Build whose candidate passed every check can still be lost to a review that ends without a valid verdict (`candidate/review_invalid: the reviewer did not return a valid verdict; edits are left in place`). On the direct provider route, the native reviewer used by the repository lineup (gpt-6.1 shape/build/review), the existing review-only rules refuse such a stop in two cases. In the first, a later invalid review (after the one automatic fresh review) left uncommitted edits, refused as "the candidate changed after its green pass". In the second, the review had already had a verdict judged and sent back ("the review already had a verdict judged and its verified edits are part of the pass"). No review-only checkpoint is saved. The last checkpoint is the native request's `tool` stage, so `kogen intent inspect` reports `resume: unsupported (not authorization)` and `kogen intent resume` refuses `uncertain tool boundary`. That was observed on this HEAD with the package's scripted provider. A Claude Code reviewer in the same situation is resumable only through the 3e759e8 external-stage path. After this change, such a stop is a review-only checkpoint of the green candidate the review started from, whatever executor runs the review. An explicit resume discards the stopped reviewer's uncommitted edits and starts one fresh review of that candidate, with no builder round and no rerun of checks. No command, flag, option, setting, retry or limit is added or raised.

1. **Every review knows its green base.** A review session's base is the complete green pass it was started from. For a session the Build starts (the ordinary review, the automatic fresh review, a resume's fresh review), it is the pass that session is given. Every checkpoint saved at the review stages `review`, `review_verify` and `review_retry_verify` now carries `continuation.base` for native reviewers too: the same JSON shape as `continuation.pass`, unchanged through the session's rounds and repairs. External reviewers already carry it (3e759e8). A native session continued by `kogen intent resume` from such a checkpoint takes its `continuation.base`. When that checkpoint has none (written before this change), the base is the checkpoint's `continuation.pass` if the saved session is not marked `repaired`; otherwise the session has no base.

2. **An invalid ending of a green candidate stops with a review-only checkpoint.** This applies when a review (native or external) ends without a valid verdict and today's rules give it neither the automatic fresh review nor a review-only checkpoint. The Build still saves the review-only checkpoint when all of the following hold:
   - the review is not the reopened conversation of a blocked review;
   - it has a base, and that base is complete green evidence;
   - HEAD, the protected baseline, the approval and the user's index pass today's checks (still checked first and reported as themselves).

   This covers a later invalid review that left uncommitted edits, and a review that had repaired: its own pass may be red or unreviewed, but its base is green. Effects:
   - the checkpoint's `continuation` is `{"stage": "review_only", "pass": <base>}`;
   - `review_retry` is the base tree's record, with this review appended (`next: "stop"`);
   - the run log has `review_only` with `review` `<n>`, `eligible` true, `tree` the base tree, `next` `"stop"` and both allowance counters;
   - the reviewer's uncommitted edits are left in place, with nothing discarded at the stop and the stop output unchanged;
   - the local facts give `resume_status` `potentially_available`, so `kogen intent inspect` prints `resume: potentially_available (not authorization)` and the `kogen intent resume <id> --project ...` line.

   Allowances are unchanged. The rejected-verdict and prose-only allowances, the tool-choice reminder, and when the one automatic fresh review runs all stay as today: a review that had repaired still gets no automatic fresh review, and the first invalid review of an unchanged base still gets it after its edits are discarded. Still not eligible, logged `eligible: false` with today's `why` and leaving no review-only checkpoint: a reopened blocker, a moved HEAD (including a reviewer's own commit), a changed index, approval or baseline, and a review without a complete green base. A `changes` verdict is never an invalid review.

3. **Resuming a review-only checkpoint discards the stopped review's edits and starts one fresh review.** All existing resume validation runs first, unchanged: checkpoint, custody, approval, baseline, configuration, Intent, index, HEAD, and a candidate identical to the checkpoint's candidate. Any change after the stop is therefore still refused, with today's `candidate contents/modes or unrelated paths changed: <paths>` message.
   - Before any new run, the saved pass must be complete green evidence, and its tree must be the tree of the checkpoint's `review_retry` record. Otherwise the resume is refused with `candidate/resume_refused` and today's message `the candidate is not the green tree of the saved review-only pass: ` followed by today's tree-drift text: observed tree, green tree, then the changed paths or why they cannot be inspected.
   - The checkpoint's `last_pass` is no longer required to equal the saved pass, because it may be a later pass of the stopped review's own repairs.
   - The candidate review tree (without other Intents' folders) may differ from the saved pass tree: those are the stopped reviewer's uncommitted edits, preserved since the stop.
   - After the ordinary lineage line `resuming Build <id> as <new> (root <root>)`, if the review tree differs from the saved pass tree, the existing review-edit restore discards the edits. It logs `review_edits_discarded` with `review` `<n>` (the checkpoint's review count), `tree` the saved pass tree, `candidate` the old tree and `paths` `[{path, change}]`. It prints `discarded review <n>'s uncommitted edits, which are not part of that green candidate: <paths joined by ", ">`. If the restore fails, or the checkout is not exactly the saved pass tree afterwards, the resumed Build stops with `candidate/resume_refused` naming the cause, and no review starts.
   - The Build's last pass then becomes the saved green pass, and today's review-only resume continues: the `review_retry` event `kind: "resume"`, then exactly one fresh review numbered `<n+1>` of the saved pass. It is a new conversation or session of the same reviewer, with the same model, effort, material, rules and allowances; it is never the invalid conversation. There is no builder round and no verification rerun.
   - An approval of the unchanged green tree commits it without a new pass. Approved reviewer edits get ordinary external verification. `changes` stops as `review_blocked`. An invalid ending stops as today: `candidate/review_invalid` with a review-only checkpoint and no automatic fresh review, since the resume records the automatic retry as spent. Each explicit resume starts one more review.

4. **Executors.** Rules 1-3 apply to native and external (Claude Code) reviewers alike. An external review's invalid ending is therefore now a review-only checkpoint too. The 3e759e8 external review-stage resume (`resumeExternalReview`, its `continuation.base` refusals and messages) remains unchanged for its other stops (round limit, executor failure, interruption). Claude Code's declared `resume: none` is unchanged and no reviewer session is revived.

Update the prose that states the old rule: README's `candidate/review_invalid` resume paragraph ("a review that used edit tools is no obstacle while the exact green tree is intact ...") and REV-4 in spec/prose/06-reviewing.md ("Only a completed review that used no tool able to change the checkout qualifies"). Both must say that an invalid ending of a green candidate stops with a review-only checkpoint, with the reviewer's uncommitted edits left in place, and that resume discards and logs them before the fresh review. The acceptance driver is compiled into package `build` with `go -overlay`. It uses the existing package test helpers (`newEnv`, `buildKogen`, `env.cli/credentials/useExternalReviewer/runIDs/runPath/head`, `landScript`, `prose`, `submit`, `finding`, `writeApp`, `fakeProvider.then/calls/count/reviewRequests`, `requestInput`, `requestText`, `cacheKey`, `jsonOf`, `newLineupExec`, `withLineup`, `withLineupResume`, `lineupWriteApp`, `verdictJSON`, `blockingFinding`, `harnessUsage`, `testSlug`); keep their names and behaviour.

## Decisions
- No new command, flag or option, and no retry or limit increase (source: request)
- Resume repeats only the review, with the same review allowances as before; an invalid verdict on the resumed review stops as it does today (source: request)
- Resumable whatever executor runs the review, without repeating checks already passed on the same tree (source: request)
