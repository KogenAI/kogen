## Root causes

- **Audit migrated one lookup, not the consumer.** `test/support/live_rework_audit.ex:115-134` now points at the unified `state.json`, but every downstream check still parses legacy flat Check records. The nested controller writes unified per-attempt state at `lib/kogen/build/verification.ex:30-31`, keeps the Candidate's Check history in the worktree via `lib/kogen/check.ex:12`, and snapshots it into control at `lib/kogen/build.ex:715-717` as `candidate-artifacts/verification-history.jsonl`, hash-bound in the record's `workspace.artifacts`. Both nested records show exactly that. This is an existing-contract violation of repair-plan §2, not an Intent gap.
- **Predicted next failures, in execution order**, all masked by the resumption assertion in cycle 3:
  1. `check_records!` at line 282 requires `verification-history-*.jsonl` archives in the raw-stream directory. Neither nested log directory contains one, because `archive_history_if_requested` in `check.ex:141` reads a cwd-relative path that is now the Candidate and the archive was never produced.
  2. `current_pass!` at line 318 reads `status`, `target`, `exit_code`, `session_id`, `candidate` from unified state, whose keys are `cycles`, `candidate_id`, `developer_session_id`, `terminal_state`.
  3. `passing_check_sequence!` at line 295 fails the same way on `state-history.jsonl` lines.
  4. `developer_invocations!` at line 166 pattern-matches exactly two attempts; both nested Builds recorded three.
  5. `developer_resume!` at line 388 and the native audit call at line 91 demand exactly two Developer captures; each nested run launched or resumed the Developer three times.
  6. After `File.rm_rf!(fixture)`, `preserve/3` in `live_reviewer_rework_fixture.ex:184-191` copies only the legacy history path and `record.json`, so `candidate-artifacts/` and its digest-bound history are lost and `audit_retained!` at line 137 checks only `status == accepted`.
- **Exactly-one resumption is a mistaken test assumption.** README line 119 says invalid handoffs share the outer allowance, `build.ex:696-706` consumes one per correction, and the connected owner already asserts only `resumptions <= config.outer_resumptions` at `live_shape_to_build_test.exs:317`. The nested scenario protocol expects one Reviewer rework, but a handoff correction in the same Developer session is legitimate controller behaviour, not a replacement session. The correct audit is: attempts equal resumptions plus one, bounded by the configured allowance; one rework receipt and one accept receipt in order; one constant Developer session across all attempts; every unreviewed attempt carries a retained `handoff_semantic` or `handoff_structure` failure, never a Check failure; Developer captures equal the attempt count. To keep this from masking the citation defect, the audit should additionally reject any invalid-handoff failure whose rejected path is a spelling the controller itself advertised, which turns the cycle-3 defect into an audit failure rather than a tolerated extra resumption.
- **Citation producer/validator mismatch remains unimplemented.** The validator is correct and narrow: `Contract.with_reference_root(ctx.workspace.path, ctx.tracking.path, ...)` at `build.ex:581` allows exactly one absolute path and resolves relative paths in the Candidate, per `contract.ex:591-612`. The producer still advertises control-relative origin paths as data the Developer reads: `verification_state.path` at `build.ex:540` and `verification_context.path` at line 292, and `task_context` at lines 831-847 supplies `tracking_path` with no artifact locator or digest. The cycle-3 Developer cited `.kogen/runtime/scenario-tracking/<id>/record.json`, the relative spelling present in the record, and was rejected with "file does not exist". Repair-plan §1's citation field, provenance labelling, and publication rewrite of Candidate-only locators are absent. Reference snapshots are keyed by absolute worktree paths that die at `Workspace.retire` (line 1063), and `lifecycle_test.exs` was loosened to `String.ends_with?` to accept those keys instead of requiring the rewrite.
- **Fakes hard-code the one working path.** `test/support/fake_codex:40` extracts `tracking_path` from the packet, so the offline route can never observe a role copying an advertised but uncitable path.
- **Connected owner blockers, all pre-paid.** `live_shape_to_build_test.exs:284,351-374` require the legacy history at the fixture root, which cannot exist after the Candidate is retired, so the connected test fails deterministically even on a perfect Build. - **Other mandated controls still absent.** `test/kogen/live_rework_audit_test.exs`, `developer_handoff_test.exs`, and `worktree_publication_recovery_test.exs` are byte-identical to c1 or the checkpoint. `workspace_dependency_test.exs` is a 27-line environment-map check. `commit_failure_rollback_test.exs:28-41` still accepts either publication success or commit failure. ## Installation workflow and authority

The admitted c1 controller requires an empty `git status --porcelain`, so untracked files count, an attached branch of any name, and commits with `git commit -F` on the current branch of the invoking checkout, per `git.ex:201-237` and `build.ex:141-154` at c1. Consequences:

- A linked worktree cannot check out `main` while the original does, a detached worktree fails the attached-branch check, and a separate clone commits to that clone's `main`, leaving a human fast-forward into this repository. None of those is controller publication of this `main`.
- The only supported workflow that ends with the controller committing to this `main` is the original checkout on `main` at c1 with an empty working tree: the 41 dirty paths must be out of the tree for the run's duration, and the Developer must import them from Git objects.
- Other-Draft interference is a discipline constraint, not a lock: nothing may write under `.kogen/intents/drafts/**` or the Approved package in that checkout while the Build runs. Moving the other Draft's shaping to a second checkout is operationally feasible because drafts are ignored files the human can copy.

Authority decisions required:

1. The newer dirty repairs are not bound by any Git object the package names. `developer-recovery.md` binds only `913ba174`, and its "preserve newer work" clause assumes the work is present, which a clean start forbids. Either the Shaper commits the current tree as a second checkpoint on the retaining branch and amends `evidence/saved-implementation.yaml` and `developer-recovery.md` to name it, which reopens the package, or the Developer must rediscover repairs such as the `mix.exs` guard in `compiled_fixture.exs` that no package text describes. This is not authorized by the current approval.
2. Replacing "exactly one resumption" with an allowance-bounded, attributable count is within the guarded paths and consistent with README and the connected owner, but the Reviewer could read the scenario protocol as pinning one. A one-line Shaper decision in `decisions.md` removes that ambiguity cheaply.
3. All other repairs are already fully authorized by `repair-plan.md` and `may_change_guarded_paths`; no new registry or attestation mechanism is needed, and I do not recommend one.
