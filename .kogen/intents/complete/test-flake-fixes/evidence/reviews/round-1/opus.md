## Findings

- **[BLOCKING] The process_custody fix does nothing, so the flake stays.** `drain_standin` returns only after the standin OS process has exited (`test/kogen/process_custody_test.exs:343-350`, `:433`). Only the standin's own code writes `.kogen/build.lock` (`lib/kogen/process_custody.ex:68-71`, `:175-208`, `:230-233`). The supervisor and provider never touch it. So by `:440` nothing can remove the lock later: if it is there, it stays. `wait_until/1` would wait 5 s and then fail the same way. The real cause is a race inside the standin. In `"stop"` mode, `release/1` (`test/support/custody_controller_standin.exs:49`) runs while the Task's `run/3` is still finishing. Its `forget_group` (`process_custody.ex:349`, `:198-203`) can read the lock after `teardown`'s `write_lock` (`:220`) and write it back after `File.rm` (`:232`), which recreates the lock for good. There is a second race: if registration takes longer than the 300 ms sleep (`standin.exs:46`; `await_registration` can take about 1 s, `:479-492`), teardown finds no groups. The provider never exits on its own (`provider.sh:18-21`), so `Task.await` hits its 5 s timeout and `:433` fails. This is a race in production code, and `lib/` is excluded by the non-goals. Five green runs could pass by luck and land the wrong fix. — **Fix:** reshape. Add `lib/kogen/process_custody.ex` to the guarded paths. Stop `record_group`/`forget_group` from recreating a lock that `release/1` removed, for example by making lock updates conditional on this controller still owning the lock, or by serialising them. Add a scenario that covers release racing a finishing run.

- **[BLOCKING] The terminal_probe diagnosis is unproven, and "deterministic" can't be shown as written.** The test throws away the probe's message (`test/kogen/terminal_probe_test.exs:71`), and the log records no message either (`ORCHESTRATOR-LOG.md:313`). The same status 1 on "success" also comes from:
  - the 2.0 s startup deadline (`test/support/terminal_probe.py:27`, `:116-127`), which covers Python startup, `Popen`, and writing the pid file and marker under load;
  - the 3 s survivor check (`:89-98`).
  
  Removing the 0.2 s sleep only matters if the process stalls for more than 1.8 s against the 2.0 s completion deadline (`:26`). It does nothing about the startup deadline. Any wall-clock deadline can still be missed, so "deterministic without changing any deadline" can't be proven. Removing the sleep also drops coverage: the descendant is no longer picked up by the process-tree walk (`:131-133`), leaving only the pid-file and `killpg` paths. That may be acceptable, but the draft should say so. — **Fix:** first change the assertion to `assert status == 0, message` so the next failure names the deadline that was missed. Then have the Shaper decide whether a startup-deadline flake may be fixed by passing an explicit per-test `--startup-timeout`, which the draft currently forbids.
