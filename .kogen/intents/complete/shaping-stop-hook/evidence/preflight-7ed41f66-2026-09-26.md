## Question: does the fixture-copy step used by the live evaluation exclude
`.kogen/build.lock`, and does it handle a Candidate worktree's `.git` file
correctly?

**Method.** Read `test/support/shaping_evaluation/driver.py:344-352`
(`setup_fixture`) and its `copy_dependency_sources()` helper. Grepped
`test/kogen/shaping_evaluation_test.exs` and `driver.py` for
`build.lock`/`build_lock`.

**Observed.** The rsync exclude list is:
```
rsync -a --exclude=_build --exclude=deps --exclude=.git \
          --exclude=.kogen/runtime --exclude=.kogen/intents \
          --exclude=test/support/shaping_evaluation  <PROJECT>/ <fixture>/
```
`.kogen/build.lock` is a single file, not under either excluded directory,
and is not excluded by name: it would be copied into every case fixture
when `live-shaping-quality` runs from inside a Build (i.e. while the outer
checkout holds the lock). Zero matches for `build.lock`/`build_lock` in
either file, so no existing regression test guards this: the scenario
`evaluation-fixture-excludes-build-lock` is still needed.

`.git` (a directory in a normal checkout, or a one-line gitdir-pointer FILE
in a linked Candidate worktree) is excluded by name either way, so the
fixture never inherits a Candidate worktree's gitdir pointer. Keep that
exclusion; it already covers the worktree case by accident of matching on
name, not type.

## Question: is a Stop hook's toolchain resolution ("KOGEN_SHAPING_TOOLCHAIN_PATH")
plausible in this environment?

**Method.** `which mix elixir erl`, then `env -i HOME=$HOME
PATH=/usr/bin:/bin sh -c 'which mix elixir erl'`.

**Observed.** The normal shell resolves all three via mise-managed install

## Question: what does the write boundary actually confine, and is Shaping
subject to it?

**Method.** Read `lib/kogen/build/write_boundary.ex` in full; ran an
offline `sandbox-exec` reproduction with a minimal grant-only profile
against a scratch directory, `$HOME`, and `/tmp`.

**Observed.** One macOS Seatbelt profile (`(allow default)(deny
file-write*)` then explicit `subpath` grants) wraps a Build role's whole
process tree. Grants: Candidate worktree, harness home, per-Build tmp_dir,
optional Claude/Codex scope grants (minus denied Codex sub-entries), the
login Keychain file, and stdio/pty devices. `forbidden/4` refuses `/`,
`/private/tmp`, `/private/var`, `/tmp`, `/var`, `$HOME` or any ancestor of
`$HOME`/the control root as a grant. This is applied only at Build
admission (`lib/kogen/build.ex:462`); Shaping (launch `nil`) is never
wrapped by it. The offline reproduction confirmed: writes inside a granted
subpath succeed; writes to `$HOME` or `/tmp` outside any grant are
kernel-denied ("Operation not permitted"), matching the module's own
documented behaviour.

## Provider probes

Method: real managed Codex (0.156.1) and Claude Code (2.1.281) binaries,
against the shared login scopes already logged in from prior real use; no
new paid model turns beyond the tiny schema-check calls noted below. Source:
a read-only helper's scratchpad at `probe-provider/NOTES.md` (transient),
copied here in full.

- **`--output-schema` and lookaround.** `codex exec --output-schema
  schema-plain.json ...` (model `gpt-6-luna`, effort low) exits 0 with
  `{"findings":[]}`. The same call with a lookaround pattern
  (`^(?!x).*$`) in the schema is rejected before generation: exit 1,
  `"Invalid JSON schema: regex lookaround is not supported. Found at
  $.properties.findings.items.properties.id.pattern."` This confirms the
  Draft's "no lookaround" constraint on the auditor's findings schema is
  real and precisely diagnosed by Codex itself, not a guess.
- **`multi_agent` and `--disable`.** `codex features list` shows
  `multi_agent` stage=stable, effective=true (on by default). `codex
  --disable multi_agent features list` flips it to `effective=false`;
  `codex exec --disable multi_agent --help` parses (exit 0), so
  `--disable multi_agent` works on the `exec` subcommand.
- **`--search` is interactive-only.** `codex --help` documents `--search`
  (native web_search) at the top level; `codex exec --search --help` fails
  to parse: `error: unexpected argument '--search' found` (exit 2). Any
  Draft wording implying the auditor (which runs via `codex exec`) can use
  `--search` is wrong; `--search` belongs only on the interactive Codex
  Shaper launch.
- **No feature literally named `request_user_input`.** `codex features
  list` (0.156.1) has no feature with that exact name; the nearest are
  `default_mode_request_user_input` and `request_permissions_tool`, both
  `under development` and off by default. Proving run 6 (cited elsewhere in
  this package) observed the `request_user_input_async` *tool* in use by
  default — that is a tool, not a feature flag. Any Draft text claiming
  "`request_user_input` is a feature flag on by default" should read: "the
  `request_user_input_async` tool is available by default; no feature flag
  named `request_user_input` exists in 0.156.1 (`codex features list`)."
- **Login scope inside a Build's harness home.** Source
  (`lib/kogen/codex.ex`, `lib/kogen/codex/environment.ex`,
  `lib/kogen/claude_code.ex`, `test/kogen/codex_environment_test.exs`,
  `test/kogen/harness_home_test.exs`) plus a real-binary reproduction:
  - Codex: `CODEX_HOME` is always the bound login **scope** path, resolved
    once and frozen in the Build's binding (`lib/kogen/codex.ex:213-221`
    `effective_scope/1`; `operation_root/2` at `:114-118` is only the
    private HOME/XDG/sqlite operation root, never credentials). A
    real-binary reproduction with `CODEX_HOME` set to the real shared scope
    and `HOME`/`XDG_*` pointed at a scratch private root still reports
    "Logged in using ChatGPT".
  - Claude: a Build launch sets `CLAUDE_CONFIG_DIR = <harness_home>/claude`
    (fresh, per-Build) but `CLAUDE_SECURESTORAGE_CONFIG_DIR = scope.path`
    (the frozen bound scope) — `lib/kogen/claude_code.ex:118-124`,
    `launch_environment/2`. A real-binary reproduction with that split,
    using the full inherited environment (not `env -i`), reports
    `{"loggedIn":true,"authMethod":"claude.ai","subscriptionType":"max"}`,
    matching the only two fields Kogen's `require_login`/`auth_metadata`
    read.
  - **Caveat found during this probe:** `env -i` (stripping the whole
    inherited environment) broke the Keychain call and falsely showed
    `loggedIn:false` even with the scope wired correctly. Any reproduction
    of login readiness must merge onto a full inherited environment (as
    production's `System.cmd` delta-merge does), never use `env -i`, or it
    will produce a false negative.
- **Claude settings and `AskUserQuestion`.**
  `priv/kogen/claude_code/shaping-settings.json` does not exist at
  `7ed41f66` — only `priv/kogen/claude_code/settings.json` does, containing
  just a `PreToolUse` (Bash) and a `Stop` hook, no `permissions`/`deny`
  key at all. Tool denial in this repo is argv-based
  (`lib/kogen/harness/claude.ex` `disallowed_tools/1`): built-in-agent
  denials plus, for reviewer/expert only, `@editing_tools`.
  `AskUserQuestion` is in neither list and appears nowhere as a `deny`
  entry — confirmed clear. The pinned managed Claude Code 2.1.281 binary's
  own embedded hook documentation (via `strings`) documents `"decision":
  "block"` as a supported Stop-hook result, and lists `AskUserQuestion` as
  a real built-in tool. No paid call was needed for this probe.

**Limitation.** These are point-in-time probes against the specific pinned
runtimes (Codex 0.156.1, Claude Code 2.1.281) and the machine's existing
shared login scopes; a different pinned version could change feature names
or flag defaults.
