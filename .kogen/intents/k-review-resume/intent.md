# Resume claude-code Builds after a green candidate

Fix K-REVIEW-RESUME. Today `kogen intent resume` refuses every checkpoint whose builder was an external executor (`Builds by executor claude-code cannot be resumed in this version (resume capability: none)`, cli/build/resume.go and builder.go `resumeStage`). It also refuses every review-stage checkpoint whose independent reviewer was an external executor (`an independent review by executor claude-code cannot be resumed ...`). That throws away a candidate that already passed every configured check. After this change, such a Build continues from its preserved candidate. Where that cannot be done safely, Kogen states exactly which work must be redone and why. No new command, option, setting, limit, timeout or retry is added or raised. Claude Code's declared capability stays `resume: none`: no Claude Code session is ever revived (`--resume` is still used only between rounds of one running role invocation). The external reviewer's `reviewExternal.Resume` seam keeps refusing.

1. **A claude-code builder no longer blocks resuming a review stage.** For a checkpoint whose `state.executor` names an external builder, resume refuses with the unchanged existing message only at the builder stages `builder` and `builder_verify`. At those stages the builder's own unfinished session is the work that cannot continue. At the review stages `review`, `review_verify`, `review_retry_verify` and `review_only`, the builder has finished. Resume then proceeds exactly as it does today for a native-builder checkpoint at that stage: the same validation and the same reviewer behaviour, with no builder session or round. Example (Build 7659baca): claude-code builder, native reviewer, the reviewer's approved repair stopped by SIGTERM during its final verification (stage `review_verify`). Resume now reverifies that repair and lands it as the native case does, with no new provider request. The `tool`, `commit` and `startup` stages, blockers, drift and every other existing refusal are unchanged.

2. **External reviews record their base.** While the independent review is served by an external executor (`models.review.executor` not native), every checkpoint saved at the stages `review`, `review_verify` and `review_retry_verify` carries `continuation.base`. That is the complete green pass (the same JSON shape as `continuation.pass`: `n`, `clean`, `green`, `tree`, ...) that the current review session was started from, i.e. the pass given to that reviewer's `Review` call. It stays the same through the session's rounds, its failed repairs (when `continuation.pass` becomes a later red pass) and its stop. Checkpoints of native reviewers do not get the field, and their bytes are unchanged.

3. **Resuming an external review stage starts one fresh review of the green base.** This applies to `review`, `review_verify` and `review_retry_verify` with an external reviewer. All existing resume validation runs first and is unchanged: checkpoint, custody, approval, baseline, configuration, Intent, index, HEAD, and a candidate identical to the checkpoint's. Then, where `<id>` is the stopped Build, `<x>` the review executor's name, `<n>` the checkpoint's `state.review` and the suffix is today's `refuse()` suffix:
   - a. **Blocker.** The saved review verdict is `changes` (stage `review_verify` with verdict `changes`, or stage `review_retry_verify`). Resume refuses with `candidate/resume_refused` before any new run or change: `Build <id>: review <n> by executor <x> ended with a blocking finding that only that reviewer's own new decision can clear, and its session cannot be resumed (resume capability: none); inspect the preserved candidate and evidence read-only and preserve them manually, then start a fresh Build from a Build-clean checkout under the still-current exact approval (ordinary Refine and new approval if the authority must change)`, then the suffix. A fresh session never clears a blocker.
   - b. **No base.** `continuation.base` is absent, or is not complete green evidence (the completeness rule the review-only path uses). This covers checkpoints written before this change, such as Build 94901097. Resume refuses with `candidate/resume_refused` before any new run or change: `Build <id>: review <n> by executor <x> cannot be continued (resume capability: none) and this checkpoint records no complete green pass that review started from, so no fresh review can start from verified work; start a fresh Build from a Build-clean checkout under the still-current exact approval`, then the suffix.
   - c. **Otherwise.** The resume starts its new run with the ordinary lineage line `resuming Build <id> as <new> (root <root>)`. It prints on stdout `review <n> by executor <x> cannot be continued (resume capability: none); starting fresh review <n+1> of the green candidate verified in pass <base.n>, with no builder round and no rerun of its checks`. The review tree is the candidate without other Intents' folders, as reviews see it. When it differs from `base.tree`, the stopped session's uncommitted edits are discarded with the existing review-edit restore. The resume logs `review_edits_discarded` (`review` `<n>`, `tree` `base.tree`, `candidate` the old tree, `paths` `[{path, change}]`) and prints `discarded review <n>'s uncommitted edits, which are not part of that green candidate: <paths joined by ", ">`. If that restore fails, or the checkout is not exactly `base.tree` afterwards, the resumed Build stops with `candidate/resume_refused` naming the cause, and no review starts. Then exactly one ordinary fresh review of `base` runs: a new session of the same external reviewer (same model, effort and `max_rounds`), numbered `<n+1>`, with cumulative reviewer usage. It follows every existing rule: the automatic verdictless retry, exact-tree evaluation, external verification of its edits with failures returned to that new session, `changes` stopping as `review_blocked`, and its own round limit. An approval of the unchanged base commits `base.tree` without a new verification pass.
   - The external `review_only` resume is unchanged.

In the 94901097 shape, a claude-code reviewer's red repairs exhaust `max_rounds` after the builder's green pass. A new checkpoint is then resumable: the red edits are discarded and logged, and the green candidate gets one fresh review. A resumed Build can never land work that no completed review judged on its exact green-verified tree.

Update the prose that states the old refusals: README's resume paragraph, docs/configuration.md (Resume), docs/executor-contract.md (E4, the capability table's resume row note and Routing status) and spec/prose/04-building.md LOOP-14. Keep the existing spec scenarios for the builder-stage refusal and the blocked external review: both refusals remain true. The acceptance driver is compiled into package `build` with `go -overlay`. It uses the existing package test helpers (`newEnv`, `useExecutor`, `useLineup`, `newLineupExec`, `withLineup`, `newFakeExecutor`, `externalWritesApp`, `harnessUsage`, `writeApp`, `verdictJSON`, `blockingFinding`, `lineupWriteApp`, `env.start/build/resume/writeCheckpoint/runIDs/runPath`, `attempt.shown`, `fakeProvider.calls/then/count`); keep their names and behaviour.

## Decisions
- Continue from the preserved candidate where safe; otherwise refuse, stating exactly the work to redo and why (source: request)
- Keep review independence and custody: no revived reviewer session, no landing of unreviewed or stale-reviewed work, and blockers stay with their own reviewer (source: request)
- No new command or option, and no limit, timeout or retry raise (source: request)
