# Adapt Kogen to kogen-loop af456d5

This is a fix (repo kogen, request K-REPIN-ADAPT-AF456D5). Make Kogen's configured checks pass on top of the already-landed delivery commit "Re-pin kogen-loop to af456d5", which was made with packaging/sync-kogen-loop.sh. Kogen must behave as the pinned caller contract `cli/third_party/kogen-loop/docs/contract/loop-v1.md` now describes. Do not edit `cli/third_party/kogen-loop/` or `cli/loop-pin.json`, which are protected from Builds. Add no option, timeout or limit. Keep every configured check, its settings and all useful unrelated assertions.

The pin changes two things Kogen sees. First, the shell tool text: "A new command waits up to one second; retrieval waits up to 30 seconds. Both return immediately on completion; ..." (loop af456d5). Second, a streamed attempt now ends when its visible output exceeds 131072 bytes (loop 262e88d, L-OUTPUT-CAP).

What changes:
- Kogen tests that pinned exact loop request bytes or tool text only to detect loop changes get the new pinned values.
- The one Kogen test assertion about the loop's default instructions is removed.
- Specification LOOP-5 is corrected to the new shell waits.
- The scripted provider of the window-reset building scenario stays under the visible-output bound and still proves both resets.

Acceptance runs focused regressions and that one building scenario, not the full suite. The whole command must stay within approval's 120-second limit (about 38 s measured). The complete configured checks remain the final gate on the Build's tree.

## Decisions
- Authority is the pinned loop-v1.md. Shell: a call supplies exactly one `command` or `handle`. A new command waits at most one second and retrieval at most 30 seconds. Both return immediately on completion, without an execution timeout. Running commands keep yielding `status: "running"` JSON with an opaque handle. Visible output limit: one streamed attempt (ChatGPT/SuperGrok Responses, Anthropic Messages) may carry at most 131072 visible bytes; more is a transient failed attempt. It is retried by the loop's unchanged policy (3 attempts, 2 s then 8 s backoff). A third cut ends as `provider/unavailable` with detail `ChatGPT did not answer after 3 attempts: visible output exceeded 131072 bytes`. Kogen adds no handling, retry, option, timeout or limit around either behavior. (source: request)
- Kogen tests that pinned exact loop bytes or tool text only to detect loop changes get the new pinned values. Their unrelated assertions stay unchanged. This covers the shell definition in `cli/agent/testdata/defs_golden.json` and the plain-request golden `cli/testdata/loop_knobs_golden.json` of TestResearchRemovalDefaults. It also covers the request goldens of TestKRevodGatePartsUnchanged, TestNamedFeedbackCompatibility, TestContextExternalNativeBytes and TestKReviewRetryUnchangedValidRequests, only where the shell text and the byte counts derived from it changed. Comments that name the current pin say af456d5 instead of 1a3eb18. (source: request)
- Kogen tests make no claim about the loop's default instructions or other loop behavior Kogen does not rely on: Kogen uses its own instructions on every request path (main, 1 Nov). Remove the `loop.DefaultInstructions` "call finish right away" assertion from TestResearchRemovalDefaults, together with its doc-comment sentence about the default loop instructions and the then-unused `kogen-loop/loop` import. No Kogen test (Go tests and testdata outside the vendored loop, the scenario suite, spec features and Intent steps) may mention `DefaultInstructions`, `call finish right away` or `You are a coding agent`. Kogen's builder prompt states no shell wait duration and stays unchanged. (source: request)
- Specification LOOP-5 (`spec/prose/04-building.md`) currently says every call "waits at most one second". It must state the contract: a new command waits at most one second, retrieval by handle at most 30 seconds, and both return immediately on completion, with no execution timeout. The phrase "and waits at most one second" is removed from that paragraph; the rest of LOOP-5 is kept. (source: request)
- The window-reset scenario's scripted output size is incidental; Kogen does not handle the outcome differently. Reason: LOOP-9, LOOP-10 and REV-2 specify a local reset when the complete next builder or reviewer request exceeds the 524288-byte input ceiling at a completed boundary. Nothing in Kogen's specification makes the size of one response's visible output part of that behavior. The script `build-local-windows` (in `test/acceptance/support/fake-servers.js`) writes 180000 bytes of `write_file` content in each of its first four builder and reviewer responses. That size was only a quick way to grow the conversation. A real model streaming more than 128 KiB of visible output in one attempt is a runaway, and the loop's contract now ends it. The resulting `provider/unavailable` is the honest documented stop, and Kogen must not mask or reclassify it. (source: request)
- Fixture rules for that scenario. Each scripted builder and reviewer response carries at most 131072 visible bytes, counting the complete function-call argument JSON text. The conversation still grows past 524288 bytes, so that the builder window and the independent reviewer window each reset locally. The scripted ChatGPT server keeps streaming function-call arguments as `response.function_call_arguments.delta` events: do not change how it streams or hide output from the loop's count. Scenario "Completed builder and independent reviewer windows reset locally" (spec/features/04-building.feature) keeps its tags and every step and asserted text; only a request number may change, to the request that actually carries the asserted text. Other users of the fake server keep their behavior. (source: request)
