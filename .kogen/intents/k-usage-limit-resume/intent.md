Fix K-USAGE-LIMIT-RESUME. A builder round stopped by an executor account usage or rate limit must stop with an explicit `executor/usage_limit` cause and a checkpoint eligible for the existing `kogen intent resume <build-id> [--project <checkout>]`. Explicit resume continues the interrupted logical round, not a new Build from round 1. Preserve candidate files (including partial changes in the stopped round), completed round history, previous verification results, approval, staging custody and run lineage. Previous results remain historical and tree-bound; no stale pass authorizes a changed candidate. No automatic resume, waiting or retry is added. Other executor failures retain today's behavior.

## Decisions
- Use the existing Resume command only; add no command, flag, option, timeout, retry or limit change. Nothing else about building changes. (source: request)
- Permit a fresh executor conversation when necessary, including Claude Code's `resume: none`. Clearly label that continuity is a fresh conversation, not restored provider history; carry the complete ordinary task authority, preserved work, interrupted round number and previous verification feedback. Do not replay completed rounds or treat stale checks as current. (source: answer 1)
- Identify an actual usage/rate-limit signal, not every `api_error` or every executor error. At the Claude Code stream boundary, support an assistant `error: "rate_limit"` followed by the error result (`subtype: "success", is_error: true, terminal_reason: "api_error"`). Also recognize an explicit quota/usage-limit diagnostic in the terminal error payload; generic `api_error` alone remains `executor/failed`. A nonterminal limit warning that ends in successful completion is not a stop. Authentication, overloaded/server errors, malformed streams, turn limits and ordinary errors keep their existing meaning. Do not infer quota exhaustion from percentage used or the clock. (source: request)

The implementation belongs in the unprotected executor contract/types, Claude Code adapter and Build checkpoint/resume handling. Do not change the pinned loop or its digest, provider transports, configured checks or protected acceptance artifacts. Keep Claude Code's honest `resume: none`: the new exception reconstructs a Build round in a fresh session, not exact provider-session resume. Limit stops must pass the existing baseline/HEAD/process custody checks before being eligible; this change does not permit continuation of uncertain tools, changed approval, unsafe index/HEAD drift or protected blockers. Preserve current authentication selection; switching accounts is an operator action, not a new login/fallback feature. Update README and executor-contract documentation for this narrow exception.

Observe the stopped run before resetting the fixture: nonzero stop, usage-limit cause, no commit, markers intact, round 1 and verification pass 1 retained, checkpoint resumable.
