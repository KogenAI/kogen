### Provider and credentials

The provider identifier is `opencode-go`. `kogen provider login opencode-go` reads one key from stdin (interactive terminal input is not echoed; restore terminal state on success, error and SIGINT/SIGTERM/SIGHUP). Piped stdin is supported without putting a key in argv. Trim the terminating line ending and surrounding whitespace, reject empty or multiline/control-bearing input, and do not impose a guessed vendor key-prefix requirement. On successful local storage print `opencode-go: key saved (not verified)` and exit 0. Login does not perform inference or claim account verification. Empty input exits 4 with `provider/login_failed: no OpenCode Go key supplied; saved login unchanged`. Invalid input, interrupted input or storage failure preserves previous credential bytes; never print input or filesystem exception content containing it.

Store only `{"provider":"opencode-go","api_key":"<stdin value>"}` in `~/.kogen/credentials/opencode-go.json`, atomically replaced under `opencode-go.lock`, 0600 file and 0700 custody directories, consistent with existing providers. Use only this Kogen-owned credential for Go inference. `kogen provider list` is offline, showing `opencode-go: not signed in` when absent, `opencode-go: key saved (not verified)` when locally usable, or the existing saved-login-unusable style of guidance for malformed storage. Do not mistake local presence for included-usage eligibility. Selected roles alone require their logins; unused ChatGPT/SuperGrok must not be required by a Go-only Shape/Refine/Build/Review/resume. Missing Go credentials are `provider/login`, exit 4, naming `kogen provider login opencode-go`, before any inference. Uninstall keeps and names all three credential/lock paths.

### Go transport and exact replay

Send Kogen's own `User-Agent: kogen/<version id>` and a non-secret, generated `x-opencode-session` per conversation. Never impersonate OpenCode, Pi or Codex.

Use non-streaming Chat Completions initially: JSON POST, `stream:false`, `store:false`, `model`, ordered `messages`, ordered function tools with the existing schemas nested under `function`, `tool_choice:"auto"` when tools exist, plus the selected supported effort. No ChatGPT `include`, `input`, cache options or breakpoints, Responses conversation state, `previous_response_id`, truncation, padding, prewarming or new sampling controls. The output/reasoning reserve is a local budget, not a guessed `max_completion_tokens` value to send to Kimi.

Adapt the policy to the first system message; translate text content blocks to Chat Completions text blocks without rewriting their text. Stable policy, tool definitions (names, descriptions, schemas and order), approved contract and original request/Q&A precede changing working material; append new messages without rewriting old ones. Keep the complete original request/source-provenance facilities and documentation tool available on Go as on other routes.

A completed Go response has `choices[0].message` with `role:"assistant"`, nullable text `content`, optional `tool_calls`, and the observed reasoning shape: scalar `reasoning` plus `reasoning_details` entries with `type:"reasoning.text"` and index 0. Do not replace it with the earlier incorrect `reasoning_content` assumption. Use a canonical assistant message's `opencode_go_message` field to retain that raw message, and keep it through `Shape.replay_item`, working windows, source custody and version-3 checkpoints. Normalize text and function calls for the existing tool loops, but on Go rendering emit the raw assistant message exactly once and suppress its duplicate normalized calls/text. Emit one role-tool message for each actual tool output, matched by `tool_call_id`, in order. Never replay one provider's private conversation into another. Missing/incomplete/malformed choices, unusable tool calls, truncation (`finish_reason:"length"`), explicit errors or refusal are failures, not completed work; never execute a partially validated tool batch. This is a new adapter, not a rewrite of ChatGPT/SuperGrok terminal validation.

### Caching and budget across all three providers

Send the body field, not a redundant Chat Completions header. API docs recommend it; subscription acceptance and cache benefit remain unqualified. A synchronous HTTP 400 explicitly naming unsupported `prompt_cache_key` (code `unknown_parameter` or `unsupported_parameter`, param exactly `prompt_cache_key`) permits one retry removing only that field within the same deadline. Remember that refusal within the owner conversation and its checkpoint; do not retry it on later requests/resume. Other 400s, 402s, 403s, failed streams and unknown rejection shapes are not permission to change requests. Retain failure/unknown-usage evidence of the rejected attempt.
