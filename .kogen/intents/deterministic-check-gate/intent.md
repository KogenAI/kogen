# Stabilize the native Mix test gate

Repair Kogen's own test orchestration, not the Build algorithm. Keep the configured `test` command `if test -f mix.exs; then mix test; fi` and all existing behavioral coverage. Ordinary failed verification continues through the existing builder/reviewer repair path; genuine environment, protected-contract, authentication, resource and unresolved-review stops remain honest stops. Do not retry a failed check until it happens to pass.

The concrete local defect is test-resource custody: `Helpers.project!` starts a linked registry and `Helpers.start_kogen` opens a Port owned by the test process. ExUnit shuts that process down before `on_exit`. A focused probe observed the registry dead, Port absent, and OS child still alive in `on_exit`. Current `cleanup_case` can consequently lose every live child and delete a workspace while processes still use it. The two reported modules passed in isolation here: 28 tests in 197.8 seconds, including release preparation. That is not a reproduction or explanation of every historical host failure.

## Decisions
- Preserve every safety guarantee, use real processes/files/Git/releases, and neither cancel unrelated workloads nor require a quiet host. Do not edit `.kogen/project.yaml` or the 524288-byte/131072-token guards. Staged Intents, Go migration, Studio, release delivery and deployment are outside this change. Test-only preparation of the existing installed-release fixture remains necessary. (source: request)
- Fix this in one Intent and at its test-harness cause, without automatic retries, a scheduler, polling long Builds, or disabling legitimate Build stops. The historical 30-minute operator observation request does not authorize a new monitoring product. Existing read-only `context`/`intent inspect` remain the observation path. (source: request)

### Settled technical contract

1. Keep test-owned process custody usable after normal ExUnit test shutdown and abrupt test-owner death. `Helpers.cleanup_case(context)` must stop the CLI and its owned core/project-command descendants and wait for their termination **before** removing the case workspace. This includes a Build blocked in a real shell command. A closed Port or dead registry is not evidence that its OS process exited. Cleanup must not silently swallow a failure to stop owned processes or remove the workspace. Already-completed invocations remain harmless to clean up. Kill only processes established as belonging to this fixture, never a broad host process-name match. Apply the same lifetime rule to failed project preparation and suite cleanup where they own live resources. Use existing CLI graceful cancellation/EOF behavior before bounded, fixture-scoped escalation; do not change production signal semantics merely to accommodate the harness.
2. Bound the installed-release integration workload within one `mix test` invocation to one integration module at a time, including its setup/teardown. Use ExUnit's supported grouping (`group: :installed_release` on the async installed-release modules); existing synchronous modules stay synchronous. Cheap independent tests can remain concurrent. Cover all modules that use `Helpers.setup_suite!`, not just the two named in the report. Keep the existing once-per-invocation fresh source archive and separate per-module installation prefixes: tests deliberately modify their installed core. Do not use a stale archive, a successful retry, exclusions, reduced assertions or a change to configured checks as the fix. Existing explicit `KOGEN_ARCHIVE` test-suite input remains supported.
3. Give installed-release integration test/setup orchestration a finite 300000 ms ExUnit timeout and marker waits a finite 60000 ms default, instead of the current 60000 ms test and 10000 ms marker deadlines. Preserve explicitly short deadlines that test actual product timeout behavior. Marker success still requires the actual file/event, not elapsed sleep. Keep explicit timeout overrides usable; a genuinely absent marker fails with its path. Align affected test orchestration waits with this bounded headroom, without increasing production deadlines, disabling timeouts, or changing response-budget tests. In the postcommit-interrupt regression replace the 200 ms scheduling assumption with a real acknowledgment/barrier at the existing wrapper/process boundary, so the query is released only after cancellation reaches that boundary. Preserve rollback/index/approval assertions.
4. Release-fixture packaging is still a real fresh build once per suite invocation. Propagate a nonzero packaging/compiler/process result and its diagnostics; do not reinterpret exit 196, real resource exhaustion, or startup failure as success. Removing self-inflicted concurrency and stale owned processes is the scoped repair, not a promise that arbitrary host starvation cannot fail. Do not edit release/deployment behavior. Record supported-platform qualification honestly: a local pass does not certify both macOS and Linux.

Builder-owned implementation work belongs in `test/support/integration_helpers.ex`, installed-release integration modules and narrowly related test support/documentation. No protected implementation edit is required. The acceptance driver is an independent measurement harness, not an implementation file. New focused harness regressions may live outside the two historical regression modules so acceptance does not impose a fixed overall test count.
