**Cause 1: kogen-verification 25884c52dde4 checks the install.** `verify.ToolsFromInstall(root)` no longer returns the `node-path` file's own path as the Node when that file cannot be read. It returns an empty `Node` and records why (`node-path is missing`, `node-path is unreadable` or `node-path is empty`). The new `Tools.RequireInstall(model bool)` runs at the start of readiness (shaping, refine, approve and Build readiness, before the acceptance command): it refuses with `environment/tool_missing` (exit 3) unless `node-path` is readable and names a Node that is an existing, regular, executable file (the details read `node-path is missing at node-path <root>/node-path; reinstall Kogen` or `node target is missing at node-path <root>/node-path (target <path>); reinstall Kogen`, and for a non-regular or non-executable target `node target is not regular` or `node target is not executable`), unless `<Cucumber>/@cucumber/cucumber` is a directory (`cucumber is not available at <dir>; reinstall Kogen`) and, only when the Intent has a model, unless the Quint `cli.js` is a regular file. kogen's fixtures write installs and `verify.Tools` values with no `node-path`, no Node or no Cucumber package, so every approve, refine and preflight call of those tests and every `kogen intent approve` through a built binary exits 3 before it reaches the behavior the test is about.

**Cause 2: kogen-executor 5e9ca167fa44 pins Claude Code 2.1.318** (`claudecode.Version`, and with it `claudecode.RuntimePath`, the `~/.kogen/claude-code/2.1.318/claude` runtime and the `provider list` line `claude-code runtime: Claude Code 2.1.318 ...`). Fakes and expectations that still say 2.1.312 are refused as `executor/unavailable: Kogen's Claude Code at <path> reports 2.1.312 (Claude Code), not the pinned 2.1.318; remove <dir> to reinstall it`.

**Fix 1: fixtures and consumer tests follow the install check.**
1. These are `buildApproveCLI` in cli/approve_deadline_test.go and `buildKogen` in cli/buildprogram/k_reviewretry_cli_test.go (the install root is the folder holding `bin/kogen`, `<prefix>/lib/kogen`), and `newFx` in cli/consumes/kogen-shaping/helper_test.go (`f.tools.Node` is an existing executable file and `f.tools.Cucumber` holds `@cucumber/cucumber`). Any other fixture the failing tests use gets the same layout. The tests' assertions, exit codes and timeouts are unchanged; `kogen-setup` and `kogen-build` consumer fixtures already pass and stay.
2. `TestToolsFromInstallWithoutNodePathFile` in cli/consumes/kogen-verification/tools_test.go states the new contract: with no readable `node-path`, `ToolsFromInstall(root).Node` is empty (no other node runs). Its line in cli/consumes/kogen-verification/README.md says so; the old statement that `Node` is the file's own path is removed. The consumes suites reference only identifiers that kogen's non-test code uses, so `RequireInstall` is not referenced there.
3. The kogen-shaping consumer suite pins the refusal kogen relies on: `Approve` with `Tools` whose Node target does not exist returns a `*sys.Error` whose rendering starts with `environment/tool_missing: ` and whose Exit is 3, and writes no approval. It is a new subtest of `TestApproveRefusalsAreSysErrorsWithTheirExit` in cli/consumes/kogen-shaping/approve_test.go; cli/consumes/kogen-shaping/README.md lists it (text `environment/tool_missing`) and says the fixtures now carry a Node stand-in and a Cucumber package folder.
4. spec/prose/04-building.md LOOP-12 states the check: before any model request, shaping, refine, approve and Build readiness require that `<prefix>/lib/kogen/node-path` is readable and names a regular executable file, and that the bundled Cucumber package exists, whatever the Intent's model; Quint is required as before when the Intent has a model.
