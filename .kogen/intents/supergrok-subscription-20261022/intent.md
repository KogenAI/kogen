- Use Kogen's own RFC 8628 device-code flow on xAI's shared OAuth client with honest identity `referrer=kogen` and `User-Agent: kogen/<version id>`; never another harness's referrer, `X-XAI-Token-Auth`, credentials, cookies or `XAI_API_KEY`. A rejected device request stops without retrying another identity. Separate registration is not required by any evidence found. (source: request)

### Login, storage and status

`kogen provider login supergrok` posts `https://auth.x.ai/oauth2/device/code` form fields exactly `client_id=b1a00492-073a-47ea-816f-4c329264a828`, `scope=openid profile email offline_access grok-cli:access api:access`, `referrer=kogen`, with `accept: application/json` and `user-agent: kogen/<id>`, where `<id>` is the second token of `Kogen.version()` (`007087b9` or `dev+<hash8>`). A non-200 device answer prints `provider/login_failed: the SuperGrok device authorization request failed (<status>[ <error>])` after exactly one request. Required `device_code`, `user_code`, `verification_uri` and positive integer `expires_in`; otherwise `provider/login_failed: the SuperGrok device authorization response is incomplete`. `verification_uri` and any `verification_uri_complete` must be absolute `https:` URIs with a host, else `provider/login_failed: the SuperGrok verification address is not HTTPS` before any token poll. Stdout then has exactly `Continue with SuperGrok`, the complete address when present (else `verification_uri`) and `Code: <user_code>`. No listener or browser is started; the device code is never printed.

Poll `https://auth.x.ai/oauth2/token` with form fields exactly `grant_type=urn:ietf:params:oauth:grant-type:device_code`, `device_code`, `client_id`, waiting at least the current interval before the first and each later poll. `authorization_pending` continues; `slow_down` permanently adds 5 s; `access_denied` or `authorization_denied` print `provider/login_failed: the SuperGrok sign-in was denied`; `expired_token`, or reaching `expires_in` measured from the device answer (no poll starts at or after it), print `provider/login_failed: the SuperGrok sign-in code expired`; other answers print `provider/login_failed: the SuperGrok token request failed (<status>[ <error>])`. Bridge cancellation stops waiting/HTTP promptly with the existing signal exits and no later poll. Login failures exit 4, except cancellation uses the existing signal exit, and keep any earlier credentials byte-identical.

A grant needs nonempty `access_token` and `refresh_token` (else `provider/login_failed: the SuperGrok sign-in returned no usable tokens`). The granted `scope` must contain `api:access`; an absent `scope` means the requested scope (RFC 6749 §5.1). Missing access prints `provider/login_failed: SuperGrok API access was not granted; sign in again and allow it` and stores nothing. Success writes `~/.kogen/credentials/supergrok.json` atomically under exclusive lock `~/.kogen/credentials/supergrok.lock` (same O_EXCL/pid/stale rules as GPT-3) with mode 0600 inside 0700 `~/.kogen/credentials` and 0700 `~/.kogen`, even under umask 022. It holds exactly `client_id`, `referrer` (`kogen`), `access_token`, `refresh_token`, `expires_at` (now + `expires_in`, else 3600), `scope` and, when the id_token payload yields a string, `email`; never device/user code or id_token. Then print `supergrok signed in[ (<email>)]` (exit 0).

`kogen provider list` prints the unchanged ChatGPT line, then `supergrok: not signed in`, `supergrok: signed in[ (<email>)]`, or `supergrok: saved login cannot be used; run kogen provider login supergrok`. Usable means nonempty string client_id/access_token/refresh_token, integer expires_at and referrer exactly `kogen`. It sends no request. Shape (shape role plus enabled workers), Refine (shape) and Build/resume (build, review) check only providers their roles use, before any request: `provider/login: not signed in; run kogen provider login supergrok` or `provider/login: saved login cannot be used; run kogen provider login supergrok` (exit 4). Legacy configurations keep today's ChatGPT check exactly; `kogen init` stays ChatGPT.

### Requests, refresh and errors

A SuperGrok role posts `https://api.x.ai/v1/responses` with application headers exactly `authorization: Bearer <access>`, `accept: text/event-stream`, `content-type: application/json` and `user-agent: kogen/<id>`; ordinary HTTP framing headers remain transport-generated. No conversation, harness, cookie or API-key header and no `previous_response_id`. The body is `Kogen.ChatGPT.request_body/4` for that role: model, `reasoning.effort`, `include: ["reasoning.encrypted_content"]`, complete `input`, `stream: true`, `store: false`, plain `instructions`, and `tools`/`tool_choice: "auto"` when tools exist. The prompt-cache gate becomes explicitly provider-scoped: SuperGrok never sends `prompt_cache_options`, `prompt_cache_breakpoint` or a developer policy message and records cache status `unknown` with no boundaries; ChatGPT routing and its cache-refusal compatibility retry are unchanged and ChatGPT-only. Full ordered replay keeps encrypted reasoning, assistant phase, complete tool pairs and frozen typed `view_image` outputs unchanged; reasoning stays private replay data. Stream validation, terminal evidence, the 1,800,000 ms logical budget, the 524288-byte inclusive complete-request ceiling with 131072-token reserve (`Kogen.WorkingContext.measure/1` of the actual body, including typed image envelopes), image guards, working windows, version-3 checkpoints, independent reviewer conversations and pinned initial-review source delivery stay identical. Typed images are sent as typed content; xAI acceptance on the account is not yet observed, so a provider rejection is an honest failure, not a substitution. Local image/replay checks prove plumbing only, not pixel interpretation or designer approval; when native image input is refused, retain the existing external preparation/pixel-review handoff.

Refresh proactively when `expires_at - 60 <= now` and once after a 401, under the lock with re-read, posting `https://auth.x.ai/oauth2/token` form fields exactly `grant_type=refresh_token`, `refresh_token`, `client_id`. Save a rotated refresh token or keep the old one when omitted; `expires_at` from `expires_in`, else 3600. `invalid_grant`, or any failure after a 401, prints `provider/login: the SuperGrok sign-in was rejected; run kogen provider login supergrok`; other proactive failures print `provider/login: the SuperGrok sign-in expired and could not be refreshed; run kogen provider login supergrok`. A second 401 after the retry is rejected the same way.

SuperGrok errors are labelled SuperGrok and exit 4: 402 `provider/refused: SuperGrok reported a billing or credit limit (402[ <detail>]); Kogen uses only the subscription sign-in and never falls back to paid API usage`; 403 `provider/refused: SuperGrok denied API access for this sign-in (403[ <detail>]); Kogen never falls back to an API key or another provider`; 429, 5xx, network errors and cut streams follow the existing 3-attempt 2 s/8 s policy as `provider/unavailable: SuperGrok did not answer after 3 attempts: <detail>`; `model_not_found` gives `provider/model_unavailable: grok-4.7 is not available to this SuperGrok account`; `context_length_exceeded` keeps context handling; other 4xx `provider/refused: SuperGrok refused the request: <status> <detail>`; unreadable output `provider/invalid_response: SuperGrok sent a response Kogen cannot read: <detail>`; budget expiry `provider/unavailable: SuperGrok response wait exceeded 30 minutes`. Existing `provider_failure` diagnostics stay allowlisted. No pool-exhaustion code is invented. ChatGPT `subscription_sharing_*` handling stays ChatGPT-only.
