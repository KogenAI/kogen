This is a fix (repo kogen, request K-REPIN-ADAPT-F2E30A4). Make Kogen's configured checks pass on top of the already-landed delivery commit "Re-pin kogen-loop to f2e30a4" (L-BOUNDED-SHELL-WAIT, issue 3943154d), which was made with packaging/sync-kogen-loop.sh. Kogen must behave as the pinned caller contract `cli/third_party/kogen-loop/docs/contract/loop-v1.md` now describes. Do not edit `cli/third_party/kogen-loop/` or `cli/loop-pin.json`, which are protected from Builds. Add no option, timeout or limit. Keep every configured check, its settings and all useful unrelated assertions.

The pin changes one thing Kogen sees: a new shell command now waits up to 45 seconds (was one second) and returns its exit status and output in the same response when it completes; only a command that outlasts the bound yields a running handle. Retrieval by handle still waits up to 30 seconds. Both return immediately on completion, without an execution timeout.

What changes: the two silent-shell Go tests and the "Default shell calls remain unbounded" building scenario used a 2-second command only to obtain a running handle. They now use a command that genuinely outlasts the 45-second wait, so each still proves what it proved. Specification LOOP-5 states the 45-second wait. Test comments that describe a one-second wait are corrected. Nothing else is removed.

Acceptance runs that one building scenario end to end through the installed `kogen intent build`, plus quick text checks of the silent-shell test source, LOOP-5 and the stale comments. It does not run the full suite or any Go test by name. The configured `go-test` check runs the two silent-shell Go tests. It took 65 s measured, within approval's 120-second per-step limit. The complete configured checks remain the final gate on the Build's tree.

## Decisions
- Authority is the pinned loop-v1.md "Shell time limit": a call supplies exactly one `command` or `handle`. A new command waits at most 45 seconds and retrieval at most 30 seconds. Both return immediately on completion, without an execution timeout. A fast command returns `exit status: <n>\n<combined output>`. A running command returns JSON with `status: "running"`, an opaque `handle` and cumulative `output`. Retrieval returns that shape, or `status: "completed"` with the same handle, an integer `exit_status` and cumulative output. Kogen adds no handling, retry, option, timeout or limit around it. (source: request)
- Route chosen for every affected test: a command that genuinely outlasts the new bound, never a switch to asserting the completed result. Reason for the Go tests: TestSilentBuildShellNotStopped and TestSilentReviewShellNotStopped each prove two things, in Build and in independent Review. A silent shell is not stopped (no `command_no_progress` event, the run lands one commit). And the yielded handle is retrieved to completion (at least 3 requests, `exit_status` 0, output `done\n`). An inline completed result would drop the retrieval half in both owners. Reason for the scenario: "Default shell calls remain unbounded" (@LOOP-5 @LOOP-11) proves that a shell call has no time limit. A 2-second command that completes inline cannot tell an unbounded shell from one with any timeout above 2 seconds. Only a command still running past the wait, not killed, and completed through its handle proves it. (source: request)
- The outlasting command is `sleep 47`: 2 seconds beyond the 45-second bound. The loop starts its wait timer after it starts the command, so `sleep 47` cannot complete within the wait. Retrieval then completes it after about 2 more seconds, within the 30-second retrieval wait. The value keeps acceptance near 65 s and the two parallel Go tests near 50 s each. (source: request)
- `cli/build/silent_shell_test.go`: `silentCommand` becomes exactly `"sleep 47; printf 'done\\n'"` (Go source text, so the shell prints `done` and a newline). Every assertion of both tests stays: the `running`/`completed` handling in `continueSilent`, the handle retrieval call `map[string]any{"handle": handle}`, exit 0 and output `done\n`, one commit, the request-count checks ("the handle was not retrieved", "review requests: the handle was not retrieved"), and no `"command_no_progress"` events. Its leading comment no longer says the shell yields after a one-second wait; it states the 45-second wait that the command outlasts. (source: request)
- `spec/features/04-building.feature`, scenario "Default shell calls remain unbounded": keep its tags `@LOOP-5 @LOOP-11`, its name and every step. Only the command changes from `sleep 2` to `sleep 47`, in both the script step (`with command "sleep 47"`) and the assertion (`Then the tool result for "shell sleep 47" contains "running"`). The `shell continuation` lookup in `test/acceptance/support/handlers.js` (`findServerToolResult`) finds the initial call by command. It must look for `sleep 47`, keeping its checks that the handle exists and was retrieved to `completed` with `exit_status` 0. The `build-runs-command` script in `test/acceptance/support/fake-servers.js` keeps its behavior; only its comment about the "one-second wait" says 45 seconds. (source: request)
- Specification LOOP-5 (`spec/prose/04-building.md`) currently says "A new command is given at most one second" and "A command that exits within that first second". It must state the pinned contract: a new command at most 45 seconds, retrieval by handle at most 30 seconds, both return immediately on completion with no execution timeout. The words "one second" and "first second" leave that paragraph; the rest of LOOP-5 is kept. (source: request)
- Comments in Kogen's tests that describe the old wait are corrected, with no behavior change. These are `cli/build/silent_shell_test.go` ("one-second wait"), `cli/build/executor_native_test.go` (the conformance driver's "The shell yields after one second") and `test/acceptance/support/fake-servers.js` ("one-second wait"). The conformance cancellation and deadline scripts (`interrupt_kills_children`: `sleep 30` cancelled after 4 s; `deadline`: 1 s) are now interrupted inside the first wait. They still prove that interruption stops a running command, and their code stays unchanged. (source: request)
- Tests that pin exact loop bytes or tool text only to detect loop changes get the new pinned values. Inspection found none that needs it at this pin. `TestDefinitionsMatchTheElixirDefinitions` compares the loop-owned shell definition with `tools.Definition`. `TestResearchRemovalDefaults` normalizes the shell definition before comparing goldens. The delivery land-tree run reported no other failure. If the configured checks show such a test on the Build's tree, update only its pinned loop values. (source: request)
- Historical evidence such as `docs/evidence/loop-repin-af456d5/README.md` keeps its wording about the old one-second wait. It is a record of that pin, not a current claim. (source: request)
