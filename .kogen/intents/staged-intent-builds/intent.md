# Build one approved Intent in verified stages

Slug: staged-intent-builds

Let native Shape choose and publish an optional sequential stage plan before approval. Native Build consumes that plan under the one existing approval, verifies each stage, preserves completed progress across supported explicit same-checkout Resume, and finally runs the normal whole-Intent verification and fresh independent review before one commit. A stage is a verified implementation milestone, not a delivered Intent, a new approval, a commit, a separate critic, or permission to weaken checks. This capability itself bootstraps through an ordinary Build; this package does not require its as-yet-unimplemented stage format to execute.

## Decisions
- Shape decides whether scoped milestones materially improve feedback for a large cohesive change; it does not ask the human engineering questions, automatically split the request, or impose a fixed migration outline. Publish the chosen plan with the full contract before exact approval. (source: request)
- Keep one approval and one final implementation commit; intermediate success is progress only. Whole-Intent verification and independent review remain mandatory. (source: request)
- Keep normal packages without a stage plan unchanged, including their fail-fast verification behavior. No new CLI flags, scheduler, parallel lanes, automatic resume, provider or model selection are introduced. (source: request)
- Preserve the Go candidate and its external authorship as diagnostic reference only. Do not perform the migration, apply a stash, transfer approval, or resume across paths here. Studio and the separate approval-card-recovery and Claude API lanes are untouched. (source: request)

## Contract

### Plan and exact approval

Use an optional `## Stages` section in `intent.md`, containing exactly one fenced `json` object, with this format (the executable fixture supplies concrete commands):

```json
{"version":1,"stages":[{"id":"foundation","title":"Foundation","goal":"Establish the first runnable section","checks":["<scoped shell command>"]},{"id":"surface","title":"Surface","goal":"Integrate the second section","checks":["<scoped shell command>"]}]}
```

The plan has exactly `version` and `stages`; version is integer 1. `stages` is an ordered array of at least two entries. Each entry has exactly `id`, `title`, `goal`, `checks`: unique slug-form id (`^[a-z0-9]+(-[a-z0-9]+)*$`), nonblank title and goal, and a nonempty ordered array of nonblank shell command strings. Invalid JSON, duplicate sections, unsupported version, missing/extra fields, invalid/duplicate ids, too few stages, or blank/mistyped fields are Intent lint problems naming stages, not ignored metadata. No section means the existing single-stage route. Do not infer stages from arbitrary prose/headings or from a word-count threshold.

Extend native Intent parsing/lint, Shape's format/guidance, approval-card rendering and specification accordingly. Shape should choose stages only when each has a coherent outcome and a real scoped executable gate that can pass before whole delivery. It must inspect dependencies, preserve the complete requested outcome in final acceptance, and explain the division and what each stage proves. A plan cannot replace final acceptance/model/checks or hide a missing prerequisite. Guidance must explain `## Stages`, the schema, scoped-versus-final proof, and the absence default. Include plan title, goal and every ordered command on the approval card, in order, under a clearly labelled staged plan. Existing baseline hashing already protects the whole `intent.md`; use that exact identity, not a second approval or hash waiver. Stage gate helper files should be declared under `Acceptance:` (or already protected by project configuration), so Build cannot implement success by editing a gate.

Native Refine may change an existing plan in owned `intent.md` through its normal original-full-hash, investigation and fresh readiness path. Successful correction revokes the old approval. No builder-authored substantive plan change, automatic replanning, old approval transfer or replay of old checks is supported. Existing new-file/shared-step/model/acceptance-path restrictions on Refine remain. Changing the plan after approval refuses Build/Resume through existing exact-authority guards.

### Stage execution

After unchanged startup safety/setup/preexisting configured-check checks, start the existing builder with complete approved authority and an explicit active stage (1-based index, total, id, title, goal, gate commands). Keep complete whole-Intent authority in every request; the active stage is additional navigation, not clipping. Keep the same builder owner across stage boundaries, ordered replay and tool/result pairs, opaque reasoning and assistant phases. Use existing bounded working-window machinery when necessary; stage advancement is not an excuse to silently discard history or increase the ceiling. No separate planning/provider request is needed.

While a stage is active, `finish` (and the existing no-tool-response verification boundary) runs normal fixers, then a native stage verification pass instead of prematurely running whole-Intent acceptance. Materialize the exact current Snapshot candidate into fresh disposable scratch, run verbatim configured setup and that stage's ordered commands through the ordinary command boundary. Stop at the first red; name the actual failure/output and remaining not-run commands. Enforce existing source/scratch mutation checks, protected baseline, HEAD/index and interruption rules. An interrupted or incomplete stage gate is not completed evidence; Resume reruns it from fresh setup. Ordinary red returns to the same builder at the same stage; it is not a protected blocker or a request for human engineering intervention. Repair continues until green or one of the existing honest stops occurs; there is no new automatic retry limit or background polling.

A green stage requires all setup and scoped commands to finish successfully on a stable clean candidate. Save its exact candidate tree, full approved contract identity, stage id/index, ordered command outcomes and clean/green result durably before advancing. Emit `stage_pass` log events with `stage_id`, `stage_index`, `tree`, `green`, `failing`, `not_run`, and retain actual command evidence using existing private run/checkpoint custody. Emit clear progress naming active stage and whether its gate passed/failed. Advance only to the next declared stage, once; return explicit successful-stage/next-stage feedback to the same builder. Do not run final acceptance/model or independent review between stages, create interim commits, consume approval, or report landed success.

After the last green stage, immediately enter finalization and run the existing complete fresh-scratch gate: configured setup, all whole-Intent acceptance scenarios exactly once, declared model, and every configured check in normal order with honest fail-fast not-run accounting. These are not replaced by stage results. Final red goes to the same builder in finalization, not back to stage one; subsequent finish runs the complete final gate. Earlier stage evidence is historical for its recorded tree, never asserted green for a later edited tree. Final acceptance must detect regressions in earlier sections. A whole green candidate goes to one fresh independent whole-Intent reviewer with complete approved authority and current whole verification; stage evidence is labelled historical diagnostic evidence. Reviewer repairs run the normal complete external verification and stay with that reviewer on red. Only an exact current wholly verified and reviewed candidate can produce the single ordinary commit, run hooks/signing and consume approval.

### Durable progress, stops and compatibility

For staged Builds, add a `stage_progress` object to retained `result.json` (and preserve it in the checkpoint and read-only native inspect output): `{"total":2,"completed":["foundation"],"active":"surface","phase":"stage"}` is the exact example after stage one. `completed` contains only completed ids in plan order. `active` is the current id during stage work and null after all stages; `phase` is `stage`, `final`, `review` or `landed`, reflecting actual progress, never using `landed` for a partial candidate. Do not add invented completed progress to old unstaged records. Keep this navigation and its contract/tree-bound evidence in working-window resets and resumed conversations without misrepresenting old evidence as current final proof.

Resume remains explicit, same physical checkout and native lineage, with exact approval/configuration/baseline/candidate/index/HEAD and bound working-context/image/source custody validation before inference or effects. Resume after a completed stage continues the saved current stage/final/reviewer owner and conversation, without replaying completed tool effects or rerunning already completed stage gates merely because the provider stopped. Prior stage trees are honest historical milestones, not a claim that the current tree was checked by those gates. Candidate or plan drift and another checkout are refusals without changing files/index/HEAD/approval or calling a model. Preserve old result bytes, original index and failed/unknown usage; known counters remain cumulative. Existing protected-blocker recovery is still required for `candidate/build_blocked`, not a way to bypass plan authority. Keep current version-3 unstaged checkpoints supported; if stage state is present, validate it against its exact approved plan and evidence. Malformed/inconsistent stage state is refused, not silently treated as unstaged or completed. Version 2 and older remain unsupported. No cross-path conversion, approval/check replay or automatic import is added.

Update README and relevant maintained prose/Gherkin/Quint specifications and useful implementation tests. Keep the delivered Build/Review windows, Shape windows `44c2e06d`, constant navigation `65640c64`, Review/Refine working room `0e43500b`, protected blocker recovery `a6a1083f`, bounded transient retry `2137fa9b`, deterministic Mix gate `48bc5efc`, and bounded text tool results `71dd6da1`.
