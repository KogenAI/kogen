# Speed up the kogen/build and kogen/shape tests

Slug: k-go-test-critical-path
Model: not applicable — test scheduling, a test-only sync switch and reuse of one resolved fact; no product state or lifecycle changes
Acceptance:
- .kogen/intents/k-go-test-critical-path/acceptance.feature
- features/steps/k_go_test_critical_path_steps.js

Kogen's go-test check (`cd cli && go test ./...`, no `-race`; Kogen's own host runs it as `(cd cli && GOFLAGS=-trimpath go test ./...)`) runs each package's tests in one test binary under Go's default 10-minute timeout, so it takes as long as its slowest package. Make kogen/build and kogen/shape run the same tests, with the same assertions and coverage, well inside that timeout on a 4-CPU host, so that neither package holds the check near the timeout. Nothing raises a timeout, and nothing adds a command, flag, option, setting or environment knob.

Measured on the shaping host (Mac Studio, 10 CPUs, Go 1.27.2, load averages 15 to 28), running uncached with `GOMAXPROCS=4` (the go command then runs four test binaries at once and each binary four parallel tests: a 4-CPU host's scheduling): kogen/build took 569 to 581 s and kogen/shape 421 to 432 s. With the default GOMAXPROCS under load about 45, kogen/build hit the timeout (605.9 s). The causes, in order of size:

1. Serial tests. Go runs every top-level test that does not call `t.Parallel()` one at a time before any parallel test starts. kogen/build ran 245 s and kogen/shape 275 to 302 s of tests serially, using one of the four slots.
2. Disk flushes. Kogen's private records are flushed with `os.File.Sync`, which on macOS is `F_FULLFSYNC`. One heavy build test took 8.2 s with syncs and 1.9 s without them.
3. Git processes. A typical full-Build test starts about 163 git processes. 41 of them are the `git rev-parse --absolute-git-dir` that `project.Checkout` runs on every Build facts update.

## The change

1. **Parallel scheduling.** In `cli/build` and `cli/shape`, every top-level test and every subtest calls `t.Parallel()` unless it changes process-wide state: the environment (`t.Setenv`, `os.Setenv`, including shape's `serialTmp` TMPDIR), the working directory or package-level variables. In kogen/shape a fixture helper may make the call, as `newShpFx` does now; a test never calls `t.Parallel()` twice (register in `parallelTests` or equivalent). These tests stay serial:
   - the kogen/shape tests that use `serialTmp`. Their leftover checks look in the process TMPDIR, and Kogen's temporary paths come from the protected `sys.TmpPath`, which reads the process TMPDIR.
   - `TestKRevodGatePartsUnchanged`, which uses `t.Setenv`. It may become parallel only by passing `KOGEN_REVOD_GATE_ACCEPT` through its fixture's own environment, with its assertions and golden unchanged.
   Measured with this rule applied: build's serial phase 19 s and shape's 87 to 94 s (the `serialTmp` tests). Currently serial tests include `TestBuildRequestBudget*`, `TestKRevodB*`, `TestKReviewRetry*`, `TestChangesWhilePartsAreUnread…`, `TestShapeBudgetRolesBuild`, `TestLoopKnobs*` in build, and `TestApprove*`, `TestK18b*` and many Refine/Shape tests in shape.
2. **A test-only sync switch.** Add package `cli/durable` (import path `kogen/durable`, standard library only). It has exactly this interface:
   - `func Sync(f *os.File) error` returns `f.Sync()`, and returns nil without calling it once syncing is switched off.
   - `func SkipSyncInTests()` switches syncing off for the rest of the process. The switch is process-wide and safe for concurrent use.
   Every fsync in Kogen's own code goes through `durable.Sync`, with the same error handling: `shape/window.go` `writePrivate`, `project/provenance.go` `privateWrite`, `build/run.go` `PublishCheckpoint`, `build/material.go` `materialWritePart`, `build/stages.go` `retainStage`, `build/context.go` `prepareContext`, and `build/recover.go` `writeNew` and `syncDir` (a directory). `TestMain` in `cli/build/main_test.go` and `cli/shape/main_test.go` calls `durable.SkipSyncInTests()` before `m.Run()`. No non-test code calls it, so the `kogen` program always syncs. kogen-loop's own syncs are protected and unchanged; Kogen calls `loop.Run` without session persistence, so build and shape tests do not reach them.
3. **One resolved checkout per run.** `startFacts` already resolves `project.Checkout(root)`. `localFacts` keeps that result and `update` publishes with it instead of resolving it again, so the published facts are the same. Facts would differ only if the checkout's physical root or Git directory changed during the run, which a Build under its lock does not support. Measured: 163 to 127 git processes in a typical full-Build test.

Unchanged: test names, bodies, fixtures, data sizes, rounds, golden files, assertions and the `//go:build !race` constraint. The only test-file edits allowed are the scheduling calls, the `TestMain` switch call, and moving a process-wide variable into one fixture's environment with the same value. No test is removed, renamed, skipped, constrained or weakened. No `-timeout`, `-parallel`, `-p`, `GOMAXPROCS` or `GOFLAGS` is set in any test or configuration. `.kogen/project.yaml`, the configured checks and `cli/third_party/kogen-loop/**` stay unchanged. Kogen's behavior is unchanged apart from items 2 and 3. Snapshot frequency, checkpoint content and durability in the program do not change. Host safety: stop only processes you started, never by name or pattern; use no synthetic CPU load.

Run `(cd cli && go test -race -count=1 ./build ./shape)` once before finishing, to catch data races between tests that now run concurrently. A race found there is a defect in the scheduling change.

The acceptance measures the outcome with `GOFLAGS=-trimpath GOMAXPROCS=4 go test -count=1 -json ./...` in `cli`. kogen/build may run serial tests for at most 30 s (only the Setenv test remains serial) and kogen/shape for at most 120 s. That bound stops a run of the unchanged tree within about half a minute, inside approval's 120-second step bound. Every package must pass. kogen/build and kogen/shape must each finish within 400 s, two thirds of the timeout, against 569 to 581 s before. With items 1 to 3 applied in a shaping scratch copy, kogen/build took 326 s and kogen/shape 338 s, at load 19 to 22. The tests and subtests must keep their exact identities and skips: 884 and 479 passed, and kogen/build's two `TestNamedFeedback*` tests skip under `-trimpath` because `runtime.Caller` paths are module-relative, which is today's behavior. Load on the host moves these times. This is a one-host observation, not a statistical guarantee.

## Decisions
- No raised timeouts; no new command, flag or option. (source: request)
- The same tests with the same coverage; no test removed or weakened. (source: request)
- Kogen's go-test check (`cd cli && go test ./...`, no `-race`) stays as configured; measure on a 4-CPU host. (source: request)

## Source comparison
- Addressed: "finish well inside the existing per-package timeout on a 4-CPU host". Scenario 3 bounds kogen/build and kogen/shape at 400 s each (600 s timeout), with 4-CPU scheduling emulated by GOMAXPROCS=4. Shaping measured 569–581 s / 421–432 s before, and 326 s / 338 s after the remedy in scratch.
- Addressed: "no longer dominated by one package". The check lasts as long as its slowest package. Both previously dominant packages are bounded, and their serial phases (30 s / 120 s) removed most of the single-slot time that made kogen/build the critical path (26 of 28 in the request).
- Addressed: "same tests, same coverage; no tests removed or weakened". Scenario 1: `go test -list` counts and name hashes (253 / 265), t.Skip counts (5 / 1), the only build constraint `//go:build !race`, no timeout/parallelism/GOMAXPROCS/GOFLAGS setters. Scenario 3: 884 / 479 passed test and subtest names with exact skips. Prose: bodies, fixtures, sizes and assertions unchanged.
- Addressed: "No timeout raise; no new command, flag or option". Scenario 1's setter scan, prose, and an unchanged project.yaml (protected baseline). The sync switch is a Go function only test binaries call (scenario 2 source scan), not an option.
- Addressed with evidence: the request's timeout tests (TestOneInvalidVerdictIsSentBackAndASecondEndsTheBuild, TestClaudeLineupReviewExactTree, TestClaudeLineupReviewMaterialDelivery, TestAConversationOverTheBudgetIsResetToALocalWorkingWindow) are parallel parents that wait for queued subtests. Their duration follows total package work, which items 1 to 3 cut. Their names are in the inventories.
- Omitted, owned elsewhere: real-time waits (K-CHECKTIME-CLOCK), landing race pass (K-CHECKTIME-SHARD), round-targeted tests (K-ROUND-TARGETED-TESTS). This Intent changes no sleeps or waits. The research files under ~/Scratch.noindex are not readable here; the request's figures are kept as supplied.
- Omitted as evidence only: the 28-invocation profile, cache hit rate (2 of 54), laptop/MacBook/Studio timeout histories and the 330 s / 510 s upper bounds. These are not acceptance thresholds; the cache is not changed.
- Considered and rejected: raising `-parallel`/`-timeout`, sharding by `-run`, and re-executing test binaries (new options or weakened timeout semantics). Also rejected: moving tests to other packages (they use unexported internals), keeping a persistent private index for candidate snapshots (not equivalent when ignored or excluded paths change), and routing `sys.TmpPath` through a session TMPDIR (protected kogen-loop code).

## Tests
- kogen/build and kogen/shape finish within 400 s at 4-CPU scheduling, their serial tests within 30 s and 120 s, and every package of the check passes: acceptance scenario "The two slowest packages finish well inside the package timeout on four CPUs" (scenario)
- Same tests and coverage (names, subtests, skips, constraint, no timeout/parallelism/GOMAXPROCS/GOFLAGS setters): acceptance scenarios "kogen/build and kogen/shape keep exactly their tests" and the inventory steps of scenario 3 (regression)
- `durable.Sync` reaches `f.Sync` by default, returns nil without it after `SkipSyncInTests`, and no non-test code calls the switch: acceptance scenario "Kogen itself still flushes its private records to stable storage" with its overlay unit test (unit)
- The changed sync call sites and the Build facts reuse keep their behavior: the existing build, shape and project tests pass unchanged (existing)

## Feasibility
- Baseline on the shaping host, uncached, `GOMAXPROCS=4 GOFLAGS=-trimpath go test -count=1 -json ./...` in a clone of 815a7c4: exit 0, kogen/build 581.2 s (serial 245.3 s), kogen/shape 431.7 s (serial 275.1 s), kogen 178.0 s, kogen/verify 56.5 s, load 17 to 28. A build/shape-only run gave 568.9 s and 421.1 s. With the default GOMAXPROCS (10) under load about 45, kogen/build failed at its 10-minute timeout (605.9 s) and kogen/shape passed in 553.5 s.
- Scratch remedies, same command: parallel scheduling alone 514.6 s / 460.7 s (the four slots stay full); syncs skipped alone 446.7 s / 369.0 s; both 372.5 s / 333.1 s; both plus the facts reuse and two more parallel tests 326.4 s / 338.3 s, serial phases 18.9 s / 93.4 s. Every package passed, and the passed names (884 / 479) matched the baseline in each run.
- One full-Build test: 6.3 s, about 163 git processes (41 `rev-parse --absolute-git-dir`), 127 after the facts reuse. A pinned-parts test: 8.2 s with syncs, 1.9 s without. In a 22 s pinned-parts test, 374 candidate snapshots (read-tree/add/write-tree) took about 19 s; this is product behavior and stays.
- The acceptance on the unchanged tree took 33 s: scenario 1 passed, scenario 2 failed (`undefined: Sync`), and scenario 3 stopped kogen/build's serial phase at 30 s. On the scratch remedy with a correct `kogen/durable`, all 3 scenarios passed in 358 s. The overlay test rejected a Sync that never syncs, a switch that does nothing, and syncing off by default.
