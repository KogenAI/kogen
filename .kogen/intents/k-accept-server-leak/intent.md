# Stop processes an acceptance run leaves behind

Slug: k-accept-server-leak
Model: not applicable — the change adds one cleanup action at the end of the existing acceptance step; no new state, transition or interacting rule
Acceptance:
- .kogen/intents/k-accept-server-leak/acceptance.feature
- features/steps/k_accept_server_leak_steps.js
- features/steps/k_accept_server_leak_driver.go

Fix K-ACCEPT-SERVER-LEAK. When an acceptance step puts a server in the background in its own session or process group, the server keeps running after the acceptance run ends, with parent pid 1, so the host looks busy and later work waits behind it. After this change, when an acceptance run ends (passed, failed or timed out), every process it started, including servers a step put in the background, is stopped before Kogen continues, and only processes the run started are touched.

Current behavior (the code does this now): `verify.RunAcceptance` (`cli/verify/run.go`) runs the configured acceptance command through `runStep` with `sys.Options{KillGroupOnExit: true}`; under an approval `Attempt` the step is also bounded (120 s, `StepTimeout`) and a timed-out step has its process group terminated. Only the command's own process group is swept. A process that left the group (`setsid`, Node `spawn(..., {detached: true})`, Python `start_new_session=True`) is never stopped. Reproduced on the unchanged tree for all three outcomes (see Feasibility). This replaces the documented limitation "processes that leave the group with `setsid` are not reached" for acceptance runs only.

Scope: every run of the acceptance command through `verify.RunAcceptance`, which is the one path used by the Shape and Refine readiness dry runs, `kogen intent approve` readiness and every Build verification pass. Setup commands, fixers, checks, probes, hooks, Git, the builder's and reviewer's shell and the Claude Code executor are unchanged. No option, setting, timeout or limit is added; the 120-second approval step bound, the Build's unbounded acceptance step, the no-progress watch and the existing group sweep and termination are unchanged.

## Decisions
- When an acceptance run ends, passed, failed or timed out, every process it started is stopped, including servers a step put in the background; nothing it started survives the run. (source: request)
- Only processes the run started are touched; a process started outside the run is left running. (source: request)
- No new option, timeout or limit. (source: request)

## Execution contract

1. Marker. `verify.RunAcceptance` generates a fresh random value for each run (at least 128 bits, lowercase hex) and adds `KOGEN_ACCEPTANCE_RUN=<value>` to the acceptance command's environment next to `KOGEN_ACCEPTANCE_FEATURES` and `KOGEN_ACCEPTANCE_REPORT`. It replaces any value inherited from the caller (a Kogen run nested inside another acceptance run gets its own value; Go's `exec.Cmd` keeps the last duplicate, so the per-run value must come after the session environment). Kogen's own process never carries its runs' values.
2. Stop. Once the acceptance command was started and before `RunAcceptance` returns, whatever the ending (exit 0, nonzero exit, the approval step timeout after the existing group termination, `ErrTimeoutObservation`, `command_no_progress`, or a stop while it ran), Kogen takes a snapshot of the process table and selects the processes owned by the current user, other than Kogen's own process, that carry exactly `KOGEN_ACCEPTANCE_RUN=<this run's value>` in their environment, plus every process that descends from one of them by parent pid in that snapshot. It sends each SIGTERM, sends SIGKILL to those still present after up to 5 seconds, then repeats snapshot-and-SIGKILL for any newly matching process until a snapshot finds none. A zombie counts as gone. Then `RunAcceptance` returns its usual result unchanged. A process table that cannot be read does not change the acceptance result.
3. Nothing else is touched: no process without this run's value that is not a descendant of one with it, no process of another user, never Kogen itself or its ancestors. Processes of an enclosing or concurrent run carry a different value and are left alone.
4. Platforms: macOS on Apple Silicon and Linux x86-64 glibc, Go standard library only. Linux reads `/proc/<pid>/stat` (parent pid, state) and `/proc/<pid>/environ`; macOS uses `sysctl` (`kern.proc` for the table, `kern.procargs2` for the environment, as `cli/third_party/kogen-loop/sys/timeout_observation_darwin.go` already calls `SYS___SYSCTL`) or `/bin/ps -E -ww`. A process whose environment cannot be read is selected only as a descendant. Honest limit, to be documented: a process that removes the marker from its environment and whose parent is no longer running when the command ends cannot be attributed.
5. Documentation: `docs/configuration.md` (the Commands bullet lists `KOGEN_ACCEPTANCE_RUN` for the acceptance command and says that when the acceptance command ends Kogen stops every process carrying it and their descendants, with the limit above); `spec/prose/05-verifying.md` VER-3 states the same; `spec/prose/04-building.md` LOOP-11 adds `KOGEN_ACCEPTANCE_RUN` to the variables Kogen adds; `spec/prose/02-shaping.md` SHP-10 keeps "processes that leave the group with `setsid` are not reached" for other commands and points to VER-3 for acceptance runs. `(cd spec && sh check.sh)` stays green.
6. Protected harness interfaces. The driver is mounted with `go test -overlay` as `cli/verify/k_accept_server_leak_acceptance_test.go` in package `verify` and uses `RunAcceptance(ctx, s, root, tools, slug, command, report, ev, log)`, `NewAttempt(root, slug, red)`, `(*Attempt).Into`, the unexported `Attempt.timeout` field, the `*stepTimeout` error type and `Tools{}`; keep these names and signatures, and add no `kasl`-prefixed identifiers to package `verify`. The approval observation installs the newest `dist/kogen-*.tar.gz` (built by the configured setup's `sh packaging/package.sh`) through `features/steps/go_driver_support.js` `setupSuite`, and needs `python3` (or `KOGEN_TEST_PYTHON_BIN`) and `ps` on `PATH`.

## Feasibility
- Repository inspection: every acceptance run goes through `verify.RunAcceptance` → `runStep` → `sys.Session.Run` with `KillGroupOnExit`; the approval bound is `Attempt.timeout`. The fix fits in unprotected `cli/verify` (and docs/spec); no protected kogen-loop file needs an edit.
- I ran the protected driver on the unchanged tree in an external read-only session as a `go test -overlay` of package verify (observed by me, not recorded by Kogen as a probe): passed (exit 0), failed (exit 1) and timed-out (`step acceptance timed out` after 3.1 s) runs each left their `python3 -m http.server` alive in its own process group 5 s after `RunAcceptance` returned; the unrelated server stayed running. The driver killed every server afterwards.
- The complete feature against the current release in a `git archive` scratch copy: 5 scenarios, each failing only at its "no background server … is still running" step (the unrelated checks passed), in 42.5 s, leaving no fixture server. Against a scratch-only prototype (marker plus `ps -E` sweep in RunAcceptance, packaged with `sh packaging/package.sh`): 5 of 5 passed in 19.4 s and the unrelated servers were untouched. The prototype is not part of the Intent.
- On macOS, `ps -E -ww` showed `KOGEN_PROBE_MARK=abc123` in the environment of a detached same-user `python3 -m http.server` with parent pid 1 (observed in this session). Linux `/proc/<pid>/environ` for same-user processes was not run here; it is untested in this session.
- The controls below qualify the protected observer with known-good observations and independently damaged predicates (a surviving server per fixture scenario and per outcome, a stopped or never-started unrelated server, a fixture server that stayed in the run's group or was never recorded, a refused or hung approval, a fixture scenario not run or not passing, wrong exit statuses, a missing step timeout or one that ended early, a mismatched mode). They are observer controls only, not product evidence.
