# Name missing acceptance items before no_progress

Slug: k-build-early-stop
Model: not applicable — one remembered notice per identical red inside the existing native stall rule; the Build state machine, its endings and its limits are otherwise unchanged
Acceptance:
- .kogen/intents/k-build-early-stop/acceptance.feature
- features/steps/k_build_early_stop_steps.js
- features/steps/k_build_early_stop_driver.go

Fix K-BUILD-EARLY-STOP. A native Build stops with `candidate/no_progress` while acceptance still reports most of its required scenarios as not passing. The builder's last round ends quickly without a tool call, the next verification pass fails the same way, and Kogen ends the Build. It does not make the builder write the missing items.

Current behavior (`cli/build/noprogress.go`, `stalled`, LOOP-7). In a native whole-Intent pass or stage gate, Kogen stops at once in one case. The round made zero tool calls (`finish` counts as one). The pass is red and clean, with no moved files, a nonempty tree and a nonempty failing set. Its identity (stage, candidate tree, failing item names) also equals the previous red pass. The stop message is `the builder answered the failure feedback without a tool call, and verification pass N is the same red as the pass before it; edits are left in place`.

New rule. It applies only to the native builder, at that same stall condition (call it C).

- **Missing acceptance items of a pass.** When `pass.Acceptance` is not nil, these are its expected scenarios whose `Status` is not `passed`, in feature order. Each is rendered `<status>: <name> (line <line>)`, for example `failed: Second (line 4)`. This is the first line of that scenario's existing feedback problem. A pass whose acceptance did not run (nil), or whose scenarios all passed, has no missing items.
- **First time C holds with missing items.** This applies when C holds, the pass has at least one missing item, and no notice has been given yet for this same red identity. Kogen does not stop. It records one run-log event `{"event":"missing_items_notice","pass":<N>,"missing":[<items>]}`, then sends the builder the notice, a blank line and the ordinary `PassFeedback` of that pass. This counts as an ordinary red repair, and the same conversation continues. The tool-free round ended without `finish`, so this text is the next user message.
- **Exact notice text** (here N=2, two items):
  `Required acceptance items are still missing: verification pass 2 is the same red as the pass before it, and your last round ended without a tool call. The Build is not complete until each of these acceptance scenarios passes:` newline, then one `- <item>` line per item, each followed by a newline, then `Work on them now with your tools (write the missing tests and the implementation they need), then call finish. Another round without a tool call into the same red stops the Build as no_progress.`
- **C holds again after a notice.** If C holds again for a red identity that already got a notice, the Build stops `candidate/no_progress` (exit 1). This also covers rounds that made tool calls without changing that red. The message is `the builder was told which required acceptance items are missing and answered again without a tool call; verification pass <N> is the same red as the pass before it; edits are left in place`. Its lines are `candidate tree: <tree>`, `failing: <failing items joined by ", ">`, one `missing: <item>` line per missing item of that pass, and then the existing unchanged resume sentence. Stdout therefore shows, for example, `  failing: acceptance\n  missing: failed: Second (line 4)\n  missing: failed: Third (line 6)\n`. Candidate edits, HEAD, checkpoint and approval are preserved, as today.
- **C holds without missing items.** Examples are a red configured check with green or unrun acceptance, and a staged gate, whose scoped pass never has acceptance. The stop stays immediate, with the existing message and lines and no notice.

Termination. Kogen gives at most one notice per red identity (stage, candidate tree, failing items). Once given, the following identical tool-free red stops the Build. A green pass clears the remembered notice. A different red identity needs a changed tree, stage or failing set, which existing rules already treat as progress. So the Build cannot loop without bound on notices. The notice memory lives with the existing in-memory `progressWatch` and is not checkpointed: like the prior-red memory, a resumed Build starts without it. No limit, round count, retry value, option, setting, CLI flag or environment knob is added or changed. External executors are unchanged: `executor_no_progress` after three identical passes still stops with `executor_round_limit`, with `max_rounds` unchanged. Stage gates are unchanged.

Update the LOOP-7 prose in `spec/prose/04-building.md`, and the verification-level `no_progress` sentence in `docs/configuration.md`, to describe the one notice before the stop. Do not edit protected `cli/third_party/kogen-loop/**` or `cli/loop-pin.json`; the change belongs in `cli/build`. Tests use only the existing scripted fake provider and fake acceptance and check scripts: no live model calls, and no sleeps as synchronisation.

## Decisions
- While required acceptance items are still missing, one tool-free identical red does not end the Build. The builder is told exactly which acceptance scenarios are not passing and is asked to work on them. If it answers that notice again without progress, the Build stops as `no_progress`, and the stop message names the missing items. (source: request)
- A Build that genuinely cannot progress still stops: at most one notice per identical red. No limit, round or retry value is raised, and no option or CLI change is made. (source: request)
- Required acceptance items are the scenarios Kogen's own acceptance accounting reports as not passed. Kogen cannot tell a test that was never written from a failing one in general: the evidence includes Go names and ExUnit tags. So any non-passed expected scenario counts as missing, and the named-test lines already in the feedback stay in the ordinary feedback that follows the notice. (source: request)
- Tests use fake builders and fake check output, with no live model calls and no sleeps as synchronisation. (source: request)
