# Stop Builds on repeated host or base failures

Slug: k-env-failure-park
Model: not applicable — the change adds one remembered environment failure of the previous builder pass to the existing round end and one stop; the Build state machine is otherwise unchanged
Acceptance:
- .kogen/intents/k-env-failure-park/acceptance.feature
- features/steps/k_env_failure_park_steps.js
- features/steps/k_env_failure_park_driver.go

Fix K-ENV-FAILURE-PARK. A configured check that fails because of the host or the base, not the candidate, keeps going back to the builder as repair feedback. On 1 Nov 2026 (MacBook, 16:58-20:50Z) Kogen's `go-test` check ended in `panic: test timed out after 10m0s` in 9 of the last 10 runs because two or three test suites overlapped on the host; K-MANAGED-CLAUDE, K-SATISFIED-REBUILD and K-SHAPE-UNWRITTEN-TESTS each spent 4 to 6 builder rounds on these timeouts, each round costing model time and a full verification, and no builder could fix them.

Current behavior (`cli/build/builder.go` `verifyAndReview` and `stageGate`): every red pass after a builder round increments `Repairs` and returns `PassFeedback` to the builder, whatever the failure. Only the native LOOP-7 `no_progress` rule, the external `executor_no_progress` rule (three identical passes over an unchanged tree) and an external `max_rounds` cap end that loop, so changing candidates keep receiving the same timeout.

New rule. It applies to every builder pass: a whole-Intent verification pass after a builder round (whatever the executor, native or external such as `claude-code`) and a stage gate.

- **Environment failure of a pass.** A result in the pass's check results (`pass.Checks`: the configured checks, or a stage gate's `stage-<id>-<n>` checks) with a nonzero status whose captured output has a line that, with surrounding whitespace removed, begins with `panic: test timed out after `. This is the Go test binary's own timeout panic. Its failure text is the first such line, trimmed, for example `panic: test timed out after 10m0s`. No other output is an environment failure: an ordinary failure such as `--- FAIL: TestAppIsReady` stays a candidate failure. Setup commands, acceptance and the model are not inspected.
- **Same failure, two passes in a row.** Kogen remembers, in memory, the environment failures (check name and failure text) of the previous builder pass of this Build attempt; every builder pass replaces that memory, so a pass without an environment failure, or a green pass, clears it. When a builder pass has an environment failure with the same check name and the same failure text as the previous builder pass, the Build stops at once. The first such pass is still ordinary feedback to the builder, unchanged. The memory is not checkpointed: a resumed Build starts without it. Passes that verify an independent reviewer's repairs are unchanged: they neither stop nor update the memory.
- **Precedence.** The check runs right after the pass, before the LOOP-7 `no_progress` decision and the missing-items notice, before `Repairs` is incremented and before the external `max_rounds` cap. When it holds, it wins; no feedback is sent.
- **The stop.** `environment/host_or_base_failure`, exit 3. Detail (here check `go-test`, passes 1 and 2): `check go-test failed the same way in verification passes 1 and 2: panic: test timed out after 10m0s; this failure is in the host or the base, not in the candidate, so no further builder round was requested; edits are left in place`. Lines, in this order: `check: <name> (<command>)`, `failure: <failure text>`, `evidence: <name> output of verification passes <N-1> and <N> in <absolute run log path>`, `candidate tree: <tree of pass N>`, and ``No further builder round was requested. Fix the host or the base (for example, run the check when no other test suite is running), then `kogen intent resume <build-id>` verifies this candidate again, or start a fresh Build.`` Before the stop the run log records `{"event":"host_or_base_failure","check":<name>,"failure":<failure text>,"passes":[<N-1>,<N>]}`. The ordinary stop path follows: `failed <slug>: host_or_base_failure (Build <id>)`, `still failing: <name>`, the existing checks comparison with the check's output excerpt, `edited:` and `run log:` lines, result outcome `host_or_base_failure`, and the existing checkpoint at `builder_verify`. Candidate edits, HEAD, the user's index and approval are preserved; nothing is committed. Native `kogen intent resume` verifies again as for `no_progress`; external executors keep their existing builder-stage resume refusal.

Nothing else changes: ordinary candidate failures, including an identical ordinary failure repeated in every pass, still get builder rounds; `no_progress`, `missing_items_notice`, `executor_no_progress`, `max_rounds` and the review stage behave as before. No command, flag, option, setting, timeout, retry, limit or round count is added or changed. Do not edit protected `cli/third_party/kogen-loop/**` or `cli/loop-pin.json`; the change belongs in `cli/build` (and, if useful, a small recognizer in `cli/verify`). Keep the existing `cli/build` test helpers the acceptance driver calls (`newEnv`, `useExecutor`, `newFakeExecutor`, `withExecutor`, `physical`, `writeFile`, `eventsNamed`, `itoa`, the env methods and the fake provider) usable with their current signatures. Update `spec/prose/04-building.md`: add `host_or_base_failure` to the list of Build endings in its first paragraph, describe this rule in LOOP-7, and say in LOOP-14 that it applies to external executors too. Tests use only the scripted fake provider, fake external executor and scripted check commands: no live model calls and no sleeps as synchronisation.

## Decisions
- When the same environment failure ends two verification passes in a row, the Build stops sending builder rounds and stops with a host-or-base failure that names the check, the repeated failure and the evidence, leaving the candidate in place; a real candidate failure still gets builder rounds as today. (source: request)
- The recognized environment failure is exactly the Go test binary's `panic: test timed out after <duration>` line in a failing check's output, the request's example; no other output is classified as environmental. (source: request)
- No new command, flag or option, and no timeout, retry or limit change. (source: request)
- The acceptance is one fast check with fake builders and no model, well inside approval's 120-second step limit. (source: request)

## Tests
- The same `panic: test timed out` in the same configured check ending passes 1 and 2 stops the native Build after pass 2 as `environment/host_or_base_failure` (exit 3) with the named lines and event, after exactly one feedback round and no further builder request, candidate left in place: acceptance scenario "native timeout", plus a Go regression test in `cli/build` asserting the same over the scripted fake provider (regression)
- An external executor Build gets the same stop after pass 2 with 2 rounds instead of running to `executor_round_limit`: acceptance scenario "external timeout" (scenario)
- Two timeouts that are not in consecutive passes do not stop the Build; the stop names the consecutive passes 3 and 4: acceptance scenario "not in a row" (regression)
- An identical ordinary test failure in passes 1 and 2 still gets builder rounds and lands: acceptance scenario "ordinary failure" (existing)
- The recognizer classifies the timed-out `go test` output as the environment failure `panic: test timed out after 10m0s` and an ordinary `--- FAIL` output, or a zero status, as none: a focused unit test of the recognizer (unit)
- A stage gate whose check times out the same way in two consecutive gates of the same stage stops with the same `host_or_base_failure`: a Go integration test in `cli/build` with a staged plan (integration)
- Existing LOOP-7 `no_progress`, missing-items notice and `executor_no_progress` behavior is unchanged: `cli/build/noprogress_test.go` and `cli/build/k19_no_progress_test.go` pass unchanged (existing)
- Configured checks stay green after the change: format, compile, test, go-test, no-home-paths, spec and the chapter 04 cucumber check (existing)

## Feasibility

It compiles and runs the real Build in all four modes in about 9 s with a warm cache and reproduces the defect: "native timeout" gets 5 feedback rounds on the same timeout until the fake provider's script ends (`provider/refused`, exit 4); "external timeout" runs 6 rounds to `candidate/executor_round_limit` (exit 1); "not in a row" runs 7 passes; "ordinary failure" already lands after 3 rounds and its step passes.
