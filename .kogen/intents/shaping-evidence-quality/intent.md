### Native evidence declarations

Keep the existing Intent sections. Add an optional machine-readable bullet to `## Feasibility` for each declared obligation:

`- evidence: {"id":"route","kind":"capability","inputs":["route.json","route.cjs"],"observers":[],"checks":[{"name":"support","command":"node route.cjs","exit":23,"output":"explicit rejection\n"}]}`

The JSON is one line. `id` names the obligation for diagnostics; ids are unique within the Intent. `kind` is `capability` or `observer`. `inputs` and `observers` name the exact repository-relative regular file inputs and observer files used by the commands, including any local executable fixture. A capability has one `support` check. An observer names its final generated protected observer file(s) in `observers` and has exactly two checks in order, `good` and `bad`, demonstrating that those same observer bytes accept the known-good fixture and reject the known-bad fixture. Each check declares a shell `command`, expected integer `exit` and exact combined `output` string. A nonzero expected exit is legitimate observed rejection, not a tool failure to hide. Timeout never discharges an obligation. These declarations are small targeted checks, not the full acceptance suite, a second review, or an implementation of the proposed product.

Shape and Refine guidance must explain this optional format and when to use it. Before expensive implementation, identify genuinely uncertain outcome-critical dependencies; probe the actual proposed request on its supported target route/scope/model, or a real relevant local fixture, rather than a different route or old driver. Distinguish observed support, explicit rejection and untested uncertainty. If unsupported, shape an honest supported outcome/fallback or clarify a material UX choice; do not claim support. Already fresh relevant native probe evidence may discharge an identical check only when actual command, input/observer bytes and observed outcome match. Narrative claims, fabricated records, model-only green, an unrelated successful probe or a missing-feature assertion are not evidence.

Readiness executes any outstanding declared checks using the existing bounded scratch probe path and records actual results before granting readiness. Reuse the current probe mechanism and retained evidence, not another runner/service. Scratch-only fixture overlays are useful for exploratory probes, but final proof must identify the submitted final formatted input/observer bytes. Do not silently use an earlier observer version or warm output as the final proof. Applicable probe execution must retain the command, file identities, actual exit, timeout and output, including mismatches. Return a bounded diagnostic naming obligation id/check, expected and actual results to Shape/Refine when a check fails. Keep failed observations inspectable in existing native local evidence; do not publish ready proof for an unsatisfied obligation.

For completed readiness, extend `.kogen/local/readiness/<slug>.json` with `feasibility`, an ordered array matching the declared obligations. Each entry contains `id`, `kind`, `inputs` and `observers` (maps of relative path to lowercase SHA-256 of the actual bytes), and ordered `checks` containing `name`, actual `command`, actual `exit`, actual `timed_out` and actual combined `output`. The existing full baseline hash, HEAD, declarations and Snapshot candidate tree bind this evidence to the exact complete package. For a no-obligation Intent, absent or empty `feasibility` is equivalent and existing valid version-3 records remain usable. For a declared obligation, absent, incomplete, mismatching, stale or inconsistent proof is a normal cache miss, never readiness.
