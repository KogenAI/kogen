# Expose checkout-local Kogen facts

Slug: checkout-cli-dx
Model: .kogen/intents/checkout-cli-dx/model.qnt invariants=Safety seed=21 samples=1000 steps=40
Acceptance:
- .kogen/intents/checkout-cli-dx/acceptance.feature
- features/steps/checkout_cli_dx_steps.js

Provide checkout-local lifecycle facts and discovery through the actual CLI, not shell presentation. This is one native Intent. Implementation, tests and maintained specifications belong to native Build, verification, independent review, final verification and the signed commit path. Root owns installed qualification, publication and default adoption. The operator prerequisite is that the compatibility repair has been separately qualified/pushed and source-owner handoff is clear; this Intent does not assert or perform that external handoff. Preserve active frozen prefixes and the default Studio store. Fixtures use disposable prefixes/homes only.

## Decisions
- Supply facts for prompts, completion, editors and other consumers, without Starship formatting, colors/layout, Git/SSH indicators, history/autosuggestions or machine shell configuration. Do not add worktree creation/orchestration, parallel services, a daemon, a shell framework, or provider/model/cap/pipeline levers. (source: request)
- Use `kogen context`, `kogen intent list`, `kogen intent inspect <run-id>`, `kogen intent preflight <slug>` and `kogen completion zsh`. All four checkout read commands accept `--project <checkout>` and resolve a nested directory to its containing checkout. Existing Build/resume command names remain unchanged. (source: answer 1)
- Context defaults to JSON; list, inspect and preflight default to concise human output and accept the boolean `--json`. Context accepts `--json` as an explicit spelling of its default. (source: answer 2)
- Last built means the Intent whose Build most recently started in this checkout, even if it failed; rejected invocations do not replace it. Explicit resume creates another attempt with original lineage and retains previous results. Review is one conversation, not numbered repair cycles; verification pass count is the existing pass number, not a failure count. (source: request)
- Preflight is a read-only, point-in-time investigation of useful existing prerequisites, not comprehensive Build validation or authorization. Never execute setup/checks/hooks, stash, clean, commit, approve or resume in a read interface. Preserve exact approval, protected-contract recovery, signed commits and normal authoritative Build revalidation. (source: request)

### Authoritative owners and implementation boundaries

Inspected owners are `cli/main.go` and `cli/session.go` (grammar, bridge, cancellation and core crash), `Kogen.Build` (fresh checks, start, resume, pass counter, commit and stopped receipts), `Kogen.Review` (same conversation and external repair verification), `Kogen.Run` (private run custody and atomic checkpoint publication), `Kogen.Lock`, `Kogen.Config`, `Kogen.Intent`, `Kogen.Readiness`, `Kogen.Git` and `Kogen.Snapshot`. Extend those owners at real execution transitions. Do not introduce a second Build controller or deserialize opaque Erlang checkpoint state in Go. Current `b.phase` distinguishes only startup/building and cannot by itself supply the requested phases. Preserve checkpoint version 2 compatibility and its guarded resume validation; integration metadata must not become approval or resume authority. Share/extract narrowly reusable existing read-only validation rather than copying all Build validators.

The current CLI starts the core for every ordinary invocation and offers none of these discovery commands. Replace that behavior for context and completion: they execute entirely as bounded local reads without Elixir/BEAM, Node, providers, login refresh, service startup, setup, checks, Git status/diff/log, or historical-run enumeration. Fixed Git checkout discovery commands are allowed; no historical search. List and inspect must also avoid scanning historical log streams or executing readiness. Keep local data in ignored `.kogen/local/`, never in commits. New production code can live in ordinary `cli/` and `lib/kogen/` files without editing `mix.exs`, `.formatter.exs`, the approved Intent/helpers or `.kogen/project.yaml`.

### Version 1 output contract

Document the following contract in maintained CLI specifications and user documentation, updating obsolete command/help and always-start-core claims and their tests. JSON stdout is exactly one UTF-8 JSON object plus newline, with no progress/help mixed in. Progress remains stderr. Each JSON response contains `schema_version: 1`, `kind` (`context`, `intents`, `run`, `preflight`), `checkout` (null or `{id, root, git_dir}`), `data` (object or null), and `error` (null or `{class, reason, detail, paths: []}`). Roots and git_dir are canonical absolute paths. `id` is an opaque exact-checkout identity, stable across repeated reads and different from another linked worktree; consumers must not parse it. Required fields are present: null means unknown/not applicable/absent, [] means no entries. Additive fields are allowed. Do not fabricate historical facts to fill missing fields.

Successful reads exit 0, including context outside a Kogen project and empty lists. Outside a Kogen project context has checkout null, data `{project: false, active: null, last_built: null, integration_state: "missing"}`, error null. A project is a containing Git checkout with `.kogen/project.yaml`; malformed configuration is not a successful preflight. For list/inspect/preflight, absent project is `environment/not_project`, exit 3. Existing CLI exit categories remain: 2 argument/usage, 3 environment, 1 negative result, 5 caller action where already applicable, 70 internal defect. New JSON-mode argument errors use `intent/invalid_argument`, exit 2, not a help page; unavailable project uses `environment/project_unavailable`, exit 3; unknown run uses `intent/run_not_found`, exit 1. Invalid local metadata must not crash or imply activity: context reports `integration_state: "invalid"` and null unknown facts, exit 0; list/inspect report available bounded evidence with explicitly unknown fields or `environment/local_data_invalid` (3) if their required record cannot be interpreted. Document which observations are recorded versus checked now.

Context data in a project is `{project: true, active, last_built, integration_state}`. `integration_state` is `ok`, `missing` or `invalid`. `active` is null or `{slug, run_id, phase, verification_pass}`. Phases are `startup`, `building`, `verifying`, `reviewing`, `committing`; `verification_pass` is a positive integer only while verifying and null otherwise. `last_built` is null or `{slug, run_id}` and remains set after every stop/completion. The file `.kogen/local/context.json` is the documented integration snapshot; the CLI validates schema, checkout identity and ownership/liveness before advertising activity. Its private ownership fields need not be a public API. Publish a coherent whole snapshot by same-directory atomic replacement. A read must see an old or new whole version, never torn JSON or mismatched run/phase/pass. Dirty files and Kogen-Intent commit trailers have no role in liveness or last-started selection. Missing/malformed snapshots do not trigger historical reconstruction.

Publish last_built when a fresh Build has actually acquired run custody (`Run.start` after existing fresh prerequisites), including subsequent startup failures. Never change it on failed approval/configuration/cleanliness/tool/login/conflict prerequisites that create no Build, refused resume, or the landed-resume no-op. Publish a new active run and last_built for an accepted resume, retaining parent/root IDs and cumulative pass count. Original result/checkpoint evidence remains intact. Clear active for normal completion, negative results, cancellation and interruption. Abrupt CLI/core death must stop being advertised as active within 15 seconds without a later Build or reader mutation: validate the matching live owner, not just presence of a file/PID or dirty tree. A dead owner leaves recorded last_built visible and inspection reports an interrupted/crashed observation, not a fabricated completed outcome. Account for PID reuse and lock-owner mismatch. Do not add heartbeat services or impose Build duration caps.

### Listing, inspection, completion and preflight

`intent list [--limit N] [--cursor TOKEN] [--json] [--project DIR]` returns `data: {items: [], next_cursor: null|opaque-string}`. Default limit is 20, valid range 1..100. Items are ordered by slug ascending; an Intent package row (`type: "intent", slug, package_state, approval_state`) precedes its Build rows (`type: "build", slug, run_id, started_at, state, phase, resumed_from, root_run, resume_status`). Within a slug Build rows are most-recent-started first, ties by run_id ascending. The limit bounds total rows, not just Intent count. Pagination visits each row once for an unchanged dataset; invalid cursors/limits are argument errors. Package state is `valid`, `invalid` or `unknown` from static package information/retained readiness, not fresh execution; approval state is `absent`, `current`, `changed` or `unknown`, distinct from run outcomes and current activity. Do not label static validity as freshly verified readiness. Preserve every attempt, not merely a latest outcome. Use bounded summary/index data published by lifecycle owners; do not rebuild a catalog by opening all historical runs on a prompt/completion read. Existing legacy runs may be explicitly listed/inspected with unknown/unsupported fields; no automatic historical migration is required for fast reads. Human listing uses the same rows and identifies package/approval versus run state.

`intent inspect <run-id> [--json] [--project DIR]` returns kind run and `data` containing `slug`, `run_id`, `resumed_from` (null for fresh), `root_run` (fresh ID for a fresh attempt), `state` (active or recorded outcome; `interrupted` for an unfinalized dead owner), `phase` (actual active or last recorded phase), `verification_pass`, `verification` (bounded summaries of actual pass evidence and paths), `reviews` (available verdict/findings summaries and paths), `reason`, `blockers` (with affected paths), `locations: {candidate, run_dir, log, checkpoint}`, `commit` (null or full commit), `resume_status`, `next_command`, and `observations`. Evidence arrays return at most the latest 20 entries each, chronological within that window, with `evidence_truncated` and artifact locations for older evidence. Do not read unlimited log/transcript bodies to obtain summaries. Current observations are labelled separately from historical evidence; an earlier green pass is not proof of the current candidate. Resume status is `unsupported` (legacy/missing/incompatible checkpoint or known unsafe boundary/protected blocker), `potentially_available` (compatible stopped checkpoint, still subject to authoritative safety validation), or `requires_validation` (insufficient evidence or a live attempt). This read never claims permission to resume. For a potentially available run the exact `next_command` is `kogen intent resume <run-id> --project '<canonical-root>'` with proper POSIX shell quoting. For unsupported runs it is null; explain the blocker and do not suggest retry bypasses it. Landed inspection identifies its commit and the supported landed no-op if appropriate, not a fresh Build. Inspection of one ID cannot find an identically named run in another checkout.

`kogen completion zsh` prints a standalone Zsh completion definition for commands, options, file/directory arguments and checkout-local Intent/run positional candidates. Document saving it as `_kogen` on `fpath`, `autoload -Uz compinit; compinit`, and regenerating it after updates; do not edit startup files or require Oh My Zsh/plugins. A private native helper `kogen __complete <operation> [--project DIR]` emits tab-separated `value\tdescription\n` candidates (no progress). Operations are `build`, `approve`, `refine`, `preflight`, `inspect`, `resume`. This helper exists only to support completion without jq/Python/Node/runtime startup. It reads the same bounded local facts: at most 100 candidates, stable ordering; unknown/missing data yields no invented candidate. Intent operations use local slugs; build prioritizes current approvals, approve prioritizes unapproved/changed packages, refine offers existing ready packages where known, and preflight offers existing packages. Inspect offers recorded Build IDs; resume excludes known unsupported and landed attempts and supplies concise descriptions containing slug and recorded state, not a guarantee of safe resume. Respect selected `--project` and nested working directories; do not use another worktree's approvals/runs. Static command and option completion stays usable outside projects. Actual resume still performs all existing validation.

`intent preflight <slug> [--json] [--project DIR]` returns `{slug, ready, checks, blockers, limitations}` as data. `ready` means only that its named supported observations passed. Support read-only configuration parse, static Intent/package lint, exact current approval identity, Build's allowed-dirty-path policy, and execution/Git-operation conflict observation. Checks use names `configuration`, `package`, `approval`, `cleanliness`, `conflict` with status `passed`, `blocked` or `not_evaluated`; blockers have class/reason/detail/paths. Reuse/extract authoritative Config/Intent/Build/Git/Lock validation and path rules rather than reimplementing them. Inspect lock ownership without acquiring, releasing or recovering locks. On a blocker ready is false, return exit 1 with data/blockers (error null); invalid environment/config can use the established environment error with paths and exit 3. Explicit limitations must say setup/checks/hooks/providers/tool availability/signing and full readiness/resume safety were not executed/established. No snapshots that mutate Git, new run/readiness/approval records, lock recovery, dependency installation or configured command execution. Build revalidates normally after a green preflight. Document the investigation's concrete owner reuse and omitted prerequisites before claiming supported scope.

Stopped Build receipts supplement existing error categories and signal exits with slug/run when created, actual phase, concrete reason, preserved candidate/index/evidence locations, blockers and an exact supported inspect or continuation command. A refusal before run creation must explicitly have no newly created run and must not borrow an old ID. Preserve existing error lines where compatible; update byte-exact CLI/spec tests where the added commands/receipts intentionally replace old output. Core crash receipts report observed HEAD honestly and do not perform new recovery. Unsupported resume and protected-contract blockers recommend inspection/correction/fresh exact approval as appropriate, never imply automatic clearance.

### Evidence requirements

Acceptance helpers are independent drivers, not feature implementations or editable implementation tests. They install a freshly packaged release using maintained temporary-project/fake-provider helpers, call real CLI commands, pause actual Build/verification/reviewer/commit transitions, and retain measured observations. Expected outcomes are in the feature. An unknown new CLI command is legitimate baseline red, not evidence that later fixtures ran correctly. Builder must add focused callable-rule tests for metadata validation/filtering/pagination and extend maintained lifecycle/process tests for races, owner mismatch/PID reuse, malformed/missing metadata, startup failure and refusal timing. Exercise successful and failed builds, repeated failures, cancellation, abrupt core/CLI death, same-reviewer repairs/final verification and guarded resume. Keep independent actual end-to-end lifecycle evidence; do not replace it with seeded integration JSON alone.

Measure 20 installed context and resume-candidate reads both before/after accumulated history, record p50/p95/max wall milliseconds, and show context/resume completion still work with the installed core removed and historical-run directory inaccessible as a FIFO. The acceptance budget is p95 <=100 ms and max <=500 ms per read on the local supported test host, excluding fixture/package preparation. This is an integration-read budget, not a whole Build performance promise. No heavyweight child may be launched even if it happens to finish quickly. Add read-bound tests beyond timing (fixed metadata reads and bounded catalog pages, not a linear run-history search); use controlled history fixtures/denied access, not provider call counts alone. Demonstrate real Zsh syntax and dynamic candidate wiring, and add a Zsh completion integration check for selected command/options/positionals. Measure installed latency without Mix/core startup included in the measured read path. Record platform and sample counts; supported-platform release qualification remains Root's separate job.

- Completion resolves operation-relevant local candidates without heavyweight startup: installed candidate helper and Zsh syntax scenario plus actual Zsh command/option/positional integration test (scenario)
- Context/completion are bounded even with history and unavailable core: installed blocked-history reads and measured 20-sample latency scenario (integration)
- Preflight reuses narrow authoritative read-only prerequisites without running commands or modifying custody: green/dirty/changed-approval/conflict installed scenario (scenario)
