# Show key saved, connection tested, role verified

Slug: onboarding-credential-states
Model: not applicable — the three states are derived from files on disk (the saved credential, one recorded test result and a docs table) each time they are shown; nothing carries between runs beyond the recorded result
Acceptance:
- .kogen/intents/onboarding-credential-states/acceptance.feature
- features/steps/onboarding-credential-states__steps.js

A saved key says nothing about whether the endpoint answers or whether a model has been qualified for a role. The CLI shows three separate states with exactly these labels, the same ones Kogen.dev uses: `key saved`, `connection tested`, `role verified`.

`docs/providers.md` gets a section `## Credential states` that defines each label in one sentence, as three bullets of the form ``- `<label>` means <one sentence>.``: `key saved` means a credential is stored locally; `connection tested` means a minimal request to the configured endpoint succeeded (HTTP status and a well-formed reply) at a recorded time; `role verified` means the provider and model are listed with a qualification record for that role in docs/providers.md.

`kogen provider test <provider>` is new and opt-in. It makes one minimal request to the configured endpoint: one short user prompt, no tools, an output ceiling of a few tokens and a streamed reply. It prints `<provider>: connection tested <time> (HTTP <status>)` with the time as UTC RFC 3339 (for example 2026-11-28T10:00:00Z) and exits 0, or prints `<provider>: connection test failed, class: <class> (...)` and exits 4, where the class is one of `auth` (HTTP 401 or 403), `endpoint` (no connection, or any other non-2xx status), `timeout` (no complete reply before the watchdog) and `malformed reply` (a 2xx answer that is not a Chat Completions reply). It never prints the key or any part of the response body. It records the result (time, ok or failed with the class, the endpoint origin) in a file next to the credential in `~/.kogen/credentials/`, outside the repository; a failed test replaces an earlier success, so the state is dropped. The command never runs inside Shape, Build or Review.

`kogen provider list` keeps its current lines and then prints, for each provider and for each role in `.kogen/models.yaml`, which of the three states hold, one line each: `states <provider>: <held labels joined by "; ">` and `states role <shape|build|review> (<provider>, <model>): <held labels joined by "; ">`, or `none` when no state holds. `connection tested` is followed by the recorded time. `role verified` is derived only from the qualification table in docs/providers.md shipped with the binary (the `<Role>: verified (<record path>)` cell of the provider's row), never from a test result. Provider lines show only `key saved` and `connection tested`; `role verified` is a role state.

The guided QwenCloud login from onboarding-account-first offers `Run a connection test now? [y/N]` after it has saved the login and the build role (default no; any other answer than `y` runs nothing). Its summary then prints the three states of the build role in the same role line form.

## Decisions
- Only `openai-compatible` is testable. Its endpoint is the `base_url` of the first role (shape, build, review) whose provider is openai-compatible, read from the lineup with the project loader; other providers are refused with usage exit 2 naming the testable one, because their transports (OAuth, subscriptions, executors) have no configured endpoint to call from the CLI and the loop package that owns them is protected.  (evidence: cli/main.go; cli/third_party/kogen-loop/provider/provider.go; cli/native.go) (assumption: the request names only the fixture openai-compatible route and the QwenCloud build role; testing the other providers is out of this row) (source: request)
- The test sends the saved key only to the origin the key is bound to; when the base URL origin differs from the saved origin, or the origin is plain http that is not localhost or a loopback IP, nothing is sent and the command refuses with exit 4 without recording a result. Plain http loopback is allowed so fixtures work; the login itself still saves keys only for https origins, so the acceptance writes the credential file directly with the fixture origin. (constraint: no key in output; key only to its origin) (evidence: cli/third_party/kogen-loop/provider/origin.go; cli/third_party/kogen-loop/provider/login.go; cli/third_party/kogen-loop/provider/keys.go) (source: request)
- The watchdog is a constant chosen by the Build (no setting), short enough that the command ends well inside the 60 seconds the acceptance harness allows it: acceptance has the fixture withhold its first byte indefinitely and requires the command to end by itself with the timeout class while the fixture still waits. Acceptance asserts no particular length.  (evidence: cli/third_party/kogen-loop/provider/chat_stream.go) (assumption: the request names a watchdog but not its length; the acceptance step limit of 120 seconds forces it below 60 seconds) (source: request)
- A reply is well formed when it is either a server-sent event stream whose data lines include a JSON object with a `choices` array, or one JSON object with a `choices` array (some hosts ignore the stream request, as the Chat Completions route already tolerates). (evidence: cli/third_party/kogen-loop/provider/chat_stream.go) (source: request)
- The recorded result is a file in `~/.kogen/credentials/` next to the credential (private mode, no key inside, no repository file written). `connection tested` is held by a provider only while its latest record is a success; a role holds it only when the record's origin equals the origin of the role's base_url. (evidence: cli/third_party/kogen-loop/provider/creds.go) (source: request)
- `key saved` holds for a provider when the existing local status (provider.Status) reports a stored usable login: a line starting `key saved`, `signed in`, `token saved` or `managed access snapshot fresh`. The existing status lines, including their `(not verified)` wording from the protected loop, stay unchanged and the new `states` lines follow them. Acceptance finds the lines at run time: the role line is the list line naming the build role and its model, the provider lines are the other lines naming the provider; it does not assert the `states` prefix. (evidence: cli/native.go; cli/third_party/kogen-loop/provider/creds.go) (source: request)
- `role verified` for a role holds when the provider's row in the table of the shipped docs/providers.md has `<Shape|Build|Review>: verified (` for that role. The table lists providers and roles, not models, so a verified cell qualifies the role for its provider as recorded today; no model-level check is added. The binary reads `<install root>/docs/providers.md` (the archive already ships docs/); when it is missing no role is verified.  (evidence: docs/providers.md; cli/providers_guide_test.go; packaging/package.sh) (assumption: the table has no model column, so the model half of the request's wording is satisfied by the record named in the cell) (source: request)
- Role lines are printed only when the project lineup loads (project.LoadConfig of the current directory); an unloadable lineup prints no role lines and does not fail the command. (evidence: cli/readiness/readiness.go) (source: request)
- The three labels are Go constants used by every output; docs/providers.md carries the definitions, and acceptance compares the CLI's printed labels to the docs section. `provider test` is added to the `kogen provider` page, to `cli/help.go`, and to each kept copy of that page (spec/prose/09-cli-and-process.md and test/acceptance/support/handlers.js) so the existing byte-equality tests still pass. (evidence: cli/main.go; cli/help.go; cli/help_pages_spec_test.go) (source: request)
- The guided-login prompt and summary are verified by Go tests that inject the test runner (the existing guided tests type their answers; EOF after the confirmation means no), not by a pseudo terminal scenario, because the QwenCloud base URLs are public https hosts and the test must never reach them from acceptance.  (evidence: cli/login_guided_test.go; cli/login_guided.go) (assumption: the four numbered checks of the request use local fixtures; the guided prompt is covered at unit level) (source: request)
- The credential-removal hint printed by uninstall also names the new record files. (evidence: cli/main.go) (source: request)

## Source comparison
- Addressed: exact labels and one-sentence definitions in docs/providers.md (request; scenario 4, Credential states section).
- Addressed: `kogen provider test <provider>` minimal request, success line with time, failure classes auth, endpoint, timeout, malformed reply, no key printed, record outside the repository (request; scenarios 1 to 3).
- Addressed: `kogen provider list` per provider and per role, role verified only from the docs table (request; scenarios 1, 2 and 4).
- Addressed: guided QwenCloud login offers the test and prints the three states (request; Go tests in cli/).
- Kept as constraints, not acceptance: the test is opt-in and never runs inside Shape, Build or Review; no key in output.
- Omitted: connection tests of providers other than openai-compatible; model-level qualification beyond the table.
- Not asserted by acceptance: the exact wording after the class, the record file name and format, the `states` line prefix, the watchdog length, the prompt length and the exact output ceiling; those are the Build's choice within the contract above.

## Tests
- A passing test prints connection tested with a time, sends one minimal streaming request without tools, records outside the repository, and list shows key saved and connection tested but not role verified for a QwenCloud build role: scenario 1 in acceptance.feature (scenario)
- A 401 prints the auth class, leaves no key in output, and list shows key saved but not connection tested after an earlier success: scenario 2 in acceptance.feature (scenario)
- A first byte that never arrives prints the timeout class and the command ends by itself: scenario 3 in acceptance.feature (scenario)
- The labels printed by the CLI equal the labels defined in docs/providers.md: scenario 4 in acceptance.feature (scenario)
- Failure classification (auth for 401 and 403, endpoint for connection refused and other non-2xx, malformed reply for a 2xx non-Chat-Completions body) and well-formed reply detection for stream and plain JSON: Go tests in cli/ with httptest servers (unit)
- Role verified parsing of the providers.md table (verified cell with a record path, not qualified, missing file): Go test in cli/ (unit)
- The guided QwenCloud login offers the test after saving, runs it only after y, and its summary prints the three states; the existing guided tests keep passing: Go tests in cli/login_guided_test.go (unit)
- Parsing of `kogen provider test <provider>` and the updated help pages stay in step with spec chapter 09 and handlers.js: existing cli/parse_test.go, cli/help_test.go and cli/help_pages_spec_test.go updated (existing)
- The provider test is never reached by Shape, Build or Review: no call site outside the `provider test` command and the guided login prompt; covered by review of the change, no test (existing)
