Fix K-REVIEW-SOURCE-BOUND (Studio kogen issue 90061617-7999-4485-8781-10687e87c1f1). Today the external independent reviewer (`reviewExternal`, cli/build/review_external.go; the Claude Code executor) sends its whole first prompt — `claudecode.ReviewConstraints`, a blank line, `Brief.Stable` (authority, diagnostic and staged context, review task), a blank line and `Brief.Dynamic` (the complete candidate source) — bounded only by the Claude Code adapter's 16 MiB sanity bound. The native reviewer's ceiling check (`materialPrepare`) never sees it. Build 6eb946ca (K-MODELS-FILE, 79 files) passed every check and then lost its green attempt: Claude Code answered `Prompt is too long` (terminal reason `blocking_limit`, 0 tokens), reported as an ordinary `executor/failed`. After this change Kogen measures the complete first prompt of every external review session, source included, before sending it. A prompt that fits is reviewed exactly as today. A larger one is reviewed in ordered parts, each in its own fresh session whose complete prompt fits. Mandatory material that leaves no room stops with an explicit review-size result before any review is sent, and a "Prompt is too long" refusal is a context result, never an ordinary executor failure. No ceiling, budget or timeout is raised; no CLI command, flag or setting is added; the native reviewer is unchanged.

1. **The ceiling and what is measured.** The ceiling is the existing inclusive input ceiling `tools.InputBudgetBytes` = 524288 bytes (equality fits), the byte proxy the native reviewer already uses; it is not raised. What is measured is the exact first-round prompt the executor sends for a brief. The executor contract (cli/executor/executor.go, docs/executor-contract.md) gains an optional method by which an executor reports the exact byte length of its first-round prompt for a role and brief. The Claude Code adapter implements it with its real rendering (`constraintsFor(role) + "\n\n" + Stable + "\n\n" + Dynamic`, the same function `session.prompt` uses), so measured and sent bytes are identical. An executor without the method is measured by `len(Stable) + len(Dynamic)`. Later rounds of a session send only Kogen's feedback, as today. The adapter's 16 MiB bound stays for every role.

2. **Fitting prompt: unchanged.** When the complete inline prompt (today's Stable with `reviewTask`, today's Dynamic with the complete source) fits, the review is byte-for-byte today's: one fresh session, the same Stable and Dynamic, `executor-review/review-<n>-authority.txt` (= Stable), `review-<n>-source.txt` (= Dynamic) and `review-<n>-material.json` without `review_parts` (or with an empty one), session folder `executor-review/session`, same delivery and custody rules.

3. **Larger prompt: ordered parts.** Otherwise, unless rule 4 stops it:
   - Stable is today's authority, diagnostic and staged text followed by a parts review task instead of `reviewTask`, identical for every part and written as `review-<n>-authority.txt`. The parts task keeps `reviewTask`'s repair, `agent.LimitRaises` and structured-verdict sentences, and replaces its first paragraph with: the candidate's source does not fit one review prompt, so it is reviewed in ordered parts, each by its own independent session; this message carries the complete authority and one part (the check results, every changed path and one consecutive piece of the exact diff and full text of changed files, nothing clipped, the other pieces going to the other parts' sessions); review against the approved Intent with this part as focus and read any checkout file needed; reviewers of earlier parts may have made verified repairs, so the checkout holds the current candidate.
   - The complete source (exactly today's `materialSet.Source`) is written as `review-<n>-source.txt` and cut, in order, into consecutive byte ranges `[from, to)` whose concatenation is exactly that text.
   - Part k's Dynamic (its part text) is written privately (0600) as `review-<n>-part-<k>.txt`. It starts with the line `# Review part <k> of <N>`, then states its source byte range, the total and the SHA-256 of the complete source, followed by the sections `# Check results of the final pass` (the results of the pass the source was cut from), `# Every changed path` (the existing catalog entries as one JSON line) and `# Source part <k> of <N>` holding its exact slice. Every part text is written and every part's complete prompt measured before part 1 is sent.
   - Cutting rule: parts are cut in order, each as long as possible such that (a) its complete prompt fits the ceiling; (b) it does not end inside one path's material — the path's block in the diff (from its `diff --git` line to the next block or the end of the diff), or its `--- <path>` heading and full text in the full-text section (to the next heading or the end) — when that material alone would fit the room of one part; (c) otherwise it ends just after a newline when one is available within the room, else at a UTF-8 character boundary. The existing per-path segments (`materialManifest`) locate path material.
   - Before part 1: one `review_parts` run event `{"event":"review_parts","review":<n>,"parts":<N>,"source_bytes":<S>,"ceiling":524288}` and the progress line `kogen: reviewing (review <n>) in <N> parts: the complete review prompt would be <B> bytes, over the 524288-byte ceiling`.
   - Parts are reviewed one after another, each in its own fresh session of the review executor (same model, effort, schema, protected paths and `max_rounds` per session), with its own private session folder `executor-review/part-<k>/`. Each runs the existing external review loop unchanged: rounds, verdict validation and the rejected-verdict allowance, the guarded round, custody checks (authority, source and that part file re-read before each round and before an approval is accepted), delivery before approval (the part counts as delivered after a completed round of its own session) and `evaluate` (repairs verified, red results back to the same part session). Progress per part: `kogen: reviewing (review <n>, part <k> of <N>)`; `executor_round` events carry `"part": <k>`.
   - An approval of part k < N does not commit: part k+1 starts with the pass that approval bound (the green pass, or the verified pass of a repaired tree). Only the last part's approval is the review's approval, and the commit follows as today (exact final-tree eligibility).
   - A `changes` verdict of any part stops with today's `candidate/review_blocked` and its `review: <path>:<line>: <message>` lines; later parts are not started.
   - A part that ends without a valid verdict ends the whole review without a verdict (today's `candidate/review_invalid` path): the one automatic fresh review and an explicit `kogen intent resume` start the whole part sequence again from part 1, as a new review number, from the green base.
   - Any other error of a part stops the Build as today. Usage of every part session accumulates in the review executor's known totals; its `session_id` is the newest part's.
   - `review-<n>-material.json` gains `review_parts`, one object per part in order: `part`, `file` (`review-<n>-part-<k>.txt`), `bytes` and `sha256` of that file, `from`, `to`, `prompt_bytes` (the exact complete first prompt), `session_id` (`""` until started), `delivered` (bool) and `delivered_round` (once delivered), updated as each part starts and is delivered.

4. **Mandatory material that leaves no room.** When the complete prompt of a part with an empty slice leaves fewer than 6000 bytes (the size of one pinned source part, `materialPartBytes`) under the ceiling, the review stops before any session starts, with exit 1: `candidate/context_budget_exceeded: review: mandatory review prompt of executor <name> is <M> bytes without candidate source; fewer than 6000 bytes remain for source under the inclusive 524288-byte ceiling; nothing was sent. Inspect the run evidence; ordinary Refine and new exact approval are required if the Intent, README or diagnostic context must shrink.` No review process runs; the candidate files, HEAD, index and approval are unchanged; nothing is committed; the result outcome is `context_budget_exceeded`.

5. **Provider refusal.** In the Claude Code adapter, for every role, a result event with `is_error: true` whose `terminal_reason` is `blocking_limit` or whose `result` text contains `Prompt is too long` is no longer `executor/failed`. It is checked after the existing authentication check and before the usage-limit check, and stops as `candidate/context_budget_exceeded` (exit 1): `Claude Code refused the <role> prompt as too long for the model's context (terminal reason "<terminal_reason>": <bounded result text>); the round's prompt was <bytes> bytes; nothing was clipped or retried`. The `executor_round_failed` event then carries reason `context_budget_exceeded`. There is no retry. The observed shape (Claude Code 2.1.312, Build 6eb946ca `round-1.jsonl`): an assistant event with `error: "invalid_request"`, `is_api_error_message: true` and text `Prompt is too long`, then a result with `subtype: "success"`, `is_error: true`, `terminal_reason: "blocking_limit"`, `result: "Prompt is too long"`.

6. **Unchanged.** The native reviewer (`materialPrepare`, pinned parts, `on_demand`), the inline external review, Shape, the builder (except rule 5's classification), review allowances and retries, `max_rounds`, resume semantics and every existing ceiling, bound and timeout. Update README.md (the review paragraph and the Claude Code review description), spec/prose/06-reviewing.md (REV-2: the external reviewer's measured first prompt, parts and stop) and docs/executor-contract.md (the optional prompt-size method, parts and the refusal result). The protected acceptance driver uses these existing test helpers and names, which must keep working: `newEnv`, `useLineup`, `env.build`, `head`, `commitsSince`, `read`, `jsonFile`, `Input.External`/`Input.Reviewer`, `testSlug`, `claudecode.New`, `claudecode.Options{Home, HookCommand, Env}`, `claudecode.RuntimePath`, `claudecode.ReviewConstraints`, `project.IntentMDPath`, `project.FeaturePath` and `sys.AsError`.

## Decisions
- A review prompt that does not fit is reviewed in ordered parts that each fit, rather than always stopping; the stop is reserved for mandatory material that leaves no room for source (source: request)
- The review-size stop and the provider refusal both use the existing named `candidate/context_budget_exceeded` result with review-specific, actionable detail instead of an ordinary executor failure (source: request)
- Small changes keep today's single inline review unchanged (source: request)
- No new CLI command, flag or setting; no ceiling, budget or timeout raised (source: request)
