# Retry verdictless independent reviews

Slug: k-reviewretry
Model: .kogen/intents/k-reviewretry/model.qnt invariants=Safe seed=31 samples=100 steps=30
Acceptance:

Prevent a green candidate from becoming a dead end solely because independent Review ended without a valid verdict. Preserve all existing valid-verdict behavior. Add one automatic fresh review per exact green candidate and an explicit review-only Resume after that allowance is exhausted. Also repair the in-conversation interaction between rejected verdicts and prose-only turns. This changes neither the CLI nor configured limits, timeouts, retry defaults, review authority, delivery requirements or verdict validation.

## Decisions
- A terminal invalid review of an unchanged, finally verified green candidate gets one fresh independent conversation of the same kind, with the same material and rules, numbered as the next review. Do not reuse its invalid conversation as the fresh review or expose builder replay. (source: request)
- If that fresh review is also invalid, stop with candidate/review_invalid, preserving candidate work and a durable review-only checkpoint. `kogen intent resume <build-id>` validates the checkpoint and unchanged checkout first, then starts a fresh review; it must not replay builder rounds or completed green verification. Explicit resumes do not replenish the automatic retry allowance for that candidate. (source: request)
- Separate the existing one-rejection allowance from the existing one-no-tool reminder allowance. A rejected submit_review does not spend the no-tool reminder, and a prose-only turn does not spend the rejected-verdict allowance. Neither allowance is raised. Preserve the existing unread-parts progress exemption and delivery validation. (source: request)
- On the request immediately following the no-tool reminder, require submit_review at API level when the selected provider/route supports forced named tool selection. Otherwise retain today's reminder text. Log whether API forcing or text-only fallback was used, without credentials. Valid-verdict paths that never need a reminder send byte-identical requests. (source: request)
- Review attempts and terminal invalid reasons are retained in the run log, including both counters and retry/resume lineage. A valid approve or changes verdict follows today's path; a substantive blocker is not an invalid verdict and must not be bypassed by this mechanism. (source: request)
- Shared-host tests use temporary directories and local fake providers only, never synthetic CPU load or process-name/pattern termination; only processes started by the test may be terminated. (source: request)

The green candidate identity is the exact verified tree, not merely a pass number. Record durable automatic-retry consumption so interruption and Resume cannot reset it. Before automatic retry or review-only Resume, check exact tree identity and all ordinary HEAD/index/approval/configuration/protection/custody preconditions. An invalid review that changed candidate contents cannot borrow the earlier green pass. Do not relax uncertainty checks for shell, writes, incomplete tool batches, commits or external executors without evidence of a completed safe boundary. Only a completed, read-only review with no candidate writes qualifies for the new boundary treatment. A review-only checkpoint starts a new review, not the old invalid conversation; this also avoids requiring an external executor to support conversation resume. Retain the same configured reviewer kind.

Implement within the existing Build/review/checkpoint/request machinery (`cli/build/review.go`, `review_external.go`, `resume.go`, state and request plumbing as needed). Native provider rendering is in `cli/third_party/kogen-loop/provider/`; follow the repository's sync/pin convention for any necessary vendored changes. Make forcing a per-request option used only on the reminder turn, not a global profile change. Responses named-function selection is `{ "type": "function", "name": "submit_review" }`; Chat Completions uses `{ "type": "function", "function": { "name": "submit_review" } }` where supported. Do not equate protocol compatibility with host capability. Anthropic's current adaptive-thinking route and external executors use the text-only fallback rather than disabling thinking or changing executor policy to force a tool. Preserve normal tool definitions, replay and validation; forcing is a request constraint, never acceptance of an unread or malformed verdict. Do not add an extra inference attempt or paid capability probe on a provider rejection. Restore ordinary tool choice after the reminder request. Retain the counters and pending reminder choice across supported working-window/checkpoint continuation boundaries.
