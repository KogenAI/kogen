# Let Shape write long packages in bounded pieces

Slug: k-shape-long-replies
Model: not applicable — proposals stay the existing latest-wins map per path and the invalid-submission count is unchanged; no new state machine
Acceptance:
- .kogen/intents/k-shape-long-replies/acceptance.feature
- features/steps/k_shape_long_replies_steps.js

Fix K-SHAPE-LONG-REPLIES (change_type: fix). A native Shape reply can be 30-56K output tokens: at about 29 tokens/s one request takes 6-14 minutes (max 825 s), 2-4 requests per research cell ran over 120 s, and the shape was still writing when its time ran out. Nothing in those replies was rejected or wrong; the cost is the size of one answer. Today the shaper must put the whole package (intent.md, acceptance.feature, step files, model) into one `submit` call: a partial `submit` is checked as a complete package and counts as one of the three invalid submissions, and a cut-off reply (`response.incomplete`, for example `max_output_tokens`) is a non-retried provider error that stops Shape, so the only way to finish is one very long reply.

After this change a native Shape can retain files in bounded pieces before checking them, through a new model-facing tool `propose_files`, and finishes with an ordinary `submit` that checks the complete accumulated package exactly as today. A cut-off reply then loses only itself: earlier pieces stay in the conversation (the loop's existing retry of a dropped stream resends a request whose history already holds them) and in private custody on disk, which a provider stop now names. No option, setting, size limit, timeout or retry changes; no CLI change; no reply size is enforced (bounded pieces are guidance in the tool description and the shaper policy). Same validations: `submit`, readiness, lint, audit, decision check, step self-check, fixers, retained-artifact rules and publication are unchanged.

### The `propose_files` tool (native Shape only)

- Definition (cli/agent/defs.go, `ProposeFilesTool = "propose_files"`): built with the existing `fun` helper, `strict: false`, parameters `{files: pathAndContent(true)}` with `files` required, and exactly this description: `Retain Intent files without checking them yet, so a large package is written in bounded pieces across several replies: put one long file, or a few short ones, in each call and make one call per reply. Same path rules as submit's files; well-formed proposals accumulate (latest content for a path wins) and are kept privately under .kogen/local/shaping/<slug>/proposed/ as soon as they are accepted; a malformed or unsafe call retains nothing. A proposal is not a submission: it runs no checks and never counts as an invalid submission. End with submit, whose files (at least one, for example the last file) complete the package Kogen checks; a reply cut off before its tool call loses only that reply.`
- Native Shape's tool list becomes `read_file, view_image, list_files, search_text, probe, documentation, propose_files, submit` (then `shape_batch` when shape workers are enabled). Refine, init's setup conversation, shape workers and the external (Claude Code) shaper do not get the tool.
- Handling in `shaping.converse` (cli/shape/shape.go), beside `submit`: only the `files` argument is read. It is validated by the same rules as `submit`'s files (`validateFiles`: path/content strings, relative normal paths, only `.kogen/intents/<slug>/{intent.md,acceptance.feature,model.qnt}` and files under the steps folder, unique paths); a missing or empty `files` list is the problem `propose_files takes a non-empty files list`. A refused call retains nothing and its output is exactly `invalid proposal:\n` + the problem lines joined by `\n` + `\nNo files from this call were retained; earlier proposals are unchanged.` (problem lines are the existing validateFiles texts, verbatim).
- An accepted call merges its files into the accumulated proposals (latest content wins), immediately writes every proposal to `.kogen/local/shaping/<slug>/proposed/<path>` with exact bytes (the existing writeManifest custody), records one evidence event `{"event":"proposal_retained","paths":[<this call's paths, sorted>],"proposed":<number of distinct proposed paths>}`, prints the progress line `kogen: shape proposal retained: <this call's paths joined by ", "> (<n> proposed file(s))` through `sh.progress` (which appends ` (<elapsed> s)`), and returns exactly `retained: <this call's paths joined by ", ">; <n> proposed file(s) in all. Nothing was checked: submit to check the complete package.`
- A proposal is not a submission: it does not increment the submission count, is not an invalid attempt (`turns.invalid`, `submission_refused` events and the retry limit are untouched), starts no new attempt, writes nothing into `.kogen/intents/` or the steps folder of the checkout, runs no fixer, readiness, audit or decision check, and does not change declared steps or originals. A response whose only calls are `propose_files` (and reads) is a tool response, so the no-tool reminder does not apply; the conversation continues with the cumulative manifest as today. The existing rule that calls after a submit result in the same response are ignored applies to `propose_files` too.
- A later `submit` of files (still nonempty; for example only the last file) merges and checks the complete accumulated package exactly as today. A `submit` of questions or blocked ends Shape as today.

### Cut-off replies

- Unchanged: a dropped stream is retried by the pinned loop with the same request; `response.incomplete` is not retried and ends native Shape as `shape/provider_failed` (exit 4) with the existing rendered provider error and detail sentence.
- New: when native Shape stops on a provider failure while at least one proposal exists (from `propose_files` or an earlier submit), it prints, after the rendered provider error and before returning, exactly one stdout line `kogen: shaping kept <n> proposed file(s) under .kogen/local/shaping/<slug>/proposed/: <sorted paths joined by ", ">`, and those custody files hold the exact proposed bytes. With no proposals no such line is printed. There is still no persistent Shape resume or proposal replay across invocations.

## Decisions
- Long shapes progress through a new native propose_files tool plus guidance; no reply size cap, option, limit, timeout, retry or CLI change is added (source: request)
- Submit, readiness and every existing validation stay unchanged; propose_files reuses submit's file rules verbatim and never counts as an invalid submission (source: request)
- A cut-off reply loses only itself: earlier proposals stay in the conversation and in private custody, and a provider stop names them; no cross-invocation Shape resume is added, preserving the settled README principle (source: request)
