# Refuse observers that reject real runner output

Slug: k-shape-observer-runner
Model: not applicable — one more refusal in the existing Shape readiness gate and one more guidance paragraph; no new state or transition
Acceptance:

Fix K-SHAPE-OBSERVER-RUNNER (Studio kogen issue e3a24ce5-2787-42af-ad61-c113744cb22f, the same shaped-acceptance family as 42502600 / K-SHAPE-CONTRACT-CONSISTENT). Protected acceptance steps written at shape time checked the Rails runner summary with `/1 tests?, N assertions, .../` or passed `-n '^name$'` / `-i '^name$'` as the test filter. Under minitest's default reporter (what `bin/rails test` prints with `CI_PROGRESS_BAR=0`, as in the lanes/Studio cell environment) the summary reads `1 runs, 7 assertions, 0 failures, 0 errors, 0 skips`, and minitest matches a `-n`/`-i` value as a literal name, so an anchored regex runs nothing (`0 runs`). Research's model-free replay (real `bin/rails test`, `CI_PROGRESS_BAR=0 PARALLEL_WORKERS=2`) showed all 7 saved observers rejecting a passing test; builders correctly stopped `build_blocked` in 7 of 9 AoR cells.

After this change a protected acceptance step that observes a test runner is checked against that runner's real output on the unchanged tree: Shape refuses a candidate whose step fails although the minitest run it observed passed, or whose anchored regular expression given as a literal `-n`/`-i` name filter made the run match nothing; a correct observer (it accepts `N (runs|tests)` and passes the plain test name) is published as before. Shape's instructions tell the shaper to derive a runner's summary wording and name-filter semantics from a real run on the unchanged tree. No new command, flag, option or setting; no limit, timeout or retry change. Nothing else is replaced or removed.

## Shape: the runner-observer analysis
- Where: in `cli/verify`, beside the named-test analysis (`missingNamedTests` in `cli/verify/namedtests.go`), for every scenario whose report is complete and whose status is `failed`. It reads the failing step's failure message exactly as the named-test analysis does (the worst step result's `message`, else its `exception.message`). The result reaches Shape with the scenario result (for example a `ScenarioResult` field that is never serialized, like `Unwritten`); the readiness record format (version 3) is unchanged. Passed scenarios have no result.
- Summary: the last match in the message of the regular expression `\b(\d+) (runs|tests), (\d+) assertions, (\d+) failures, (\d+) errors, (\d+) skips\b` (minitest's summary line under its default reporter, `N runs`, and under progress reporters, `N tests`). Without a match the scenario has no result.
- Passing run: the summary has runs ≥ 1 and failures, errors and skips all 0. The result is exactly `the step failed although the test runner reported a passing run: <summary>`, for example `the step failed although the test runner reported a passing run: 1 runs, 7 assertions, 0 failures, 0 errors, 0 skips`.
- Anchored literal filter: the summary has runs = 0, and a `Run options:` line of the message (from `Run options:` to the end of that line, as minitest prints it) contains a name filter option `-n`, `-i`, `--name` or `--include`, preceded by the start of the line text or whitespace, followed by whitespace or `=` and a value. The value is a double-quoted string (minitest quotes values containing `$`, spaces and similar; the surrounding quotes are removed) or else the next run of non-whitespace characters. It counts when it begins with `^` or ends with `$` and is not of the form `/…/` (minitest's regular-expression form, at least two characters, starting and ending with `/`). The first such filter in the message gives the result, exactly `the name filter <option> <value> is a regular expression that the runner matched as a literal test name, so nothing ran: <summary>`, for example for `Run options: -n "^test_widget_passes$" --seed 4242` and `0 runs, 0 assertions, 0 failures, 0 errors, 0 skips`: `the name filter -n ^test_widget_passes$ is a regular expression that the runner matched as a literal test name, so nothing ran: 0 runs, 0 assertions, 0 failures, 0 errors, 0 skips`.
- Every other failed scenario has no result: a summary with any failure, error or skip (a legitimately failing or skipped existing test), zero runs with a plain name or a `/…/` filter, and no summary at all.

## Shape: the refusal
- Where: every Shape, native and external (`executor: claude-code`), in the readiness gate (`sh.rd.Gate`, set in `shape()` in `cli/shape/shape.go`, judged before anything is recorded), after the dry run accounted for every scenario and before the candidate is returned as readiness observations or accepted as ready.
- Precedence: the existing unwritten-tests refusal wins. When any scenario has an unwritten test, the `unwritten_tests` refusal is given exactly as today (its headline and only its items); the runner-observer refusal is judged only when no scenario has one. Example: a candidate with one scenario running a not-yet-written Go test and another failing on a passing `1 runs, …` summary gets only the unwritten-tests refusal.
- Refusal: when at least one scenario has a runner-observer result, nothing is published for this submission, and its tool result (external Shape: the next round's feedback) is exactly the headline
  `Acceptance rejects the test runner's real output: <N> scenario(s) fail although the test runner reported a passing run, or pass an anchored regular expression as a name filter the runner matches literally; nothing was published. A step that observes a test runner must accept the summary the runner really prints on the unchanged tree (minitest's default reporter prints "N runs", other reporters "N tests") and give a literal name filter (minitest's -n and -i) only the plain test name. Rewrite these steps; resubmitting them unchanged is refused again.`
  followed by one line per such scenario in feature order, exactly `- <scenario name> (line <line>): <result>`, joined by single newlines with nothing after the last line. N is the number of such scenarios.
- It is an invalid submission under the existing rules (SHP-4): one `submission_refused` event with gate `runner_observer` whose problems are the item lines; it counts on the shared invalid-submission counter; accumulated proposals stay; the written files stay as after other not-ready feedback. A refused candidate supplies no readiness evidence and is never acknowledgeable: an unchanged resubmission is refused again with the same text, never `accepted: unchanged checked observations acknowledged`. At the third invalid submission Shape ends as today with `intent/not_ready: the Intent is not ready to build` and the item lines (exit 1); the files of that last attempt stay.
- A candidate without results continues unchanged: accounted red goes back as readiness observations to acknowledge, green is ready.

## Shape: the guidance
After the existing `Unwritten tests:` paragraph in `cli/shape/context.go` (the named-test and unwritten-tests paragraphs kept unchanged), Shape's instructions (`ShaperInstructions`, native and external) add exactly this paragraph, ending with a newline:
`Test-runner observers: a step that runs a test runner and judges its output must accept that runner's real output on the unchanged tree, in the environment acceptance runs in. Derive the summary wording and the name-filter semantics from a real run of an existing passing test there, not from memory; an observer control's known-good input is that real output, not hand-written runner text. For example, minitest's default reporter (bin/rails test with CI_PROGRESS_BAR=0) prints "1 runs, 7 assertions, 0 failures, 0 errors, 0 skips" where other reporters print "1 tests, ...", so match "N (runs|tests)"; minitest's -n and -i match a plain name literally, so pass the test name itself, never ^name$. Shape refuses a candidate whose step fails although the test runner it ran reported a passing run, or whose anchored name filter made the runner run nothing.`
Refine's instructions do not carry it, like the other two paragraphs. `cli/agent/prompts/shaper.md` is unchanged.
