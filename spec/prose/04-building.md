# 04 Building

A Build is Kogen's own model/tool loop: a builder conversation with five tools that edits the checkout until verification (05) is green and review (06) approves. There is no time or token limit on a Build; a Build ends in exactly one of these ways: `commit` (landed), `baseline_changed`, `head_moved`, `hook_changed_commit`, `commit_failed`, `context_exhausted`, `review_invalid`, `review_blocked`, `build_blocked`, `no_progress`, `provider` or `interrupted`.

**LOOP-1 — Build directly.** After preflight, the Build starts the builder conversation on `models.build` with the approved Intent and project context. There is no separate planning model request. The builder may plan its work within that conversation.

**LOOP-2 — Prompt.** The builder's first message holds the Intent's `intent.md` (its `## Tests` section lists the tests to add or update), `acceptance.feature` and `model.qnt`, the text of `docs/testing-rules.md` (SET-6), the root `README.md`, the configured commands, the protected paths with the rule that approval freezes them and changing them ends the Build, the LOOP-5 rules for commands (stdin is closed; finite tests and browser suites run in the foreground; only persistent servers/watchers run in the background with logs and cleanup). Editable dependency manifests do not permit weakening, removing or bypassing checks or changing actual verification configuration. Preserve every configured check and its behavior; whole-file protection of a combined check-definition manifest has no dependency-only exception. The builder follows the table of section 2 of the testing rules, the case rules of section 3 and the restrictions of section 4, and runs the affected tests as it works (VER-13). Never `AGENTS.md` or `CLAUDE.md`. Optional fresh Build diagnostics append one separate labelled caller diagnostic data message; they do not replace this first message or builder tool instructions. They are explicitly lower-authority data: the current exact approved Intent and mechanical protected/check/review/commit rules win. Stale/contradictory notes cannot authorize protected changes or bypasses. Previous candidates are untrusted old data. Selective inspection and reproduction of suitable production work through native read/shell/write tools is allowed; automatic copy/apply/import, `git stash apply`, importing old protected harness bytes and reusing old verification as current proof are not. Do not encourage whole-tree rereading/copying.

**LOOP-3 — Tools.** Exactly:

| Tool | Arguments | Result |
| --- | --- | --- |
| `shell` | `command` | exit status and combined stdout and stderr |
| `view_image` | required string `path` | ordered typed text metadata and original PNG image content, or bounded actionable error |
| `read_file` | `path`, optional `start_line`, `end_line` | numbered lines, or an error |
| `write_file` | `path`, `content` | `ok`, or an error |
| `finish` | `summary` | starts verification |
| `report_blocker` | `paths`, `reason`, `evidence` | validated builder-reported protected contradiction stops without a commit |

There is no patch tool.

**LOOP-4 — File rules.** `read_file`, `view_image` and `write_file` resolve paths against the repository root. `write_file` refuses protected paths (VER-8) as a tool error, not a Build failure: `refused: <path> is part of the approved acceptance baseline`.

**LOOP-5 — Shell.** A `shell` call runs `/bin/sh -c <command>` in the repository root, in a new process group, with stdin closed (`/dev/null`), so a command that asks for input fails at once instead of waiting. No command has a time limit. The call returns when its `sh` process exits, with the exit status and the combined stdout and stderr (stderr included even when stdout is empty). A finite command, including a test or browser suite, runs in the foreground until completion even when it takes minutes; the tool waits without another model request. Do not poll such tests through repeated sleep/tail/ps calls. Only a persistent command — a dev server, a watch mode — is started by the builder in the background (`<command> > <log file> 2>&1 &`); the builder reads its log file and stops it (`kill`) with further `shell` calls. When the Build ends — commit, failure or Ctrl-C (CLI-7) — Kogen terminates the process groups of every command it started, background ones included.

**LOOP-6 — Responses.** Each response is streamed (GPT-7); tool calls are assembled from their argument fragments and run in order. A call with invalid arguments or an unknown tool gets an error result; the Build goes on.

For a validated optional `## Stages` plan, a builder finish (or no-tool response) instead runs fixers and fresh Snapshot scratch setup followed by only the active stage's ordered commands. First red stops commands with actual failure/output and not-run accounting; mutation or interruption is not green. Red repairs stay with that same builder and stage. A clean green milestone is retained privately with exact approved identity, tree, commands/outcomes and stage id/index before advancing once. `stage_pass` events name id/index/tree/green/failing/not_run. Complete authority and replay stay present; the active 1-based stage adds navigation, never scope clipping. No reviewer, final acceptance/model, interim commit or approval consumption occurs between stages.

After the last stage, immediately run the normal complete fresh whole gate. Final red stays in finalization, never restarts earlier gates. Only whole green proceeds to fresh independent whole review; reviewer repairs keep normal whole verification. Stage evidence is historical for its recorded tree, not proof for later edits. `stages.qnt` abstracts ordered milestones and whole delivery.

**LOOP-7 — Finish.** A `finish` call, or a response without tool calls, ends the round: Kogen runs the fixers and verification (05), then review (06) after a green pass. Failing pre-review checks become the next builder message. A green candidate enters one independent review/fix stage (06); its repairs receive external final verification and failures remain with that reviewer. Unresolved substantive review blockers stop with preserved work instead of returning to the builder. Ordinary implementation failures and expected missing-feature red still require repair; plain blocked text is not a terminal result. A native round that ends without any tool call, whose verification pass (or stage gate) is the same red as the pass whose full feedback it answered (same stage, same candidate tree, same failing items, clean and without moved files), stops immediately with `candidate/no_progress` (exit 1): no further fixer round, verification or model request starts, and edits, history, checkpoint and approval are preserved. Verification materializes exactly the candidate tree, so ignored files cannot make the same tree a different check input; a tool call (including `finish`), a changed tree or mode, or a different stage or failing set is progress, and there is no pass or round cap. `kogen intent resume` verifies again and returns the feedback to the same builder. External executors keep their own `max_rounds`. The builder may call `report_blocker` with exactly `paths`, `reason` and `evidence`: a nonempty unique list of concrete paths in the current approved protected baseline, nonempty contradiction reason and observed command/step/error evidence strings. Malformed, empty, duplicate or out-of-scope reports return ordinary tool feedback and grant no write permission. Before accepting a report, existing baseline and HEAD guards take priority. A valid report stops immediately with `candidate/build_blocked` (exit 1), labelled `BUILDER-REPORTED`, explicitly not independently proven. Record its paths/reason/evidence/classification in the run log and optional `blocker` result metadata. No later tool call in that same response executes, even after an earlier `finish`; no post-report fixer, verification, review or commit starts. The existing failure path preserves candidate edits, original index and approval. This is no successful gate bypass, automatic refinement, reapproval, replay or resume. Do not distort production semantics solely to satisfy a demonstrated protected fixture defect.

**LOOP-8 — Output size.** All model-facing text tool results, including errors and control-tool feedback, share Shape.output/Tools.cut in native Shape, Refine, Build, independent Review and optional Shape workers. Results of at most 16384 UTF-8 bytes are preserved exactly. Larger results keep the first 4096 bytes (backing off only an incomplete UTF-8 character), then `\n[... N bytes omitted ...]\n`, then a valid UTF-8 suffix fitting the remaining room. The 16384-byte limit includes the marker; N counts actual original bytes absent. Conservative marker-width reservation and character backoff may leave a few bytes unused. Bounding is idempotent. The delivered display is paired with its call and replayed exactly, never recut on reset/resume. The review-only deferral below applies solely to complete pinned-source reads that have not yet reached the reviewer. Line ranges are not byte limits: even explicitly selected ignored working-context custody reads use this visibly incomplete display when oversized. Ordinary fitting reads preserve numbering, ranges, whitespace and errors. Private originals, authority and archives remain complete; documentation records are parsed and probe outcomes retained before presentation bounding. Complete pinned Review source delivery remains required before approval. Typed view_image results pass unchanged through Tools.cut and Shape.output. Shell/read_file, paths, base64 text and captures do not deliver pixels. The shared UI-evidence guidance is owned by `docs/testing-rules.md`, section 2 (LOOP-2, REV-2). This does not guarantee that authority, arguments, large batches or images fit the unchanged complete-request ceiling.

Explicit view_image accepts one selected static non-interlaced RGB8 PNG, 1..131072 original bytes, width/height 1..2048. Validate signature, framing/CRC, required chunks, encoding, legal filters and bounded decompression; refuse animation and malformed/unsupported data with actionable external preparation guidance. Success is an ordered input_text JSON metadata block then input_image with exact original PNG data URL, never text substitution. Metadata version 1 records path, lowercase sha256, bytes, format png, width, height, read_candidate when established; capture_candidate, route, viewport and fixture_state remain UNKNOWN absent separately established evidence. Filenames/current checkout do not bind capture provenance. No detail/resolution guarantee is introduced.

Freeze outputs once in existing ordered conversations, private archives and version-3 checkpoints; never reread selected paths or replay tools to reconstruct outputs. Full outbound serialized JSON, including typed envelopes/base64, authority/tools/cache/replay, must fit 524288 UTF-8 bytes inclusive, reserve 131072 tokens. Completed safe Build/Review window reduction remains unchanged. Irreducible requests stop candidate/context_budget_exceeded before inference, retaining custody and naming owner, measured/mandatory size, ceiling, reserve and external preparation or ordinary Refine/new-approval guidance. Compact image_read and image_delivery events distinguish read from completed/failed/unknown delivery; observations remain assistant content, not success flags. Events are bounded to 8192 bytes with bounded path/identity text and no raw pixels or opaque reasoning. Raw custody is private (0700 directories/0600 files). Image observations cannot grant authority, clear checks/blockers or establish design approval.

**LOOP-9 — Bounded working windows and context exhaustion.** Before every builder/reviewer request, measure the complete JSON envelope using the working-context measure of the request body: 524288 UTF-8 bytes inclusive, with 131072 output/reasoning tokens reserved conceptually (not a new provider parameter). Bytes are a conservative proxy, not usage or a measured refusal threshold. At completed request/tool-batch boundaries only, oversized windows archive full ordered native replay in immutable private 0600 JSON files under `.kogen/local/runs/<id>/working-context/<owner>/` (0700 directories), linked by exact-byte SHA-256. An explicitly labelled user message starts `Local working-window reset\n` followed by version 1 JSON identifying owner, phase, exact candidate/approval, honest candidate-bound checks, lossless model observations, unfinished work, unresolved findings and ordered history references. References already listed verbatim in the mandatory pinned-source catalog are cross-referenced by count instead of repeated; native history and exact-byte custody retain every reference. Authority, frozen diagnostic data and source retrieval stay in every window; retain the latest complete exchange when it fits. Opaque reasoning/assistant phase and delivered tool pairs are never edited or orphaned. If mandatory Review context fits but the newest batch does not, only complete reads of pinned source parts not delivered in any earlier window may be deferred, last first, until the request fits. Each deferred output becomes an explicit native not-delivered notice paired with its original call; the reset lists deferred part numbers. The archive and retained input contain the substituted window actually sent. Deferred parts remain unread, retain their hash-bound originals and must be read again before approval; ordinary tool outputs, images, partial reads and prior delivery remain unchanged. If this bounded deferral cannot fit, refuse normally. Reviewer windows remain independent and continue the same repair owner. A reset is not approval, green evidence, completion or a new critique. Edits make earlier green stale. Irreducible authority/exchanges or reduction without progress stop before inference with `candidate/context_budget_exceeded`, measured/mandatory bytes, ceiling/reserve and checkpoint/history inspection and ordinary Refine/new-approval guidance. There is no total-run cap, automatic splitting or universal provider-exhaustion guarantee. When the provider reports that the conversation no longer fits the model's context, the Build ends with `candidate/context_exhausted: the conversation no longer fits <model>'s context; edits are left in place` (exit 1).

**LOOP-10 — Run record.** Each Build attempt writes `.kogen/local/runs/<build-id>/log.jsonl` (requests with model, effort, usage and `wall_ms`; tool-call names and argument/result byte counts and hashes, never raw private history or originals; verification passes; reviews; the outcome) and `result.json`. Credentials never appear (GPT-10). Request-start notices name the role/model/effort on stderr; response notices report usage and wall time without copying response content.

Continuation is explicit: `kogen intent resume <build-id> [--project <checkout>]` acquires
the ordinary Build lock and reads an atomically published version 3 `checkpoint.json` (with working-window and source continuity state).
It validates checkout identity, original HEAD, exact approval, complete protected
baseline/configuration, candidate bytes/modes/additions/deletions, excluded Intent custody
and index before model calls or mutations. The index must record exactly the saved staging: the same
version, entries (path, mode, object, stage, flags, extended flags) and extensions byte for byte
(including Git's cache-tree); only each entry's
stat cache (ctime, mtime, dev, ino, uid, gid, size), which a plain `git status` refreshes, may differ,
and only between complete version 2/3 indexes with valid checksums. Other forms must be byte-identical.
Original staged owned acceptance remains valid.
Unsafe/damaged/incompatible state is `candidate/resume_refused` (1); missing/legacy state
is `candidate/resume_unsupported` (1), with ID and inspection/correction/fresh-approval guidance.
No files, index, HEAD, approval or prior evidence are repaired on refusal. An exact already
landed commit is a successful no-op, not another commit. Pending effects are never replayed;
uncertain tool or commit execution may be refused with inspection instructions.
Checkpoint publication precedes requests and side effects and follows durable completion.
Complete replay input includes tool results, not merely diagnostic log tails. Resume retains
the phase and repair owner, including the same independent review conversation and external
verification of repairs. Only completed exact clean green evidence need not run twice, except when explicitly
reopening `candidate/review_blocked`: that retry invalidates earlier approval/evidence,
runs fresh setup and the ordinary fail-fast complete gate, and gives actual red/unrun or
green results plus the original finding to the saved independent reviewer. It never
restarts the builder or creates a new critic. Incomplete retry verification restarts setup;
completed exact retry evidence survives a failed/interrupted provider request but cannot
replace a new decision. Version 2 and older checkpoints are explicitly incompatible and refused without changes, never silently started as fresh Builds; incomplete verification reruns fresh setup and checks under its saved repair owner. Each resumed
attempt has parent/root lineage and its own outcome; prior artifacts remain byte-for-byte.
Known usage and counters accumulate; incomplete requests have unknown usage, never invented
tokens. Measured request intervals exclude stopped downtime. Credentials and the caller's
entire environment are never checkpointed. Protected-contract blockers require normal
correction and fresh approval, not continuation against changed authority.

**LOOP-11 — Environment.** Setup, `shell` calls, fixers, checks, the acceptance command and Quint run with stdin closed, without a time limit, and with the caller's environment unchanged except for the two acceptance variables of VER-3, plus `KOGEN_NODE` (the absolute path of Kogen's own Node, INS-4), `KOGEN_CUCUMBER` (the `node_modules` folder of the Cucumber Kogen ships, INS-2), which the acceptance commands of SET-10 use, and `KOGEN_QUINT` (Kogen's Quint `cli.js`, which a shaping probe runs with `KOGEN_NODE` to check a model before submitting, SHP-10); Kogen adds nothing else, and never its credentials. A real `shell` call of the installed default configuration succeeds.

**LOOP-12 — Tools.** Before any model request, shaping and Builds check that `git` and `/bin/sh` are available and — when the Intent has a model — that Kogen's own Node (the path recorded in `<prefix>/lib/kogen/node-path`, INS-4) and its bundled Quint exist. A Build then runs `commands.setup` (AUT-5) and afterwards checks the first word of each configured command, so executables that setup creates count: Kogen skips leading `NAME=value` words and the shell's own `(`, `{` and `!` in front of the program, and runs `/bin/sh -c 'command -v <word>'` in the repository root, which also finds shell builtins. The generated runner's `"$KOGEN_NODE"` word resolves to the installed Node path before this lookup. Shaping checks them the same way after its setup (SHP-2). Missing: `environment/tool_missing: <name> is not available` (exit 3; for Node and Quint the detail names the path and says to reinstall Kogen). Quint always runs with exactly these resolved paths (VER-5), never through the caller's `PATH`.

**LOOP-13 — Progress.** During a Build, stderr gets one line per step: `kogen: running setup-<n>: <command>` (also in shaping and readiness), `kogen: checking <name> before the Build changes anything`, `kogen: building (round <n>)`, `kogen: verifying (pass <n>)`, then `kogen: pass <n>: all checks passed`, `kogen: pass <n>: <names> failed` or `kogen: pass <n>: files changed while the checks ran: <paths>`, `kogen: reviewing (review <n>)`, then `kogen: review <n>: <verdict>, <k> blocking`, and `kogen: committing`.

Scenarios: `features/04-building.feature`. Model: `quint/build.qnt`.

Fresh Build diagnostics have private local custody in `diagnostic-context.json` in the run directory: exactly `text`, `source_path`, `sha256`, preserving original UTF-8 bytes independently of approval. Fresh Build reads once; resume accepts no new context. Every new working window retains this diagnostic, never check-state or protected-byte import. After protected-contract correction, archive native production externally with absolute paths/hashes, obtain new exact approval, then use production-clean fresh `build --context FILE` for selective inspection/reproduction only. No automatic stash/patch/tree replay or old green evidence.

The decoded version 3 saved Build exposes `working_context` and `source_provenance`. Its active window, ordered archive hashes, owner, observations/findings and bound source receipt are atomically checkpointed with existing candidate/HEAD/index/approval/configuration guards. Missing, changed, unsafe or unreadable referenced custody refuses before inference/mutation. Pre-window versions remain inspectable but unsupported. Existing uncertain-effect safeguards remain unchanged. Source absence is explicitly legacy, not reconstruction from prose; bound corruption is never absence.


Under LOOP-7/LOOP-10, `kogen intent recover <build-id> --output <new-directory>
[--project <checkout>]` explicitly preserves then clears only a completed protected
blocker's implementation delta. The caller-relative destination must be new, outside
the resolved checkout and nonsymlinked. Unsupported/missing/extra arguments including
`--context` are usage errors (2). The normal Build lock guards exact version-3
checkpoint/result/BUILDER-REPORTED blocker, same checkout identity, start HEAD,
protected baseline/configuration, approval, complete candidate, original index and
bound working-context/image/source custody. A completed blocker may retain its tool
continuation; other uncertain tools/commits are refused. Missing/legacy checkpoints
are candidate/recovery_unsupported (1); drift, malformed or unsafe facts are
candidate/recovery_refused (1), naming inspection/correction guidance before cleanup.
No provider, setup/check command, stash or commit runs.

A complete private archive is published before cleanup: 0700 directories and 0600
regular files, manifest.json version 1 with build/slug/absolute project/start_head/
start_tree/candidate_tree/full contract_sha256/classification BUILDER-REPORTED,
sorted changes (path, before/after null or Git mode and exact raw SHA-256), and sorted
artifacts covering every regular file except manifest itself. before/ and candidate/
retain binary bytes, executable modes, additions/deletions and symlink target bytes
(mode 120000, never followed). All protected and excluded other-Intent paths are
excluded from the delta, as are unrelated ignored outputs. index-at-start, approval.json,
checkpoint.json and result.json are byte-exact; blocker.json retains the report.
Bounded UTF-8 correction.md/context.md contain run, original contract hash, absolute
archive and evidence references/hashes; context is nonblank and at most 262144 bytes.
They label the report unproven and archived production lower-authority diagnostic
information, not authority or current proof; large artifacts are referenced, not clipped.

Print the absolute manifest path/hash; retain a private receipt under
.kogen/local/recoveries/<build-id>.json with archive/hash and preserved/cleaned state.
After publication, recheck source identity, restore only recorded implementation bytes
and modes and remove only recorded additions. Keep HEAD, original index, protected files,
approval and run evidence unchanged. Failure after publication retains durable custody
and an honest incomplete diagnostic; caught cleanup failure validates/restores candidate
bytes. Never overwrite an output or reconcile a drifted partial cleanup by guessing.
Print (but do not invoke) ordinary Refine of the same slug with ORIGINAL full hash and
correction.md, review/fresh exact approval, and a production-clean FRESH Build with
context.md. Refine independently investigates and passes readiness; correction revokes
old approval, so Build refuses until fresh approval. No automatic import or old green
reuse is allowed; normal setup/verification/model/independent review/final-tree checks
and approval consumption on landing remain unchanged. context/inspect are read-only
observation, not polling, scheduling, cancellation or retry authority.

Staged run results, checkpoints and read-only inspect retain `stage_progress`: total, completed ids in plan order, current active id (null after stages), and phase `stage`, `final`, `review` or `landed`. Landed means the single ordinary commit, never partial progress. Explicit same-checkout Resume validates exact plan/progress and private contract/tree-bound stage evidence in addition to all existing custody guards. It continues the saved owner/conversation without rerunning completed stage gates or effects. Incomplete gates rerun fresh setup. Malformed stage state refuses, never degrades to unstaged. Version-3 unstaged records remain supported without invented progress; older versions remain unsupported. Working-window handoffs retain this navigation and historical evidence under the unchanged inclusive 524288-byte ceiling and 131072-token reserve.

**LOOP-14 — Build executors.** `models.build.executor` (SET-14) selects who produces each round's candidate: `native` (the default; every rule above) or `claude-code`. An executor only produces a candidate in the checkout; its result is a claim (`finish`, `no_call`) plus untrusted text and never means verified, approved, reviewed or committed. Every round, whichever executor ran it, ends in Kogen's own round end: the fixers, verification (VER-6), independent review (REV-1) and the single exact-tree commit (GIT-1). A red result goes back to the same executor session as feedback. After every external round Kogen checks the acceptance baseline and HEAD exactly as it does after a native shell call, so a changed protected file or a moved HEAD ends the Build with `baseline_changed` or `head_moved`, whatever the executor reported and whether or not its own prevention refused the write. `max_rounds` (default 6 for an external executor) bounds the rounds: a candidate still unaccepted when the last round has ended stops with `candidate/executor_round_limit` and leaves its edits in place. The checkpoint of an external executor cannot be resumed: `kogen intent resume` refuses it with `candidate/resume_refused` and changes nothing. The run log records the executor, its exact version, every round (`executor_round_started`, `executor_round_ended`), each hook decision and the harness-reported usage. An external executor adds the endings `executor_round_limit` and the `executor/*` stops of LOOP-15 to the list above; with `native`, behavior is unchanged.

**LOOP-15 — Claude Code executor.** `executor: claude-code` runs the user's installed `claude` headless in the checkout on the user's own subscription sign-in and nothing else. Kogen strips API-key, base-URL, cloud-provider and nested-session variables from its environment and never passes `--bare`. A binary that is missing, or older than the qualified version, stops the Build with `executor/unavailable` before any edit. A sign-in that is not the claude.ai subscription on Anthropic's own API, or an init event whose credential source is not the subscription (`apiKeySource` not `none`), stops with `executor/auth_refused` before any edit; there is no paid-route fallback. The first round starts a session named by Kogen; every later round resumes that session (`--resume`) with Kogen's feedback. A PreToolUse hook that is part of Kogen refuses Write, Edit, MultiEdit and NotebookEdit of a protected path, of anything under `.git` and of anything outside the checkout, and every such tool call must have run the hook or the round is stopped. That is prevention only: shell commands are not prevented, and a protected file changed through one is found by the LOOP-14 baseline check, so detection and verification apply unchanged. Token usage and cost are reported by Claude Code (an API-equivalent estimate, not a bill) and recorded as harness-reported, never as provider-exact.
