# 02 Shaping

`kogen intent shape <slug> <file|->` turns a request into an **Intent**: short prose, executable Gherkin with its step definitions, and a Quint model when the change has meaningful state or interacting rules (not for copy changes or plain wiring). The shaper makes the requested behavior precise, proves its risky technical assumptions with quick throwaway probes, asks the caller about material UI/UX choices, chooses straightforward technical details itself, and adds only what the requested behavior needs. It never approves and never builds.

## The Intent

`.kogen/intents/<slug>/` holds `intent.md`, `acceptance.feature` and, when needed, `model.qnt`. Step definitions live in step files under `commands.acceptance.steps_dir`: existing files that are reused or edited, or new ones.

```markdown
# Add an is-even helper

Slug: is-even
Model: not applicable — a pure function without state
Acceptance:
- .kogen/intents/is-even/acceptance.feature
- features/steps/is_even_steps.js

calc.is_even(n) returns True for even integers and False for odd ones; non-integers raise TypeError.

## Decisions
- Non-integers raise TypeError instead of returning False. (source: answer 1)

## Tests
- calc.is_even returns True for even and False for odd integers: add test_is_even in tests/test_calc.py (unit)
- calc.is_even raises TypeError for a non-integer: add test_is_even_rejects_floats in tests/test_calc.py (unit)

## Feasibility
- `1.5 % 2` returns 1.5 in python3 instead of raising, so is_even checks the type itself. (probe 1: exit 0, 0.1 s)
```

`## Tests` lists, for each behavioral rule the request adds, changes or removes, the test to update or add, chosen by the table of `docs/testing-rules.md` (SET-6): one line `- <rule>: <test to add or update> (<layer>)`, where `<layer>` is `unit`, `integration`, `scenario`, `regression` or `existing`; or `- none: <reason>` for a change with no executable behavior (copy, documentation).

With a model: `Model: .kogen/intents/<slug>/model.qnt invariants=<Name>[,<Name>...] seed=<n> samples=<n> steps=<n>`. For direct probes use a Boolean expression, e.g. `quint run model.qnt --backend=typescript --invariant='A and B'`; commas belong only to Intent metadata `invariants=A,B`.

## Requirements

**SHP-1 — Input.** The slug matches `^[a-z0-9]+(-[a-z0-9]+)*$`, 3–48 characters (`intent/invalid_slug: Slug must be 3 to 48 characters and use lowercase letters, digits and dashes.`, exit 2). The request comes from a file or stdin (`-`), is read by the `kogen` command and passed as protocol data, never in argv. Empty, missing or unreadable input is `intent/request_unavailable: <stdin|abs path>: <empty|not found|unreadable>` (exit 2). When the request file is untracked inside the repository, shaping prints `note: <path> is untracked; commit or move it before kogen intent build`. The command blocks until shaping ends.

**SHP-2 — Preconditions.** Before any model request, shaping refuses: an uninitialized project (`environment/not_initialized: <path> has no .kogen/project.yaml; run kogen init`, exit 3), an invalid configuration (SET-4), an unset `commands.acceptance.run` or `commands.acceptance.steps_dir` (`environment/acceptance_unconfigured: set commands.acceptance in .kogen/project.yaml`, exit 3), a missing tool (LOOP-12), no login (GPT-5), a slug that is already shaped (`intent/exists: <slug> is already shaped; edit its files, or delete .kogen/intents/<slug>/ and shape again`, exit 5), and, right before the first request, a failing `commands.setup` (`environment/setup_failed`, as in AUT-5, exit 3), then a configured command whose program is missing (LOOP-12), then an acceptance command that does not start: it runs once on a feature with no scenarios, as in SET-13, and must exit 0 and write its report, else `environment/acceptance_unavailable: <reason>; fix commands.acceptance.run in .kogen/project.yaml` plus the start and end of its output (exit 3). So a broken environment costs no model time. While `commands.checks` is empty, shaping prints `warning: commands.checks is empty; Builds will not run your tests` on stderr.

**SHP-3 — Context.** The shaper receives the request, the root `README.md`, a deterministic index-first source navigation context with zero automatic optional source-body excerpts, the configured commands, the configured `protect` patterns, the paths currently matched by those patterns using the same public expansion as Build protection, and the automatic baseline contract: the Intent files, its `Acceptance:` paths and `.kogen/project.yaml`. It receives the Intent format and rules of SHP-6, the text of `docs/testing-rules.md` (SET-6; its section 6 is how the shaper specifies the change), and exact known step signatures and ranges (or complete paged signature references) in `steps_dir`, with exact-byte retrieval routes, with the instruction that its Gherkin may only use sentences those files or the step files it writes define. Approval freezes this baseline; it is not an exception or authorization to change a protected path. The shaper must inspect implementation edits required by the requested outcome, not infer conflicts by scanning arbitrary request prose. It has read-only tools `read_file`, `list_files` and `search_text` (paths are resolved against the repository root) and the `probe` tool (SHP-10). It cannot write project files.

**SHP-4 — Submission.** The shaper ends by calling `submit` with exactly one result: `questions`, `files`, or `blocked`. A blocked result has the exact shape `{"blocked":{"paths":["relative/protected/path"],"reason":"why the requested change requires this edit"}}`; paths and reason must be nonempty, and every path must be protected by the current baseline contract, including configured globs. It is a report, never authorization. A valid blocked result writes no new Intent or approval and starts no Build; it ends with exit 1, `shape/protected_conflict: required edits touch protected files: <paths>` in submitted order, the supplied reason, and `Next: revise the request, or review and commit .kogen/project.yaml outside Build, then shape again; preserve checks and actual check configuration. There is no protected-edit override.` A manual configuration review is outside Build and changes the approval baseline; it is not approval of a protected edit. If a previous not-ready submission exists, its files retain the existing SHP-4 behavior. Validate the entire file envelope, content types, normal owned paths and uniqueness before merging; an unsafe, malformed or duplicate-path mixed payload contributes no entries. Within one conversation, well-formed proposals accumulate: latest content for a path wins, omitted paths retain earlier proposed bytes, and explicit original content reverts an edit. The files array is nonempty. Lint, parse and readiness edits may submit only changed files; unchanged-red acknowledgments follow SHP-8. The complete accumulated package is validated before writing. An invalid submission goes back with its problems and writes nothing; well-formed proposals rejected by Intent validation remain available for correction. Previously declared proposed JavaScript steps must remain listed in `Acceptance:` and a proposed model must remain declared; abandoning these paths rejects the candidate before writing so retained executable steps cannot leave the approval baseline. Check those declarations again after formatting, before readiness or acknowledgment can certify the final package. Existing auxiliary-file ownership rules are unchanged. Omission cannot delete a proposal: preserve and park the partial package and its exclusively owned new step files, remove the now-empty Intent directory, then use normal shaping again with the same slug or a new one to discard an earlier new artifact. No deletion DSL, persistent proposal state or cross-invocation replay is provided. A valid complete merged submission is written, then the project's fixers (`commands.fix`, in order, progress `kogen: running fix-<n>: <command>`) run once in the repository root, so the Intent's files are formatted as the project formats files. The fixers' changes to the accumulated submission's files are kept: the card, the approval hash and the Build's checks on the unchanged tree see the formatted files, and the Build's own fixer rounds find nothing left to change in them. What the fixers change anywhere else is undone. The files are then checked for readiness (SHP-8); if the checks find problems, those go back to the shaper in the same way, and its next attempt overwrites the complete accumulated files, preserving omitted proposals. After a not-ready attempt the shaper may also ask questions (SHP-6); the files of that attempt stay. Invalid and not-ready submissions share one counter: at the third failed submission in a row shaping stops (exit 1). After an invalid one it prints `shape/invalid_output: the shaper's output was not a valid Intent after 3 attempts` plus the last problems. After a not-ready one it prints `intent/not_ready` (SHP-8), and the files of that last attempt stay. Files may only be the Intent's own files and step files under `steps_dir`, new or existing: shaping may prepare edits to existing step files, which the caller reviews with the Intent before approval and which are then fixed for the Build (VER-1). Every shaping progress line includes elapsed whole seconds since shaping started; a model request is printed as `kogen: shaping (request 2, 95 s)`.

**SHP-5 — Intent rules.** An Intent is valid when: `intent.md` has a title of at most 50 characters without a final period (it becomes the commit subject, and 50 characters is the common limit commit-message hooks enforce), `Slug:` equal to the folder, a `Model:` line, a non-empty `## Tests` section whose every line has the form above, and an `Acceptance:` list starting with its `acceptance.feature` whose paths exist and are not ignored; every `## Decisions` item names its source (`request` or `answer <n>`); a `## Feasibility` section lists each probe the shaper ran (or `- none`) with what it showed and its result (SHP-10); `acceptance.feature` parses (VER-3), every scenario has a `Then` step and none is tagged `@skip`, `@wip`, `@pending`, `@manual` or `@ignore`; a named model typechecks and its invariants exist. A model is required only when the change has meaningful state or interacting rules, never for copy changes or plain wiring; with `Model: not applicable — <reason>` the shaper says why. Problems print `intent/parse: the Intent cannot be read` or `intent/lint: the Intent needs changes` with one indented line each (exit 1). For a change to the acceptance runner or a step library, the Intent's scenarios exercise it through an independent harness listed in `Acceptance:`; the files that implement the requested change stay editable.

**SHP-6 — Questions.** The shaper asks only about material UI/UX choices the request leaves open; it decides technical details itself. Questions write no Intent file (files of an earlier not-ready attempt stay, SHP-4), are stored under `.kogen/local/shaping/<slug>/`, and print (exit 5):

```
Questions for is-even:
1. What should is_even do with a non-integer?
   a) raise TypeError (recommended)
   b) return False
Answer one per line as <n>: <letter or your words>, e.g. printf '1: a\n' | kogen intent shape is-even -
Or enter all: recommended to use every question's recommended option.
```

While questions are pending, the next `kogen intent shape <slug> <file|->` reads answers from the file or stdin (`-`), one per line as `<n>: <answer>` where the answer is an available option letter or free text — typed by a person or written by an agent alike. If no parsable answer line is present, it refuses with `intent/answers_invalid: expected one or more lines as <n>: <letter or your words> (or all: recommended)` (exit 2). A letter that is not an option for that question is refused with `intent/answer_option_invalid: question <n> has no option <letter>` (exit 2). The special input `all: recommended` answers every pending question with its marked recommended option. Pending questions are answered before anything else, even when files of a not-ready attempt exist (SHP-2's `intent/exists` does not apply). Unanswered questions are printed again (exit 5) without a model request. Answered questions, the request and earlier rounds go to the shaper, which may ask again. Deleting `.kogen/local/shaping/<slug>/` discards pending questions.

**SHP-7 — Never authorizes, never invents.** Shaping writes no approval and starts no Build. A blocked result cannot authorize a protected edit and cannot be paired with a ready package. The only manual configuration action is a supported review and commit of `.kogen/project.yaml` outside Build; it changes the baseline for a later shaping/approval cycle and must not be described as approval of a protected edit. Every UI/UX decision in `## Decisions` names where it came from (SHP-5); whether the prose quietly decides something else is for the caller's review (AUT-1).

**SHP-8 — Readiness.** After writing the files Kogen checks: the SHP-5 rules; the model (`quint typecheck`, `quint test`, and one `quint run` per named invariant with the stated seed and bounds, VER-5); and a dry run (`commands.setup`, then the acceptance command on this Intent, VER-3) that must account for every scenario exactly once as `passed` or `failed` — any `undefined`, `pending`, `skipped`, `ambiguous`, missing, duplicate or unexpected scenario is not ready. Binding readiness is checked separately from the scenario result: every undefined or ambiguous step rejects readiness even when an earlier assertion in that scenario failed. Defined downstream steps skipped because an assertion failed are allowed. Only stable checked bytes supply reusable evidence under `.kogen/local/readiness/<slug>.json`, owned by readiness. It records the full baseline/hash and HEAD, current title, ordered scenario results including outline grouping/counts and actual failure details, acceptance exit, and model declaration/check outcome. Errors retain at most 20 lines per failure with explicit omitted-line markers; per-detail and total rendered feedback use the existing 16 KiB UTF-8-safe byte cap and explicit omitted-byte markers. An accounted failing assertion is valid readiness, not a failed readiness check. Before reporting ready, Kogen returns its actual failing scenario, step or hook/location, bounded error, acceptance exit, evidence reference and complete checked baseline/hash/HEAD to the same shaping conversation. The model inspects whether fixtures, inputs and commands reached intended behavior, repairs demonstrated contract defects using its existing tools, or acknowledges legitimate missing-feature red. After inspecting legitimate missing-feature red, submit the smallest eligible owned artifact with its exact current candidate whole body, including previously proposed corrections. The files array must be nonempty; if only one eligible large artifact exists, submit its entire body. Omitted well-formed proposals remain retained: do not retransmit large unchanged prose/helpers or restore original disk bytes for acknowledgment. Publication and acknowledgment still concern the exact complete package. No exception-name classification, hard green baseline or extra reviewer is involved. Failures can mask later cases; acknowledgment is inspection opportunity, not universal fixture-health proof. Exact unchanged acknowledgment reuses the same checked full baseline, HEAD and Snapshot candidate tree without another readiness execution; changed candidates or inputs are checked normally and receive their own observations. Green readiness completes immediately. Observation feedback does not increment the invalid-submission counter. Missing, malformed, incomplete legacy, failed or mismatched evidence runs normal readiness with its real diagnostics. Reuse never represents a fresh execution. Recompute the complete baseline, HEAD and Snapshot candidate tree around checking and publication; changed inputs cannot be certified. Build preflight, setup, verification, review and commit guards remain fresh and unchanged. Ready (exit 0):

```
Intent: {abs:.kogen/intents/is-even/intent.md}
Acceptance test: {abs:.kogen/intents/is-even/acceptance.feature}
Step files: features/steps/is_even_steps.js (new)
Model: not applicable — a pure function without state
Scenarios: 3 (3 fail now, 0 pass now)
shape {model}/{effort} input={n} cached={n} output={n} reasoning={n} wall_ms={n}
Next: kogen intent approve is-even
```

Not ready: during shaping the problems go back to the shaper (SHP-4). When shaping stops, and for `kogen intent approve`, Kogen prints `intent/not_ready: the Intent is not ready to build` with one line per problem, naming file, line and step text for undefined steps (exit 1); the files stay for the caller to fix or delete. A genuine protected conflict is reported before readiness: when the required edit cannot avoid a protected path without changing the requested outcome, the shaper submits `blocked`, not a ready package conditional on unavailable approval. The output names the protected paths and reason and states the supported next action. If the caller keeps a legitimately protected combined manifest, revising the request is the Build path.

**SHP-9 — Provider failures.** A provider error stops shaping with the `provider/…` line and the `shape/provider_failed` sentence (CLI-6, exit 4); the failed request wrote no files (files of an earlier not-ready attempt stay, SHP-4). The sentence tells the caller to fix the provider issue and rerun with the same input: it names the request file path when a file was used, or says to pass the original request on stdin (`-`) and the same answers when questions are pending.

**SHP-10 — Feasibility probes.** While shaping, the shaper proves the risky assumptions the Intent depends on — that a library call behaves as assumed, a tool or service is reachable, a command works in this project — with quick throwaway probes. Probes run in a copy of the project outside the repository, so tools that trust folders (mise) may need `mise trust` first. The `probe` tool takes `command` (a string for `/bin/sh -c`) and `files` (optional scratch files to write first). Kogen runs it in a scratch copy of the working tree under the system temporary folder, never in the project: every file including ignored ones such as installed dependencies and builds, without `.git/` and `.kogen/local/`, cloned copy-on-write where the file system supports it, so a probe can compile and run the project as it is; each probe is stopped after 5 minutes (SIGTERM, then SIGKILL after 5 seconds) and its result is `exit status`, `timed_out` and the combined output (at most 16 KiB, as LOOP-8). Probe completion reports exit status, timeout and duration on stderr without echoing output; completed model responses report usage and wall time. The scratch copy is deleted after the probe; nothing of it is kept in the project. The shaper records each probe in the Intent's `## Feasibility` section (SHP-5). Probes are only for genuinely uncertain assumptions the Intent depends on, not a ritual for ordinary implementation knowledge; most Intents need none and record `- none`. A failed probe is a finding, not an error: the shaper reshapes around it or, when it is a UI/UX matter, asks (SHP-6). Probe state does not change the Intent's lifecycle, so no Quint model is needed; the scenarios check that the project is untouched.

**SHP-11 — Correct an existing ready draft.** `kogen intent refine <slug> <sha256> <file|->` takes a correction request and the full 64-character lowercase SHA-256 from the draft's review card. It requires an existing ready Intent, no pending shaping questions, and the same baseline hash. If approved, its approval must match that full current hash; a mismatch is stale. Preserve and stash ordinary unfinished implementation changes first: approved refinement permits only the normal Build-clean paths (GIT-1), otherwise `environment/dirty_tree` (exit 5). Refinement never stashes or reapplies a candidate. A stale hash refuses with `intent/refinement_stale` (exit 1) before any model request. Refinement holds the existing project Build lock; approval takes that lock too. It freezes HEAD, the complete nonignored checkout tree, the acceptance-baseline hash, raw approval bytes (or absence), and the actual Git index digest, establishes original readiness using an existing complete valid version3 `Readiness.cached` record for the exact full protected-baseline hash, declarations and HEAD, or checks the original in scratch on a miss, and uses `models.shape` with the usual read/probe tools and `submit_refinement`.

A valid hit intentionally skips that one fresh-original configured setup/model/acceptance execution, including nonempty setup. Version 3 validation requires the exact Snapshot candidate tree as well as baseline, declarations and HEAD; version 2 and older are misses. Raw-index checks remain operation safety, not cache eligibility. Retained original observations are evidence, not an executed fresh scratch check or proof of current environment readiness. Missing, malformed, invalid or stale records fall back to normal original scratch readiness with its mutation guard. `original-readiness.json` records hit/miss, reason, retained/scratch source, baseline/HEAD/reference and actual new execution counts; avoided measurements absent from older evidence are null. Every changed complete candidate runs fresh configured setup (a copied stamp cannot bypass it), fixers and normal readiness; drift can therefore fail it. Exact unchanged acknowledgment retains full-baseline/HEAD/current-observation checks and does not repeat readiness. Original evidence grants no candidate, approval, Build or shared-artifact authority.

The model submits exactly `{"files":[{"path":"existing/path","content":"complete replacement"}]}` with a nonempty array of whole-file contents (only changed existing files for edits; smallest eligible current-candidate artifact for acknowledgment as in SHP-8), or `{"constraint":"why the correction needs unsupported work"}`. Within one refinement run, well-formed proposals accumulate: the latest proposal for a path wins; omitted paths retain earlier proposed bytes, or their original bytes if never proposed. To revert a proposal, submit its original content explicitly. Validate the entire incoming envelope, file types, unique paths and ownership before merging: an unsafe or malformed mixed submission contributes no entries and leaves earlier proposals intact. Editable paths are the existing Intent's own `intent.md`, `acceptance.feature` and `model.qnt`, and listed step files under `steps_dir` which are absent from HEAD and referenced by no other Intent. Configured protected paths, symlinks, shared/tracked step files, configuration and other Intents are ineligible. New files, deletions, changed `Acceptance:` paths, model addition/removal/path changes and UI/UX question continuation are unsupported; report `shape/refinement_constraint` (exit 1), preserving the draft, rather than silently replacing its contract.

Each submission resets scratch to the original frozen tree, overlays the complete accumulated proposal map, runs configured fixers and complete readiness, and returns readiness problems for correction, at most three invalid/not-ready submissions (`shape/refinement_invalid`, exit 1). Lint, parse and readiness failures retain well-formed proposals for correction in that same run; unparseable Model metadata is a lint failure, while a parsed change in model presence or path is an unsupported topology change. No root files or approval change before final merged readiness. Fatal topology changes, fixer changes outside accumulated owned paths, or readiness mutations still refuse publication. Success publishes every accumulated final formatted file, rather than only the last submission. Accounted red candidates return actual bounded observations through the same conversation before publication; submitting the smallest eligible owned artifact with its exact current candidate whole body as in SHP-8 acknowledges the retained complete candidate without a second readiness execution. Changed candidates or baseline/HEAD require normal readiness and fresh observations. Original baseline observations are also in refinement context. Bounded candidate observations remain in the existing refinement evidence directory; no partial or unacknowledged candidate is published. Proposals do not resume across separate invocations. Recheck the original hash, HEAD, checkout tree, index and exact approval bytes before publishing ready replacements; an external change gives `intent/refinement_stale` and is never overwritten. Failed, provider, blocked/constraint, stale and interrupted operations leave the original draft and approval unchanged. Request, original artifacts, candidate submissions, diagnostics and result are retained under `.kogen/local/refinements/<id>/`; temporary warm preparation and clean proof directories are removed. Only the last successfully checked merged candidate may supply root readiness evidence after publication confirms its complete baseline, candidate tree and frozen HEAD match; failed submissions cannot publish earlier readiness. Successful publication archives the exact old approval as `revoked-approval.json` in the refinement evidence and removes it under the same lock. Publication or revocation failure rolls back this operation’s replacements and retains the original approval; external edits are never overwritten. Abrupt process death is not a crash-atomic multi-file transaction: any changed package with an old approval fails Build’s existing hash check. Fresh explicit approval is always required. Success prints `refined <slug> <sha8>`, changed paths, the evidence path and `Next: kogen intent approve <slug>`. It never approves or builds. Model: `shaping.qnt` `BuildOnlyOnCurrentApproval`, `ApprovalOnlyByCaller`.

Scenarios: `features/02-shaping.feature`. Model: `quint/shaping.qnt` (`NoApprovalWhileAsking`).

Native Shape and Refine provide a deterministic single-line `Context index: <JSON>` with shared repository root and revision, sorted exact path/full SHA-256/byte/ownership entries, exact signature line ranges and directory counts. Ordinary entries resolve from root plus path; frozen originals and signature pages retain explicit source overrides. Automatic optional source-body inclusion is deterministically zero, including Acceptance steps, named paths and licences. Existing read/list/search tools retrieve exact bodies and ranges. Explicit bounded excerpts carry only path, SHA-256 and line ranges in their headers, with at most 80 lines/8192 UTF-8 bytes of body; they never amend literal requests, Q&A, contracts, proposals or actual failures. Exact contracts win budgets with disclosed reasons; exact originals and cumulative proposals have retained retrieval references. Focused scratch probes answer named uncertainties, not a duplicate manual full acceptance gate. ## Clean final readiness

Final readiness uses a fresh disposable directory materialized from `Snapshot.tree`, with exact tracked (including ignored tracked) bytes, executable modes, additions/deletions and synthetic local Git. It runs verbatim declared setup before model/acceptance; ignored untracked dependency/build outputs are neither copied nor linked. Caller environment, installed tools and declared services remain available: this is not hermeticity. Raw scratch mutations, including staged additions, reject proof. Source identity is rechecked around execution and publication, including approval. Disposable directories are removed on success, failure and interruption. Exploratory probes remain warm.

Readiness record version 3 adds `candidate_tree` to the complete baseline/hash, HEAD, declarations and actual model/scenario/exit evidence. Only exact unchanged clean evidence is reusable; version 2 and older are normal misses, never migrated. Ignored untracked warmth does not affect identity; nonignored changes, deletions, executable modes, tracked ignored changes, HEAD, protected baseline and declarations do. Retaining original-precondition evidence skips only original setup/model/acceptance, not fresh changed-candidate proof, and is not current-environment proof. Refine tests and publishes its complete accumulated formatted proposals; Shape tests its final formatted files. Accounted red remains inspectable and exact unchanged acknowledgment reuses the same clean observation. Build verification, review and explicit caller approval remain separate.

Shape and refinement retain complete authoritative originals and settled Q&A before changing candidate/manifests and lower-authority evidence. They preserve valid opaque reasoning and assistant phase in append-only replay, without promoting caller material to developer policy. Native workers retain independent cache/comparison state.

## Declared feasibility obligations (SHP-8, SHP-10, SHP-11)

Declared shaping evidence is optional and selected by shaping judgment, not a universal registry or coverage claim. Before expensive implementation, identify genuinely uncertain outcome-critical dependencies. Probe the actual proposed request on its supported target route, authentication scope and model, or use a real relevant local fixture; a working old driver or exclusion-list silence does not prove a changed request. Distinguish observed support, explicit rejection and untested uncertainty. Unsupported requests need an honest supported outcome/fallback or clarification of a material UX choice. No blanket paid probes or endpoint sweep.

In `## Feasibility`, add one single-line JSON bullet per explicit obligation, for example:
`- evidence: {"id":"route","kind":"capability","inputs":["route.json","route.cjs"],"observers":[],"checks":[{"name":"support","command":"node route.cjs","exit":23,"output":"explicit rejection\n"}]}`
Ids are unique. Paths name exact repository-relative regular files, including local executable fixtures. A capability has one `support` check. An observer names the final generated protected observer file(s) in `observers` and has exactly two checks in order, `good` and `bad`: those same observer bytes must accept the known-good fixture and reject the known-bad fixture. Every check declares a shell command, expected integer exit and exact combined output string. Nonzero expected exit is legitimate observed rejection; timeout never discharges an obligation. These are small targeted controls, not product implementation or a second acceptance suite. Scratch overlays can explore, but final proof identifies submitted final formatted input/observer bytes. Fresh actual evidence can qualify only identical commands, bytes and outcomes. Narrative, fabricated records, model-only green and missing-feature red cannot qualify a declaration. Readiness executes outstanding checks and retains actual mismatches. Exact red acknowledgment cannot waive an unsatisfied obligation; ordinary no-obligation work needs no probes.

Preserve the complete original request, settled scope and supplied reproducing examples and counterexamples in executable acceptance, not only prose. Do not narrow whole-UI requests to one section or substitute an unconsumed prior-candidate pointer. Advice, proposals and host observations are lower-authority evidence, not product authority. Qualify risky protected observers using actual known-good and known-bad controls even when an earlier missing-feature failure masks them; baseline need not pass the unimplemented feature. Ground fixture/history actors in actual seed output; observe Search before resetting it; compare rendered HTML to rendered expectations, not raw Markdown; account for computed OKLCH rather than assuming RGB; distinguish compiler/process diagnostics from rendered payload; compare JSON objects semantically while preserving meaningful array and string order.
