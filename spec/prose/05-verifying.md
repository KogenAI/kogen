# 05 Verifying and repair

"Green" comes only from executed checks: the Intent's acceptance scenarios run against the real code, its Quint model, and the project's checks. Failures go back to the builder until everything is green. Repair fixes the implementation; it can never pass by weakening the approved assertions. This is a cooperative integrity contract: commands run with the caller's permissions and no sandbox is claimed.

**VER-1 — Acceptance baseline.** The baseline is: everything in `.kogen/intents/<slug>/`, every path in its `Acceptance:` list, `.kogen/project.yaml`, and every file matching `protect`. Its hash is what the caller approves (AUT-2). Approval freezes this baseline; it is not authorization to change a protected path. These are the protected paths of the Build. Dependency-only manifests and lockfiles remain editable inputs when not included by the contract; their editable portions never authorize weakening configured checks or actual verification configuration. Combined manifests defining checks may be explicitly protected whole-file, with no dependency-only exception. Implementation tests not in the list stay editable.

**VER-2 — Bindings.** Each Gherkin step is bound by a step definition in a step file that exercises the real behavior (runs the program, calls the code or inspects its output); expected values live in the feature file. Readiness rejects undefined or ambiguous bindings even when the same scenario also has a failed assertion. Shaping reuses, edits or adds step files; the caller reviews feature and step files together before approval (AUT-1).

**VER-3 — Acceptance command.** The acceptance command runs with the caller's environment plus `KOGEN_ACCEPTANCE_FEATURES` (the Intent's feature path) and `KOGEN_ACCEPTANCE_REPORT` (an absolute path in the run folder). Paths may contain spaces; the command quotes both environment expansions as single arguments. It runs exactly those features with a strict runner and writes the report as Cucumber Messages NDJSON (`@cucumber/cucumber` 13.3.0 with `--strict --format message:<path>`), from which Kogen reads each test case's scenario key and final status. The runner is the project's own Cucumber when it has one, else the `@cucumber/cucumber` 13.3.0 Kogen ships, both on Kogen's own Node (SET-10, SET-13). The **scenario key** is the feature path plus the line of the `Scenario` keyword, or of the `Examples` row for an outline; the report gives it through `pickle.astNodeIds` and its own `gherkinDocument`.

**VER-4 — Scenario accounting.** Kogen parses the feature itself, with its own Elixir parser of the Gherkin it needs (English keywords: `Feature`, `Rule`, `Background`, `Scenario`/`Example`, `Scenario Outline`/`Scenario Template`, `Examples`/`Scenarios`, steps, tables, doc strings, tags), to know the expected scenario keys. Acceptance passes only when the command exits 0, the report parses, and every expected scenario appears exactly once as `passed` in a test case that finished with a result for every one of its steps (an unfinished case counts as `report_invalid`) with nothing else present. Otherwise the feedback names each problem: `failed`, `undefined`, `pending`, `skipped`, `ambiguous`, `missing`, `duplicate`, `unexpected`, `report_missing`, `report_invalid` (each once, with the command's exit status and the start and end of its output as in VER-5, not once per scenario), or `exit <n> with all scenarios passed`.

**VER-5 — Quint.** For an Intent with a model, each whole-Intent pass runs Kogen's own Quint 0.33.0 with Kogen's own Node (INS-4; resolved the same way in preflight and execution, never from the caller's `PATH`) and the TypeScript backend (no Apalache, no Java): `quint typecheck`, `quint test` when tests exist, and `quint run --invariant <name> --seed <seed> --max-samples <samples> --max-steps <steps>` per named invariant. Any failure fails the check named `model`; its feedback keeps the start of Quint's output, where Quint names the error, and the end (the whole output when it has at most 60 lines, else the first 30 and the last 20).

**VER-6 — Pass and repair.** After each builder round Kogen runs `commands.fix` once, then materializes the Snapshot candidate tree in a fresh disposable directory (not a worktree or clone), preserving bytes and executable modes, additions and deletions. No ignored workspace output or dependencies are copied or linked. A fresh local Git index and synthetic HEAD identify this exact candidate tree, so declared commands can inspect its tracked inputs; user Git metadata, hooks and history are not copied. It runs declared setup afresh in order without a setup stamp, stopping on its first failure; a setup failure is failed verification with command, status and bounded output returned to the current repair owner. For packages without stages, and during staged whole-Intent finalization/reviewer verification, after successful setup it runs acceptance, the applicable model, then project checks in declaration order, stopping between items at the first definitive failure. Commands run verbatim; only an explicitly configured Cucumber `--fail-fast` stops cases within the acceptance runner. Model subcommands retain VER-5 semantics. Each pass, pass log event, checkpoint and stopped result records an ordered `not_run` list of later required setup-N, acceptance, applicable model and project-check names; feedback and progress/stopped summaries name these as not run because an earlier item failed, retaining executed diagnostics. An absent model is not applicable. Fixers and model tools stay in the user checkout; verification commands use the disposable directory with the normal caller environment, tools and services. The directory is removed on completion, failure or cancellation; reports and bounded diagnostics remain in the original run evidence. Failing checks go back to the builder with name, command, exit status and the last 60 lines of output (acceptance: failing scenarios with step and error). There is no repair limit. This pass is the "before commit" step of VER-13.

**VER-7 — Final pass.** Scoped stage passes (LOOP-6) are historical milestones only, never whole-Intent green evidence or commit eligibility.  A partial pass is never green or reusable. An empty `not_run` list alone proves nothing: completeness is validated against required acceptance scenarios, applicable model and declared checks, including on resume. Compatible complete old clean evidence remains reusable without the new field; workspace-only evidence does not. A whole-Intent pass is green when fresh clean setup and every check passed and nothing in the tested candidate inputs, workspace candidate or baseline changed while it ran (VER-9). The green builder pass enters review/fix (06). Reviewer changes receive a new external pass; a stable approved candidate reuses its green pass. Final failures remain with the same reviewer, and only identical green/approved contents can commit.

**VER-8 — Baseline protection.** `write_file` refuses protected paths. After every `shell` call, fixer and pass, Kogen recomputes the baseline hash; if it changed, the Build stops at once with `candidate/baseline_changed: the Build changed acceptance files: <paths>; nothing was committed; review the files, then approve again or discard the edits` (exit 1). Neither this guard nor baseline membership has a dependency-only exception for an explicitly protected combined manifest. The builder and reviewer preserve configured checks and actual check configuration when editing unprotected dependency metadata. A genuine protected conflict must be reported while shaping; the supported next action is request revision or a manual `.kogen/project.yaml` review and commit outside Build, which changes the baseline, never an override. Model: `build.qnt` `BaselineChangeNeverCommits`.

**VER-9 — Changes during checks.** Kogen snapshots the workspace candidate (VER-10) and baseline before and after a pass and compares scratch input membership, bytes and executable modes after setup/checks to the materialized tree. Ignored generated outputs do not count as mutations; tracked ignored inputs always do. Baseline guards retain precedence. Any difference makes the pass not green, whatever the checks said; the feedback lists `files changed while checks ran: <paths>`.

**VER-10 — Candidate.** The candidate is every tracked file and every untracked file not ignored by Git (`git ls-files --cached --others --exclude-standard`), with content and executable bit, except other uncommitted Intents' folders `.kogen/intents/<other>/`. Untracked ignored files never count and never enter a commit; tracked files always count. Commit-authorizing verification consumes only this exact input tree. Ignored outputs may be generated within a pass by declared commands, but ignored workspace outputs cannot supply verification inputs.

**VER-12 — Named negative cases.** Each ends without a commit: a wrong implementation the builder never fixes (the Build keeps repairing until the caller interrupts it); an undefined step (not ready, refused at approval); a failing Quint invariant (not ready, refused at approval); a changed baseline (`candidate/baseline_changed`); a validated builder-reported protected contradiction (`candidate/build_blocked`, LOOP-7), which stops before another pass and preserves evidence/work without claiming independent proof.

**VER-13 — Test sequence.** Tests run in this fixed sequence (`docs/testing-rules.md`, section 5): (1) during the Build the builder runs the tests its change affects, with `shell`; (2) before a commit Kogen's exact clean candidate verification pass (VER-6) runs the configured checks, which are the project's fast regression suite, and the Intent's acceptance scenarios, and no commit happens without a green pass (GIT-3); (3) before a release the full suite runs on the supported platforms (REL-4, REL-6); (4) live external-service tests run only when the change touches that integration, and for release acceptance (REL-1).

Scenarios: `features/05-verifying.feature`. Model: `quint/build.qnt`.
