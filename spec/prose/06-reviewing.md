# 06 Reviewing

After a green pass, one independent reviewer inspects the change and directly repairs supported defects. Kogen verifies changed contents externally before committing. An unchanged approved candidate reuses its existing completed exact clean green pass. Nothing commits unless the exact final contents have both approval and green verification.

**REV-1 — When.** The independent review/fix stage starts only after a green builder pass. It is one cohesive assessment of the requested outcome, not a recurring fresh critique after every minor repair. Final verification failures return to that same reviewer conversation with targeted feedback; they do not restart the builder or a new whole-change review. A material candidate change after the stage has completed still requires verification and approval under GIT-3. No promise is made that one assessment discovers every possible defect. Model: `build.qnt` `ReviewNeverOverridesChecks`.

**REV-2 — What the reviewer reads.** The Intent's `intent.md`, `acceptance.feature` and `model.qnt`; the text of `docs/testing-rules.md` (SET-6); the root `README.md`; the full unified diff of changed/deleted existing paths against the HEAD the Build started from; the complete current text of every changed or added file (a deleted file appears through its diff). Added source appears once, with its Git mode, instead of also being duplicated in the diff; gitlinks include their referenced commit ID; renames are represented as deletion/addition so neither side disappears; and the final pass's results (each check's name and status, the scenario count). It may read any other file of the repository with the tools in REV-3, for example a caller that should have been rewired or an old implementation that should have been removed. It does not get the builder's conversation: no assistant messages, tool calls or tool results. When the approved Intent has a `## Data stores` section (SHP-5) with at least one valid key, the authority carries, right after the `Acceptance:` line and its blank line of the `# Protected paths and configured commands` block, a `# Data stores` block followed by a blank line: the declared keys joined by `, `, the files tracked at the Build's start commit that reference a declared key (the same scan as Shape's, item validity judged at that commit and on the approved acceptance files in the checkout), one line each as `- <file> references <key> (line <n>)` (`(lines <n>, ...)` for several) followed by `: covered by <the covering item line without its leading "- ">` or `: not covered` (`- none` when there is no reference), and the instruction that a file that is not covered holds or reaches data the approved Intent neither scopes nor excludes by a Decision and needs a blocking finding at its path. Without the section, or without a valid key, the authority is unchanged. Explicit resume recomputes the same evidence from the same start commit.

When that complete initial source/diff would exceed the local working-window ceiling, the exact Intent/feature/model, README, testing rules, protection/configuration, final check results and frozen caller diagnostic remain mandatory and verbatim. Only candidate source/diff moves to private, hash-bound, ordered JSON parts; each complete part fits the existing text read-tool cap. The initial request contains every changed/added/deleted path, status, Git mode/blob ID, byte count and SHA-256, the source digest and candidate/start identities, and every exact part path/hash. Literal file names are not interpreted as Git pathspec magic. Concatenating their text in order restores the complete original source/diff; deleted contents remain retrievable from the pinned start HEAD. No authority or source is silently clipped. Small requests keep inline source. A still-oversized authority/catalog refuses before inference without source archive creation or altered checkout/index. The ceiling and output reserve do not change.

At a completed Review response/tool-batch boundary, preflight the complete rendered next request. If an initially fitting inline source message now causes pressure, relocate its exact original bytes with the same hash-bound ordered-part mechanism and attempt one deterministic smaller window. Exact authority, check results and frozen diagnostics remain mandatory. No duplicated package/source bytes are omitted from private custody. Already-pinned parts are reused, not re-pinned at each reset. The reduced complete request must be both smaller and at most 524288 bytes (equality fits), still reserving 131072 tokens. This is representation-only: the independent stage, delivered-part evidence, complete tool batches, opaque reasoning, observations and unresolved findings remain intact, without a new Build, builder replay or reapproval.

Supported version-3 inline checkpoints, including explicit resume after provider failure, convert from exact saved contract/source blocks rather than historical source reconstructed from checkout. Preserve established candidate/start bindings and the full path/status/mode/blob/byte/hash catalog. If no historical source/tree association was established, mark that source historical with unavailable tree binding instead of inventing one; newly materialized current evidence has its own current identity. Only native current-tree results authorize eligibility. Bound source/history custody is validated before inference and tool effects; damage is not permission to restart. Existing honest checkpoint/refusal semantics remain in force.

The independent reviewer must receive all pinned source parts through complete matching read_file outputs, or Kogen's own native source-data messages that carry each part's exact read_file text, in a completed continuation before an approving verdict is valid. A read call or same-response read-plus-approve is insufficient; missing, wrong-call or clipped outputs cannot count. Completed delivery remains provable through exact private working-window archives after a reset. Each Review reset handoff reports that native delivery so the reviewer need not rebuild it in every window: the tree the parts were pinned from and whether it is the candidate tree, how many parts were delivered and the numbers still unread, and every image this review was given, as of its newest delivery: path, SHA-256 and read candidate, whether that is the candidate tree and whether its pixels stay in the next window. These are facts the approval check and image custody already establish, not findings, judgments, approval or proof; parts and images of another tree are not current, and archived pixels need a fresh view_image. Early substantive blocking findings may stop without reading unrelated remaining parts. Source parts use the existing private checkpoint-history hash/mode/symlink validation, retain input=[] as evidence rather than builder replay, and stay available on safe resume. Missing/changed/unsafe custody refuses before another provider request or tool effect. Source references are evidence, never approval or permission to import the builder conversation.

A review by an external executor (Claude Code) receives its source as outgoing prompt data, not as read_file parts, and its complete first prompt is measured before it is sent: the executor's own report of the exact byte length of its first-round prompt for the role and brief (`len(Stable) + len(Dynamic)` for an executor that reports none), source included, against the same inclusive 524288-byte ceiling, which is not raised. A prompt that fits is one review in one fresh session, unchanged. A larger one is reviewed in ordered parts of the exact source, each in its own fresh session of the same model, effort, schema and `max_rounds` whose complete prompt fits: every part carries the complete authority, the final pass's check results, every changed path and one consecutive piece of the diff and full text of changed files. A part ends at a path's material boundary when that material fits one part, otherwise just after a newline, otherwise at a character boundary; nothing is clipped, and every part is written and measured before the first is sent. Parts are reviewed one after another with the same rounds, verdict validation, custody checks and exact-tree evaluation as a single session; an approval of an earlier part does not commit and the next part reviews the pass that approval bound (a verified repair included), only the last part's approval is the review's, a `changes` verdict of any part stops with `candidate/review_blocked` and no later part is started, and a part that ends without a valid verdict ends the whole review without one (the automatic fresh review and an explicit resume start again from part 1, as a new review number). Mandatory material (the authority, diagnostic context and the part's own header) that leaves fewer than 6000 bytes of the ceiling for source stops with `candidate/context_budget_exceeded` before any review is sent, and the candidate, HEAD, index and approval are unchanged. Claude Code's refusal of a prompt as too long (a result with `is_error` whose terminal reason is `blocking_limit` or whose text is `Prompt is too long`) is likewise `candidate/context_budget_exceeded`, never an ordinary executor failure, and is not retried.

**REV-3 — Who reviews.** `models.review` (default `gpt-6.1-terra`, effort `medium`, for every review size), in a fresh conversation independent of the builder, with `read_file`, `view_image`, `list_files`, `search_text`, `write_file`, `shell` and `submit_review`. It can investigate counterexamples and make scoped implementation/test repairs. File writes and shell execution have the same baseline protection as the builder. Configured fixers/check commands and protected paths are supplied. It uses focused/fail-fast checks during repairs; Kogen owns the complete final gate. It cannot commit or change HEAD, the approved baseline or the caller's staged work.

**REV-4 — What it judges and returns.** Review is against the approved Intent and explicit existing project conventions, including documented requirements that deterministic tools do not catch. Each substantive concern must identify an applicable requirement, a concrete violating path or counterexample and an observable consequence. Demonstrated current correctness, data safety, scope and meaningful-test defects, and violations of those requirements or conventions justify scoped repairs. False-passing tests and missing evidence of a required outcome are substantive; existing meaningful coverage can establish the outcome. A preferred test layer, duplication or implementation coupling alone is a note without a demonstrated current consequence. Data stores: the uncovered files of the evidence in REV-2 are the distinct files with at least one reference that no valid item covers, in path order. When there are uncovered files and some of them has no finding with `severity` `blocking` and exactly that `path`, the verdict (native and external) gets the problem `each data store the approved Intent omits needs a blocking finding at its path; the Intent neither scopes it nor excludes it by a Decision: <those files joined by ", ">`, placed after the `a changes verdict needs at least one blocking finding` / `an approve verdict cannot have blocking findings` problem and before the no-product-defect check. It goes back through the existing rejected-verdict allowance as `invalid verdict:` and the problems, so an approval is never valid while a file is uncovered, and a `changes` verdict with those blocking findings stops the Build as `candidate/review_blocked` as any blocking verdict does. The reviewer prompt carries a `Data stores:` paragraph before the paragraph that starts `Call submit_review`, which also tells the reviewer to search for the entity's id key itself when the approved Intent changes an entity's data and has no section.

Mechanical formatting and style are delegated to existing configured formatters, linters, checks and fixers, preserving their checks and settings. The reviewer must not make preference-only renamings, rearrangements, abstraction changes, speculative refactors or harmless nearby dead-code cleanup. Minimal incidental changes needed for a demonstrated repair or configured style or project requirement remain allowed; proximity or personal preference alone does not justify edits. The reviewer fixes supported defects together and adds or updates useful regression coverage, preserving useful tests and every configured check without inventing requirements. Approving unchanged correct code is success, with no edit quota; harmless preferences may remain nonblocking notes but neither block delivery nor require edits. It calls `submit_review` with `verdict` (`approve` or `changes`) and `findings`, each `{path, line, severity, message}` with `severity` `blocking` or `note`. `approve` has no unresolved substantive blocker; `changes` has at least one blocker the reviewer cannot repair within the approved scope/constraints. Every `path` must name a file of the start HEAD or candidate. A reply without `submit_review` is invalid. Within one review a rejected `submit_review` is sent back with its problems once and a prose-only turn is sent back with a reminder once, as separate allowances (the unread-parts progress exemption stays); the request right after the reminder requires `submit_review` through the provider's named tool selection where the route supports it, and carries today's reminder text only otherwise. A second spending of either allowance ends that review without a verdict. For the exact green candidate tree a review that ended that way gets one automatic fresh review (a new conversation of the same kind with the same material and rules, numbered as the next review); when that review also ends without a verdict the Build ends with `candidate/review_invalid: the reviewer did not return a valid verdict; edits are left in place` (exit 1) and a review-only checkpoint, and `kogen intent resume <build-id>` of the unchanged checkout starts one more fresh review without replaying builder rounds or completed verification and without replenishing the automatic retry. An invalid ending of a green candidate stops with a review-only checkpoint of the green pass the review session was started from, whatever executor runs the review and also for a review that had repaired or that left uncommitted edits, with the reviewer's uncommitted edits left in place; resume discards them, logs them as `review_edits_discarded` and starts the fresh review of that green candidate. Only a reopened blocked review, a moved HEAD (a reviewer's own commit included), a changed index, approval or baseline, and a review without a complete green base leave no review-only checkpoint; a substantive `changes` blocker is a valid verdict and is never retried this way.

**REV-5 — Effect.** `approve` binds the current candidate tree. If it equals the existing completed exact clean green pass, commit eligibility is checked without rerunning unchanged checks. Otherwise Kogen materializes a new disposable candidate directory, runs fresh declared setup and then acceptance, the model and every configured project check on the repaired candidate (VER-6). It commits only when the pass is green and its tree equals the approved tree. Failed checks or check-mutated contents return to the same reviewer conversation; unexpected changed-but-green contents require targeted approval before commit. `changes` stops with `candidate/review_blocked: the reviewer could not resolve a substantive blocker within the approved Intent; edits are left in place` (exit 1), followed by blocking `review: <path>:<line>: <message>` lines, preserving work, approval and the caller's original index. It does not automatically restart the builder. Explicit resume reopens this blocker only after fresh declared setup and complete
verification, returning the original finding and honest current results to the same
reviewer. A new `changes` stops again; only a new explicit `approve`, ordinary external
verification of edits and exact final green-tree eligibility permit commit. No operator
explanation is invented. Notes never block. Model: `build.qnt` `CommitOnlyWhenEligible`.

**REV-6 — Review cannot weaken checks.** Neither reviewer writes nor commands may change the baseline, configured checks or a check result. `write_file` refuses protected paths; the baseline is rechecked after reviewer shell commands and before accepting a verdict, as well as after final verification (VER-8). Editable dependency metadata is not permission to weaken verification. Do not alter production semantics or add test-facing hidden HTML comments solely to satisfy a demonstrated invalid protected fixture (for example, raw serialized HTML disagreeing with correctly escaped visible text). Investigate the actual output and failure, then use the existing `submit_review` verdict `changes` with a `blocking` finding naming the protected path, line and observed evidence when repair is outside this Build. This stop remains available after an earlier approval and failed final verification; targeted failure feedback reminds the reviewer of that route. It preserves work without authorizing protected edits or automatically refining, reapproving or resuming. Earlier green evidence or approval cannot resolve a reopened blocker, and failed or unrun obligations remain red. Changed protected contracts still require correction and fresh approval. A genuine unrepairable protected conflict is a blocked outcome; reviewing/committing configuration outside Build and shaping again changes the approval baseline, never supplies an in-Build override. Model: `build.qnt` `BaselineChangeNeverCommits`.

**REV-7 — Record and report.** Each independent review stage is saved as `.kogen/local/runs/<build-id>/review-<n>.json` (model, effort, cumulative usage, latest verdict/findings, approved tree and all valid submission attempts). Run events retain each attempt and reviewer tools/results; final verification passes are recorded normally. Blocked retries preserve the original finding, conversation/tool outputs, candidate, original-index backup, immutable failed artifacts, lineage and cumulative known usage/unknown requests. Targeted repair continuations share the stage number and conversation; `result.json` counts independent stages, not individual requests. While changed contents await final verification or targeted repair, the active review is pending despite a retained prior approval attempt. An interrupted or failed Build reports pending review, and verification when checks changed files, in `still_failing`. A landed Build prints `review: approved[, <n> note(s)]` and one `  note: <path>:<line>: <message>` line per note (GIT-8).

Scenarios: `features/06-reviewing.feature`. Model: `quint/build.qnt`.

The independent reviewer starts without builder transcript, reasoning, cache identity or cache comparison state. Its stable approved contract precedes fresh candidate and verification evidence. A saved reviewer retry keeps its own opaque replay and latest completed comparison, but still requires fresh verification and explicit clearance of unresolved blockers.

Independent review receives the approved source-provenance diagnostic retrieval reference, or `Source provenance: unavailable (legacy)`, never builder reasoning. Full originals are available through ordinary read tools; the approved Intent alone is implementation authority. Omissions require ordinary Refine and new exact approval. Local window resets preserve the same stage, observations and unresolved blockers and cannot clear native verification/review eligibility (LOOP-9).

The fresh reviewer has its own view_image invocation under LOOP-8, never builder pixels, transcript or visual judgments passed off as independent inspection. Capture relevance must be established or fresh external capture/handoff requested. Image input neither replaces complete pinned source delivery nor changes exact-final-tree eligibility.
